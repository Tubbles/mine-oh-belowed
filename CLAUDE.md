# Mine oh Belowed: instructions for LLM agents

Read this together with the global `~/.claude/CLAUDE.md`. This file holds the project's rules for agents; how things work is in the docs, entered through [doc/README.md](doc/README.md).

## Stack

- Language: Odin. Toolchain at `~/opt/odin` (release dev-2026-09). Do not install another Odin.
- Rendering, windowing, audio: raylib 6.0 through the repository collection `shared:raylib`, archives built by `tools/build_raylib.sh` ([doc/build.md](doc/build.md), The shared collection). Never import `vendor:raylib`.
- Controller input: SDL3 through `vendor:sdl3`, linked against the host `libSDL3.so.0`, with the joystick and gamepad subsystems only, never video ([doc/input.md](doc/input.md)).
- Android (0114): the same `game` package built as `libmain.so` for arm64, with raylib's input only. SDL code stays in files tagged `#+build !linux:android` ([doc/input.md](doc/input.md), Backends).
- Android-only code goes into `#+build linux:android` files (`main_android.odin`, `platform_android.odin`) or behind `when ODIN_PLATFORM_SUBTARGET == .Android`. Never a GLFW call outside a `when ODIN_PLATFORM_SUBTARGET != .Android` guard: `./build.sh check-android` fails on one ([doc/android.md](doc/android.md)).
- File watching: through `shared:fsw`. Never a polling scan of the data directory.
- Content: SJSON files under `data/`, parsed with `core:encoding/json` using `Specification.SJSON`. Never hardcode a recipe, block, machine or technology in Odin code.
- Build and verify through `build.sh` (`./build.sh check`, `./build.sh check-android`, `./build.sh test`, `./build.sh release`), which passes the `shared` collection; a bare `odin check src` does not compile ([doc/build.md](doc/build.md)). The agents' session is usually headless, so no window opens. The user playtests.

## Layout

The project structure of the global preferences: `doc/` (detail docs, index in `doc/README.md`), `doc/log/` (dated decision logs, write once), `doc/work/` (work items whose status line follows the pipeline, Work flow, The status line; the finished ones under `doc/work/done/`, the closed and folded ones under `doc/work/cancelled/`), `work/` and `tmp/` (untracked), `PLAN.md`, `DESIGN.md`, `TODO.md` (the user's inbox, the user writes there), `SUGGESTIONS.md` (only actual suggestions: decisions the user must make, tradeoffs, things to measure first; never `TODO.md`). Work an agent sees should be done is not a suggestion: it becomes a work item in `doc/work/` directly, named in the reply (user, 2026-10-03). Source under `src/`, content under `data/`, build output under `bin/`. The entry to the source is [doc/code_map.md](doc/code_map.md): the clusters, their entry files and the allowed dependencies between them.

## Code rules

- Odin conventions: `snake_case` procedures and variables, `Ada_Case` types, `SCREAMING_CASE` constants. Full words in names, no abbreviations.
- Small pure procedures, structs as data carriers, arrays of structs, no OOP.
- Never import `core:c/libc`: on Windows it links the static C runtime, which clashes with raylib's release library (0102). Declare the one C function needed against `system:c` and `system:ucrt.lib`, as `raylib_log.odin` does.
- Import `core:sys/posix` only in a file whose first line is `#+build !windows` (as `logging_posix.odin`), with a `#+build windows` counterpart; a `when` block does not keep an import out. `test_static_runtime_imports_stay_out_of_windows` enforces both ([doc/build.md](doc/build.md), The C runtime).
- One `game` package under `src/` split into files by concern. New packages only for leaf utilities with no back references, because Odin forbids import cycles.
- The simulation is deterministic: fixed 60 Hz tick, seeded RNG, no wall clock and no float accumulation in simulation state where fixed point works. Rendering interpolates, the simulation never reads the frame time.
- Shaders: every integer literal carries the `u` suffix (`hash >> 8u`), since Winlator's Gladio turns bare integers into floats on lines with float variables (0105). `shader_source_test.odin` enforces it.
- Textures go up as RGBA through `load_rgba_texture` (`render_atlas.odin`), never through `rl.LoadTextureFromImage` directly: gray formats render red on the phone (0106).
- Gamepad first: every UI works with focus navigation and with the trackpad pointer. Keyboard is only for string fields. Touch is a virtual gamepad (0115): a world action reaches touch through a gamepad binding, never through a touch code path of its own, except the hotbar slot taps (0119) and the jump tap (0134), which press their action directly because no gamepad control does only that ([doc/touch_overlay.md](doc/touch_overlay.md)).
- Keybindings are designed in modes and layers, selection wheels and smart widgets (user, 2026-10-03): a control may change meaning with the context (the inventory binding opens the aimed machine), but a world control never gains a second meaning while an item is held (no "Rotate with Sneak held cycles the height"), and a setting or a size (a foundation block's size) is chosen on the inventory view or a panel, never by cycling a world control. Every item that adds or changes a binding writes the control design out first (which mode or layer, which widget, what every existing control still does with the item held) and names that pass. The control design is the main agent's, written into the item before a subagent starts; a subagent gets it as a spec and never invents a binding (user, 2026-10-03).
- No perceivable repetition (`DESIGN.md`): sounds recur in clusters with long varying pauses and varied pitch, never on a fixed period; textures do not stripe or tile visibly, so they are isotropic or varied per block by a hash; animation cadences follow the world and never speed up with cheat speed. Every new sound, animation and texture is checked against this before it lands.
- Documentation is updated in the same commit as the behaviour it describes, in the doc that owns the topic (one place per fact). Decisions go to `doc/log/YYYY-MM-DD.md`.
- Review and commit language: plain engineering vocabulary (malformed input, validate the size before allocating), see the global instructions.

## Work flow

Work items live in `doc/work/NNNN-slug.md`, short, as the global rules say (Work items are overviews, the log is the drill-down): the goal, the controls, the change in a few lines, a `Status` line, a `Verify` list and, once designed, the `## Specification` section. An item whose work has landed and whose play build is installed moves to `doc/work/done/` (`git mv` in a commit of its own that also sets its status to `landed`, path references updated); an item closed or folded into another moves to `doc/work/cancelled/` with the status `cancelled`; open items stay at the top of `doc/work/` (user, 2026-10-03). An item is never reopened: follow-up work is a new item that refers to it (user, 2026-10-05). Each landed item gets one section in `doc/log/YYYY-MM-DD.md`, written by the main agent at the landing from the design's decisions and the review's findings, weighed: what the commit message, the code and the docs do not already say.

### The status line

The `Status` line names the item's position in the pipeline (user, 2026-10-03: "change their status from todo to better reflect its position in the pipeline"), one word, then a parenthesis with the date and, once landed, the commit: `todo` (written, nothing started), `designing` (a design agent writes the specification), `designed` (the specification approved, waiting for a slot), `implementing` (an implementer works in the item's worktree), `implemented` (the implementer reported, the snapshot is committed), `verifying` (a verifier reads the snapshot), `verified` (the review weighed and the fix round done, ready to land), `landed` (on `main` and installed, with the commit), `cancelled`. Nothing else goes into the parenthesis (user, 2026-10-05); the agent ids and the worktree of an item in flight go to `tmp/agent_ids.txt`, so a fix round can resume its implementer after a compaction. Who sets it: the main agent writes `todo`, `designed` at the approval, `implementing` in a commit on `main` before the worktree is made from it, `verifying` in the worktree before the snapshot commit, `verified` in the landing amend and `landed` in the move commit; the design agent sets `designing` when it starts; the implementer sets `implemented` when it reports. An item in flight on a branch shows a later status than its copy on `main`.

### The three stages

Every item runs design, implement and verify, each its own subagent (user, 2026-10-03: "mimicking normal software development process", a formal design step so the implementation step shrinks; a test local to this repository, promoted to the global rules when it works). The main agent is the architect and the integrator: it writes the control design into the item before anything starts (Code rules, keybindings), approves the specification, weighs the review, and alone commits, pushes, installs and moves the item. The item is a living document the stages keep current and lean (the status, the specification, a decision or a deviation that changes the plan); the reports are messages to the main agent, never pasted in.

1. **Design** (Opus, read-only on the code; writes only the item file in the main checkout). Input: the item, the docs and the code it names. It sets the status to `designing` first. Output: a `## Specification (design, <date>)` section in the item with everything an implementer needs so it never explores, written tight: the files and procedures to add or change, each with its signature and one line on what it does and where it is called; the data keys with their bounds and shipped values; a save, record or network layout change with its remap and the log line; the string keys; the tests by name with what each asserts and at which sizes or spacings; the docs by file and section; the hand-back check lines that apply and what satisfies them; every question the item left open with the answer chosen and why; and what it could not decide, as a question to the main agent. It names no binding the Controls section does not. An item that builds on one not yet on `main` is designed against that item's specification and says so. The main agent reads the specification, fixes what is wrong (a wrong seam, a float in the simulation, an invented control), appends its decisions to the section and approves it; a specification an implementer could not follow without exploring goes back.
2. **Implement** (Opus, in the stream's worktree). Follows the specification; a deviation is named in the report with its reason; runs `./build.sh check`, `./build.sh check-android`, `./build.sh test`, `python3 tools/check_docs.py` and `python3 tools/code_graph.py --check doc/code_map.md` (the two doc checks were left out of the field series' verify lists and the map's record drifted, 0208); walks the hand-back check and says what it changed because of it; sets the status to `implemented`; never commits.
3. **Verify** (a fresh Opus agent, read-only, in the same worktree). Reviews the diff against the specification and the item, runs the suite and the checks the implementer did not, and reports findings ranked by severity with file and line, each confirmed (reproduced or read in the code) or plausible, then what it ran, then a verdict. The main agent reads the findings and the parts of the diff they touch, not the whole diff; the implementer fixes what holds in a fix round (the same agent, resumed); the main agent runs the suite once itself before the commit (user, 2026-09-30).

### Model items: the sealed lab

A machine model (a machine redone from a reference sheet, 0212 and the ones after it) is not designed by the design stage and not modelled by the implementer. The pipeline's first furnace, a design agent's part table of kit primitives under the old 800 triangle cap, executed by an implementer that had read a sibling script and `DESIGN.md`'s modelling rules, came out as flat as the placeholders; the model the user accepted (2026-10-04, "i think this could very well be a final model in the released game") came from a modeller in a sealed lab. So: the design stage writes the engineering only (the footprint, the record, the tests, the old save rule) and no part table; the main agent writes the brief from `tools/model_lab/brief_template.md` into `tools/model_lab/<lab>/BRIEF.md` and builds the lab with `python3 tools/model_lab/model_lab.py build` ([doc/build.md](doc/build.md), The workbench), a directory holding the brief (the user's words on the look, the footprint, the renderer's limits, the budget of 3200 triangles and 8 materials, the commands), the reference images, copies of the kit, the palette and the record reader, a stub script, a standalone check and a Blender renderer with the workbench's cameras, and nothing else of the repository; the modeller (Opus) reads, writes and runs only inside the lab, never a sibling script, never `DESIGN.md`'s modelling rules, never the old model, and iterates on its own previews until they read as the sheet; the main agent renders the game's previews from the lab's OBJ (`model_lab.py preview` in the item's worktree) and sends them with the hero image; the user's notes go back to the same modeller; the accepted script and palette entries are integrated by an implementer in the worktree of the item that owns the integration (a new item when the modelling item has landed, never the old one reopened) (the OBJ regenerated and compared byte for byte with the lab's, the record's open cells set to what the model leaves empty, the tests and docs following), and the verifier reads that.

### Streams and worktrees

Items that touch different clusters of [doc/code_map.md](doc/code_map.md) run in parallel streams; items that touch the same files run in one stream, in series, each built on the one before. A stream is a pipeline (user, 2026-10-03): its items are at different stages at the same time, the design of the next item, the implementation of this one and the verification of the previous one, so every item has a worktree of its own, `.claude/worktrees/NNNN` on the branch `item/NNNN`, made when its implement stage starts from the stream's tip (the previous item's branch, or `main` for the first; `git worktree add .claude/worktrees/NNNN -b item/NNNN <tip>`), the tip rebased onto `main` first so the specifications committed there reach the worktree. `shared/` is tracked, so `build.sh` and the suite run in a worktree as in the main checkout, each with its own `build/`. The design stage reads the main checkout and, for an item that builds on one not yet landed, that item's worktree; implement and verify run in the item's worktree and every prompt names its path. When an implementer reports, the main agent sets the status to `verifying` and commits its tree on the item's branch as it stands (the commit message is written at landing), so the next item's worktree can be made from it and the verifier reads a tree nobody edits; a fix round edits the same worktree and the main agent amends, the last amend setting `verified`. Landing an item, in stream order: the main agent rebases `item/NNNN` onto `main` in its worktree (`git rebase main`; a conflict in `doc/log/` keeps both paragraphs, in `doc/work/` both items), fast-forwards `main` in the main checkout (`git merge --ff-only item/NNNN`), runs the suite once on `main`, pushes, installs the play build and moves the item; the next item of the stream is rebased onto the landed one before its own landing, with `git rebase --onto main <snapshot> item/NNNN` naming the previous item's snapshot commit it was made from, since the landing amend changed that commit and a plain `git rebase main` would replay the stale snapshot (0223 on 0265, 2026-10-05). Never a merge commit: the history stays linear and every commit is one item. A landed item's worktree is removed (`git worktree remove`, `git branch -d`).

### Parallelism

At most four subagents at once in this repository (user, 2026-10-03: first six for the test, then "lets dial it down from 6 to 4 so N=4"); this overrides the global one-subagent rule here for the test. The slots are assigned fluidly across the stages and the worktrees (user, 2026-10-03: "No need to strictly assign 3 subagents for the pipeline in each workstream ... feel free to assign them across the various steps across the various worktrees as you see fit"): a stream may have its design, implement and verify stages running at once on three items, or all slots may serve one stream, as the queue needs. The main agent fills the slots at its own discretion, implementers and fix rounds first, then verifiers, then designs ahead so an implementer always finds an approved specification waiting; an implementation starts on the previous item's tree without waiting for its verification, which is what the rebase at landing is for. Every agent keeps the core pinning while the user plays, never runs the game binary as a session, a preview or the benchmark (the workbench modes of 0207 are allowed: `./build.sh model-check`, `tools/make_models.sh` and `tools/model_preview.sh` open no window and touch no save), never installs the play build, and never commits; the suite under several agents takes longer, which is accepted.

## Hand-back check

Each line is a finding of the 2026-09-30 reviews that cost a fix round. The implementer checks its change against every line before it reports.

- Anything that frees or replaces memory a frame may still draw from (an arena, a string table, a screen's rows) runs between frames through a request the loop serves (`serve_data_browser`, `serve_touch_layouts`), never inside the UI pass, and a test runs the frame and then reads the draw list.
- A file is written to `<path>.tmp` and renamed over the path (`write_file_replacing`), never in place. A copy refuses a destination equal to its source. A path built from a listing or a setting stays under the directory it belongs to.
- A start-up load that the game itself can make fail (an overlay copy, a setting) falls back and reports instead of exiting.
- A number parsed from text is range checked (`strconv.parse_i64` wraps silently). A rate scaled per tick accumulates credits (`take_power_step`) instead of truncating.
- A changed save layout loads an old save (a remap and one log line), and a behaviour change that stops old saves is named in the log and covered by the dev kits.
- A new participant in a shared budget (power, fluid, a queue that credits future outputs) is checked for what it does to the existing ones: a proportional share that keeps it busy, an entry stuck ahead of it in a queue.
- A list that grows without bound is capped where it draws (the HUD), a long string is fitted or wrapped, both checked at the smallest audit size.
- A UI audit case a change makes obsolete is replaced, so the state it showed (a waiting queue, a full inventory) is still drawn somewhere.
- Tests never touch the machine's state directory or settings; they use temporary directories (the overlay directory is "" under `odin test`).
