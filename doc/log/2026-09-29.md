# 2026-09-29 Shaders that survive Gladio

Tags: #windows #shaders #gladio #decision

## Work item 0105 implemented

- Symptom: on the user's phone (Winlator, Mali GPU) the window opens and the game dies loading the chunk shader with "SHADER: [ID 12] Link error: Link failed because of missing fragment shader." and no compile log. The `gl:` line (0104) reads `vendor ARM, renderer Gladio, version 3.3, glsl 3.30`.
- Gladio is Winlator's OpenGL wrapper over the phone's GLES driver (`brunodev85/winlator-app`, `app/src/main/cpp/gladiorenderer/src/shader_converter.c`). It answers `GL_COMPILE_STATUS` with success while the compile is pending, rewrites the GLSL line by line into GLSL ES 3.20 and compiles it at link time; its compile error goes to the phone's logcat, never to the program, which is why only the link fails.
- The rewriting rule: `implicitConvertIntToFloat` runs on every line with an operator. When any word of the line is a registered variable of a float type (`float`, `vec2`, `vec3`, `vec4`, `const` globals included), every bare integer literal on the line gets `.0` appended and every `int` or `ivec` variable is wrapped in `float()` or `vecN()`. `uint` and `uvec3` are not in its type table, and a literal with a `u` suffix is not an integer to its `is_int`, so both pass untouched.
- The line that broke, in both fragment shaders: `return 1.0 + brightness_jitter * (float((hash >> 8) & 255u) / 127.5 - 1.0);`. `brightness_jitter` is a `const float`, so `hash >> 8` became `hash >> 8.0`. The other shifts shared their lines with no float variable and survived by luck; the vertex shaders have no integer literals.
- Decision: every integer literal in the shaders carries the `u` suffix, enforced by `shader_source_test.odin`, rather than working around Gladio per line. Shifting a `uint` by a `uint` literal is the same operation, so the hash is bit for bit the same and the CPU side (`texture_variation.odin`, `texture_periodicity_test.odin`) is untouched.

## Work item 0106 implemented: RGBA font atlas

Tags: #windows #textures #gladio #decision

- Symptom: on the phone (Winlator, Gladio) the title screen renders, but every glyph sits in an opaque red box: yellow letters, red where the glyph is clear.
- raylib keeps font atlases in `PIXELFORMAT_UNCOMPRESSED_GRAY_ALPHA` and on OpenGL 3.3 uploads them as `GL_RG8` with the swizzle `{RED, RED, RED, GREEN}` set through `glTexParameteriv(GL_TEXTURE_SWIZZLE_RGBA)` (`rlgl.h`, `rlLoadTexture`). Gladio forwards that call to the phone's GLES driver, which has no `GL_TEXTURE_SWIZZLE_RGBA` (only the four single channel parameters), so the swizzle is dropped and the texture samples as (gray, alpha, 0, 1): opaque red where alpha is 0, yellow where it is 1. Gladio swizzles the legacy `GL_LUMINANCE_ALPHA` upload path (`texture_utils.h` in `brunodev85/gladio`), but raylib only takes that path on GLES 2.
- Every PNG under `data/` is RGBA and the generated images are RGBA, so the font atlas is the only two-channel texture the game uploads, apart from raylib's built-in font (`GetFontDefault`), used only when a font file fails to load.
- Decision: `load_cached_font` builds the font itself as raylib's `LoadFontFromMemory` does (same glyph set, pixel size, padding of 4 and bilinear filter) and uploads the atlas as RGBA. Every texture upload goes through one helper, `load_rgba_texture`, which converts a copy of any image that is not RGBA, so a future gray PNG or generated image cannot bring the red boxes back. The fallback default font stays two-channel, accepted since it only shows when a font file is missing or unreadable.

## Work item 0107 implemented: joystick lines in the log

Tags: #windows #input #winlator

- Symptom: on the phone (Winlator) the on-screen Virtual Gamepad does nothing in the game while its mouse emulation works.
- Winlator's Wine fork presents the overlay as a HID gamepad from its own bus driver (`dlls/winebus.sys/bus_winlator.c` in `brunodev85/wine-10.10-custom`): manufacturer "Winlator", vendor and product of an Xbox 360 or Xbox One pad from `gamepad_models.json`, flagged as an XInput gamepad when the shortcut's DInput mapper type is XInput (ten buttons, axes X, Y, RX, RY, Z, RZ). The shortcut's Controls Profile and DInput Mapper Type settings pick the overlay and its device type at start.
- The SDL3 backend opened a gamepad only on `GAMEPAD_ADDED`, so a joystick SDL sees without a gamepad mapping for its GUID left no trace in the log, and neither did one SDL never sees.
- Decision: log the joystick count SDL sees at start, and one line per `JOYSTICK_ADDED` (id, name, vendor, product, GUID, gamepad or no gamepad mapping) and `JOYSTICK_REMOVED`. The gamepad lines stay. The added line is formatted by a pure procedure, `sdl3_joystick_line`, tested in `input_sdl3_test.odin`.

## Work item 0110 implemented: data watch off when scans are slow

Tags: #windows #performance #decision

- Symptom: on the phone (Winlator) developer mode drops the game to about 0.2 frames a second.
- Cause: developer mode turns the data watch on, which once a second stats every file under `data/` (469 today) on the main thread. The game folder on the phone is Android's shared storage reached through Wine and Box64, where each stat costs milliseconds, so a scan takes seconds and the frame waits for it.
- Decision: `poll_data_watch` measures the scan, and a scan slower than 50 ms (`DATA_WATCH_SLOW_SCAN`) switches the watch off for the rest of the run with one log line, `data: scanning <count> files took <ms> ms, the data watch is off for this run`. A worker thread was not chosen: no one edits data files on the phone, and the log says what happened. The first scan still stalls once on the phone, accepted. Turning developer mode off and on again does not bring the watch back.

## Work item 0109 implemented: shader load retry

Tags: #windows #shaders #gladio

- Symptom: on the phone (Winlator, Gladio) the shaders compile on most starts and fail on some, `SHADER: [ID 14] Failed to compile fragment shader code` for the water shader on one start and `[ID 11]` for the chunk shader on another, with the same files that compiled a minute before and after. The game gave up after one try and exited with "cannot load the chunk shader".
- Gladio answers `GL_COMPILE_STATUS` from its own table (`ShaderConverter_getShaderiv` in `shader_converter.c`): success while the compile is pending, failure only after a host compile failed at link time or when the shader id is missing from its table for the current context. Nothing about that is under the game's control.
- Decision: `load_shader_pair` tries each shader up to three times (`SHADER_LOAD_ATTEMPTS`) and logs `shader: <name> failed to load, attempt <n> of 3` after each failure; the final error line stays. Nothing is unloaded between attempts, since a failed `LoadShader` returns raylib's default shader. This is a mitigation for Gladio's transient failures, not a fix of them: the cause stays inside Gladio, and the attempt lines in the log show how often it stumbles.

## Work item 0108 implemented: no socket line on Windows

Tags: #windows #logging

- Symptom: on Windows every start with developer mode logged `error: command socket: no command socket on Windows`. The user: "no socket on windows is not an error".
- The Windows build has no command socket by design (0102), so the line said nothing new and carried the wrong prefix.
- Decision: a constant `COMMAND_SOCKET_SUPPORTED`, `true` in `command_socket_posix.odin` and `false` in `command_socket_windows.odin`, guards the open case of `update_command_server_open`, so on Windows no open is attempted and nothing is logged. The stub `open_command_server` keeps its return value, which its test checks.

## Work item 0111 implemented: data watch through odin-fsw

Tags: #hot-reload #decision #windows

- Problem: the data watch stat'ed every file under `data/` once a second (469 files) on the main thread. On the phone that stalled the frame for seconds (0110 switched the watch off after a slow scan), and on the couch it was 469 stats a second for nothing. The user: "Why are we stating every second? Shouldn't we be using some inotify or something?"
- Decision: the operating system reports the changes. odin-fsw (https://github.com/thetarnav/odin-fsw, commit `c2674eaa017e9bc6da18cfcc82c7a162b1a7a9df`, MIT), which the user's heimdall repository already uses for the same job, is vendored as `shared/fsw` beside raylib: inotify on Linux, ReadDirectoryChangesW on Windows, no foreign library. Three patches, recorded in `shared/fsw/README.md`: the Windows backend spells the fields of `FILE_NOTIFY_INFORMATION` the way Odin dev-2026-09 does, its completion port wait is 0 ms instead of the 50 ms that would have stalled every frame, and it re-issues `ReadDirectoryChangesW` with the subtree flag of the watcher instead of always false, which lost the subdirectories after the first event. The kqueue backend keeps its BSD build tag, so its `core:sys/posix` import stays out of the Windows link.
- `poll_data_watch` runs every frame and takes the events of one `fsw.get_events` call. fsw reports absolute paths under the absolute watched directory; each is made relative with `/` between names and mapped through `data_file_category`. Every event kind counts as a change, since editors save through a rename as often as through a write; directory events and paths outside the directory are ignored. The content settle now counts a second from the last content event instead of waiting for an unchanged scan.
- The slow scan switch of 0110 is gone with the scan. A watcher that cannot be opened logs `data: cannot watch <directory>: <error>` and leaves the watch off for the run.
