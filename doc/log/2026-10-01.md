## Direction: a voxel engine for any genre, the game as its first plugin

Tags: architecture, engine, plugins, wasm, ecs, composition

The user's direction after the cleanup series: a voxel 3D engine on which any style of game can be built (RPG, RTS, MMO, puzzle, MOBA, first or third person), with everything game logic and design related at the plugin level on a wasm plugin engine as in heimdall, and Mine oh Belowed as the first plugin. The audits' "tangled large scale" is exactly what the direction remedies. The brief is `doc/work/0146-engine-and-game-logic-cut.md`, the plan gained M12.

Decision on object composition (main agent's recommendation, open to the user):

- The engine is entity agnostic. It never iterates game entities; it needs per frame descriptions (draw list, sounds, UI draw list, camera) and a cell occupant index with flags. A host side entity store would put every component read of a 60 Hz tick behind a wasm host call, so entities live in guest memory and the engine reads views.
- Composition is the plugin's, through a game kit every plugin compiles in: kinds as compile time archetypes, component structs embedded in the kind structs, a kind table with pool and component offsets, systems over component views across kinds, generational handles carrying the kind, pool index order as the iteration order. The programming model of an entity component system without its dynamic storage, which is the simulation audit's middle path sized for this game.
- The view interface is what must be right for a general engine: a dynamic component store for games with runtime composition is added behind the same views when a game needs it, not before.
- Not a classic dynamic ECS from the start: handles would lose the kind, swap removal breaks the pinned determinism, the save needs a new format, and the coupling that matters is cut by seams, not by storage.

The refactor queue of 0143 stands and starts now, re read through the cut: pure moves and the bug fixes (0147 to 0151), then the hubs, the seams, the tables. Each seam is one boundary call of the future interface, built and tested inside one package first.
