## Android app: the first phone run (0114 follow up)

Tags: #android #bug #decision

- Symptom: the game APK (0114, version code 208) loaded on the phone, read the asset list and the first file, then logged `error: cannot copy data/bindings.sjson from the app: Permission_Denied`. The logcat showed an SELinux denial right before it: `avc: denied { read } for name="/" ... tclass=dir`.
- Cause: `os.make_directory_all` opens `/` with `O_DIRECTORY` to walk an absolute path component by component (`core/os/path_linux.odin`), and Android's policy refuses an untrusted app that read. A plain `mkdir` below the app's own folder is allowed.
- Decision: `make_directories_below` (`data_load.odin`) makes each directory of the asset's relative path under the app folder with `os.make_directory`, tolerating existing ones. No general replacement of `make_directory_all` elsewhere: the desktop builds keep it.
- Also in that logcat: `libsigchain: Setting SIGSEGV to SIG_DFL` from `install_crash_handlers`. bionic's `struct sigaction` on 64 bit puts `sa_flags` first and the handler second, `core:sys/posix` follows glibc (handler first), so bionic read the handler field as SIG_DFL and the flags from the handler pointer. Decision: the handlers are not installed on Android (`when ODIN_PLATFORM_SUBTARGET != .Android`), since the back trace is a stub there (0114) and Android's crash reporter writes the native trace to logcat.

## Work item 0115 implemented: the touch overlay as a virtual gamepad

Tags: #input #android #decision

- Goal (user, 2026-09-29): the Android app needs a way to move without a physical gamepad. The game draws its own overlay: a floating stick on the left half and a look drag on the right half wherever no button is, GameNative's button layout kept ("Keep the diamond positions, it's comfortable as it is"), sprint by pushing the stick past its rim at the top, direct touch in menus.
- Decision: the overlay is a virtual gamepad. It fills a `Raw_Gamepad` and a look delta, and the backend merges that gamepad into the physical one, so the bindings, the diagnostics and the simulation see a gamepad and nothing downstream learns a new device. Buttons latch until the finger lifts, like a game gamepad's. The layout is data (`data/touch_overlay.sjson`), scaled by the screen's height and anchored to corners. GameNative's Back and Start pills sit at the bottom centre, over the hotbar's middle slots, so they moved to the top centre (a `top_center` anchor), and a test keeps every element off the hotbar. There they overlap the discovery card while it shows, accepted since the card is transient and takes no input.
- The overlay merges into both backends, not only the raylib one the plan named: the couch and the Deck check it with `--touch-overlay`, and their default backend is SDL3.
- Sneak on B and Sprint on the stick click were bound for SDL3 only, because the raylib table never had them. On the Android build (raylib) the overlay's B would not sneak and the rim sprint would do nothing, so both bindings now act on both backends; a physical gamepad on the raylib backend gains them too, as it has on SDL3.
- While the overlay drives the world, the pointer's delta and the mouse buttons read nothing: the first touch holds raylib's left mouse button (Mine) and moves the mouse delta (look), which would double every stick drag. With a screen open the overlay draws and reads Start and Back alone, and nothing else of it. The first plan read Start and Back without drawing them, so a tap on the bottom centre of the inventory closed it; reading nothing at all over screens was tried next and left the inventory, the machine panels, the map and the other screens without a way to close by touch, since they have no close widget a pointer can hit and raylib keeps Android's back key (`rcore_android.c` consumes `AKEYCODE_BACK`). The pills now sit at the top centre and draw over the screen. A rim crossing under a screen does not latch the sprint. The overlay's gamepad alone is marked `on_screen`, so its presses leave touch the active device and a screen opened by X or Start keeps the pointer. On the desktop the cursor stays free in the world while the overlay is on, since the mouse is its touch point.
- The rim sprint latches: the first crossing of the rim within 45 degrees of straight up holds the stick click until the finger lifts (Bedrock's feel: push to the rim to sprint, keep walking, lift to stop). A press per crossing would, in the default toggle mode, switch sprinting off when the drag eased back and pushed out again, and a wobble across the rim would flicker it.
- No `dead_zone` key: the backend applies its stick dead zone (0.15) after the merge anyway, so the file's value could never go below it. The overlay hands the raw vector on. Its look delta is in the mouse delta's window coordinates, so a scaled desktop looks at the mouse's speed.
- The Accessibility tab's Touch controls row (`settings.touch_overlay`, `auto`, `on`, `off`) chooses it, `auto` meaning on for the Android build.

## Work item 0116 implemented: the Android runtime starts once per process

Tags: #android #bug #decision

- Symptom (user): the phone build (version code 211) crashes on every other launch. Logcat: two `wm_on_create_called` lines for one pid, the crash right after the second. Tombstone: `SIGTRAP` in `runtime::default_assertion_contextless_failure_proc` from `png::_register` from `__$startup_runtime` from `__wrap_main` from `android_main`.
- Cause: after Back or Home the activity ends but Android keeps the process. The next launch runs raylib's `android_main` on a new thread in the same process, and `__wrap_main` started the runtime again, which runs every `@(init)` procedure again. `core:image`'s `register` asserts that no loader of that kind is registered yet, the first run's PNG loader is, and a contextless assertion traps. The process dies, the next launch gets a fresh one, hence every other time.
- Decision: `__wrap_main` starts the runtime only once per process (a file private flag) and never calls `_cleanup_runtime`. Android ends the process without notice, and the `@(fini)` procedures among the dependencies only free the temporary allocator and `os.args` and restore a terminal the app does not have.
- A second `main` runs without the global initialisers, so each mutable global was checked. `global_string_table` is assigned by `main` before anything reads it, `thread_string_table` is thread local and the second run is a new thread, `captured_log_error` is set and restored around each data reload, and `close_log_file` (deferred in `main`) clears `global_log.file`. `global_console` was not safe: stderr still pointed at the first run's log, so the second redirect duplicated that log as the "original" stderr and the game's console lines went into the log twice. `redirect_stderr_to_log` now only moves stderr to the new log when an earlier run already redirected it, keeping the original stderr.
- Accepted: the previous run's game state stays allocated (`run_game` frees no arena at its end), one run per relaunch. `os.args` keeps the first run's slice (built once at `@(init)`), whose `[0]` points at the first launch's `arg0` bytes on raylib's stack; the game reads only `os.args[1:]`, which is empty on Android. raylib resets its own state for a relaunch after a destroyed activity (`rcore_android.c`, `ClosePlatform`, when `destroyRequested` is set).
- Correction to the Android toolchain notes of 0114 (`doc/build.md`): they said `core:os` finds the environment behind `args__` (`_get_original_env` starting at `argv[argc]`), so every variable reads as unset and nothing reads past raylib's two entry argv. That code exists only under `when ODIN_NO_CRT` (`core/os/env_linux.odin:18`). The Android build links bionic (`build.sh` passes no `-no-crt`), so `os.get_env` is bionic's `getenv` (`env_linux.odin:265`) and reads the process environment Android gives the app, which has none of the XDG variables. raylib's argv feeds `os.args` only. `__wrap_main` keeps `runtime.args__ = argv[:argc]`.
- Two more globals a second `main` would read stale: `last_touch_position` (`input_raylib.odin`, Android only) is now cleared by `start_input_backend`; the `UI_*` colours (`ui_widgets.odin`) are assigned by `apply_ui_theme` in `run_game` before any drawing.
- Decision: Quit ends the process on Android. Quit returns from `main` while the activity is alive, and raylib resets its `CORE` and `platform` state for a relaunch only when `destroyRequested` is set (`ClosePlatform`, `rcore_android.c`), so the next launch in the same process would start on stale raylib state. After `main` returns, `__wrap_main` calls `os.exit(0)` when `destroyRequested` is 0 (`Android_App` in `platform_android.odin` now declares the fields up to it, checked against `android_native_app_glue.h`). An activity the system destroys (Back, Home, then Android ending it) returns normally and keeps the process, the path above.
- If stderr cannot be moved to the second run's log, it stays on the previous run's log, the same path opened for append, so runtime errors still land in the log; the message says so.

## Work item 0118 implemented: tap to interact on the touch screen

Tags: #input #android #touch #decision

- Goal (user, 2026-09-29, Bedrock's touch scheme): interaction through the world. Hold a finger on a block to mine it, tap to place or to use a machine, and the mining progress drawn on the block. The crosshair scheme of 0115 stays, chosen by `settings.touch_interaction` (`tap` by default, `crosshair`).
- Decision: the overlay presses gamepad controls, not actions. A hold presses RT, a tap presses A or LT, and the bindings turn them into Mine, Interact and Place. An earlier draft of the work item had the overlay press the actions directly, on the ground that a tap is no trigger pull; it was rewritten before implementation, since the project rule is that a world action reaches touch through a gamepad binding, and a one frame trigger press reads through the bindings like any other.
- Decision: the aim arrives in the input frame. The frontend casts the render camera's ray through the touched point and puts the direction into `Input_Frame.aim_direction`, and `tick_player` casts the target along it instead of the look direction. The simulation never calls raylib, and the direction is input like the look delta.
- Decision: Interact or Place is chosen from the target the last tick found with the tap's aim, through one predicate (`entity_takes_interact`) composed of the two that `resolve_interact` and `resolve_use_item` act on, so the tap and the simulation agree.
- A tap waits for ticks, not frames: it aims until a tick has run with the aim, then presses until a tick has run with the press. On a 144 Hz display most frames run no tick, and Interact acts only while it is in `pressed` during the tick, so a press lasting one frame could fall between ticks. The overlay learns whether the previous frame ticked from `frame_tick_count`.
- `Player.target_direction` keeps the direction the target was found along, since the slab half placement read the look direction for the hit point.
- Third person: the simulation casts the target from the eye, and the camera sits behind and beside it, so the camera ray's direction alone would pick another block. The frontend casts the camera ray against the world (reach plus the camera's distance to the eye) and hands the simulation the direction from the eye to the hit point.
- Taps do not overlap. A lift while a tap is still aiming or pressing, or while another finger holds, starts no tap: the second tap would move the first one's aim before its press was read (a Place survives a tickless frame as an edge), and a tap during a hold would move the hold's aim and restart its dig. A tap that has waited longer than `TOUCH_HOLD_SECONDS` for a tick is dropped, so a developer pause does not fire it late. A hold that begins while a tap is still in flight drops the tap for the same reason: the hold owns the aim.
- The hold's and the tap's controls are data: the `look` element's `hold_control`, `tap_interact_control` and `tap_place_control` in `data/touch_overlay.sjson`, like the buttons' `control`.

## Work item 0119 implemented: hotbar taps on the touch screen

Tags: #input #android #touch #decision

- Goal (approved 2026-09-29 with the Bedrock recommendations): a tap on a hotbar slot selects it, a long press on the selected slot drops its stack into the world.
- Decision: one narrow exception to "touch is a virtual gamepad", for slot selection alone. No gamepad control selects a given slot (the gamepad steps the hotbar with the bumpers), so the overlay cannot reach `Hotbar_Slot_<n>` through a binding. The overlay frame carries `hotbar_tap`, and `apply_touch_overlay_hotbar` alone turns it into a `Hotbar_Slot_<n>` edge while the overlay drives the world. Every other touch still presses gamepad controls.
- Decision: the drop goes through a gamepad control. `Drop_Stack` is bound to d-pad down in the world (the layout proposal's "Down: drop", free there until now), so a physical gamepad drops with it too, and the long press on the selected slot holds `hotbar_drop_control` (`data/touch_overlay.sjson`, `DPAD_DOWN`) until the lift, like a held button. An earlier draft pressed `Drop_Stack` directly; review moved it onto the control, which keeps the exception to the one action with no control.
- Decision: the selection is an edge only, with no tick wait. The 0118 tap waits for ticks because Interact acts while held (`pressed`) and the aim must reach a tick first. Slot selection reads `just_pressed`, which the tick accumulator carries over frames that run no tick. It is not added to `pressed`: nothing reads it there, and a one frame level would hide a key press of the same action on the next frame.
- Decision: `Drop_Stack` is on X on the keyboard, not Q as the work item proposed. Q is Pipette in the world, and X is already the inventory's Drop (`Menu_Drop`), so one key drops in both places.
- A finger on the hotbar that moves past `TOUCH_TAP_SLOP` fires nothing (it stays claimed), so a look or stick drag that happens to begin on the selected slot does not drop the stack, and a flick does not select. The long press uses 0118's `TOUCH_HOLD_SECONDS` and fires once while the finger is down; the lift after it does nothing. On another slot it selects that slot only.
- The hotbar takes a finger only in the world. The HUD draws the hotbar under open screens too, but there the finger stays the pointer's, since the world strips the hotbar actions while a screen is open and a claimed finger would only swallow clicks on the screen.
- The drop happens in the simulation (`tick_player`, through the inventory's `drop_player_stack` with the selected slot, the hotbar being the first slots) before the tick's slot selection, so a drop that arrives with a select in the same tick drops the slot selected until then.

## Work item 0120 implemented: static stick and double tap toggles in the touch layout

Tags: #input #android #touch #decision

- Goal (approved 2026-09-29 with the Bedrock recommendations): a static stick for people who want it in a fixed place, and a double tap that latches a button (Bedrock's double tap sneak), both as layout data.
- Decision: a static stick keeps its `side`. A touch outside its base on that half does nothing rather than falling through to the look, so the half stays the stick's and a missed thumb does not turn the view.
- Decision: a static stick's drag counts from the base centre, not from where the finger landed, so a touch near the rim moves at once (Bedrock's static joystick).
- Decision: the double tap is measured from the lift of the first touch to the landing of the second, in frame time the overlay accumulates (frontend state, never the simulation). The touch that latches and the one that releases start no new double tap, so a quick tap after a release is a first tap again. The releasing touch still holds the button until it lifts, so a latched Sneak ends on the lift, not on the landing.
- Decision: the latches are a bit set over the element index, which caps a layout at 64 elements (validated). A data reload releases every latch and forgets the double tap (`release_touch_latches`, called where the new layout is installed), since a reload that inserts, removes or retypes elements would move a latch onto another button or strand it on an index that can never clear.
- Decision (review): latching works only while the sneak setting is Hold. In Toggle, Sneak flips on each press, so a double tap would toggle sneak on and off and latch B, and the third tap would make no edge since B is still down. Bedrock has no toggle setting, and in Toggle a single tap already toggles, so there a double tap is two taps and a switch to Toggle releases a latch. The frontend passes the setting in `Touch_Interaction_Frame.double_tap_latches`.
- Decision (review): only a tap arms the double tap, a press shorter than `TOUCH_HOLD_SECONDS`, so holding B for a while, lifting and pressing again at once is two presses, not a latch.
- A floating stick with `position = [0, 0]` and a static one without a position cannot be told apart from a missing key through the configuration loader, so a zero position counts as missing for both checks.

## Work item 0121 implemented: the touch layout editor

Tags: #input #android #touch #ui #decision

- Goal (approved 2026-09-29): the user moves, resizes, fades and rebinds the touch controls on the phone, keeps several layouts and picks one.
- Decision: Default stays in `Game_Content.touch_overlay`, loaded with the content tables as before, and the user layouts are frame state (`Frame_State.touch_layouts`), read once at start from the user directory's `touch_overlay.sjson`. `load_touch_overlay` does not merge the two, so a content reload replaces Default alone and never touches the user's layouts or selection; the overlay reads `active_touch_layout` every frame.
- Decision: the selection lives in the user file (`selected`), not in the settings, so the Touch layout row writes that file at once. A selected name the file does not hold refuses the file like any other problem.
- Decision: the Accessibility tab has two rows, Touch layout (a choice that steps the selection) and Edit touch layout (a button), since one widget cannot both step on Confirm and open a screen on Confirm.
- Decision: the d-pad moves the selected element and the left stick moves the focus. The UI reads both as navigation, so the editor tells them apart by the left stick's deflection in the frame (`touch_layout_dpad_step`), and a new widget flag `Adjusts_Vertically` (beside `Adjusts_Horizontally`) keeps the d-pad's up and down from moving the focus off the selected element.
- Decision: the editor's widgets share one focus scope over the whole screen, which is registered as no `Ui_Panel`: the elements sit in the screen's corners, outside the safe area the UI audit holds panels to.
- Decision: while the editor is on top the overlay neither reads nor draws, since its Start and Back would be both in the way and the thing being edited. The editor has its own Close.
- Decision: a move, a resize and a switch to static store whole reference pixels and hold the element on the screen and a stick on its own half. The half decides which zone a touch reaches (`classify_touch` takes a touch's half, then that half's stick), so a static stick placed on the look's half could never be touched; the loader checks only the elements' `side`, never their positions. Clamping also keeps a static stick's position off [0, 0], which the loader reads as missing.
- The user file is rewritten whole on every change. A broken file at start (logged, toasted, Default used) would have been replaced by the next save or selection change, losing the user's layouts in it; the review caught it (below).
- Decision (review): a broken user file at start locks the layouts (`Touch_Layouts.locked_path`) until the next start: the Touch layout row, the editor's Save, Save as and Delete and the frame loop's write refuse with a toast naming the file and asking to fix or remove it.
- Decision (review): a user layout needs a START button, in the loader (the layout is refused and Default used) and in the editor's Save and Save as. The bindings open the pause menu from START or Escape only and raylib keeps Android's back key, so a layout without one would strand the phone outside the menus, across relaunches since the selection is saved.
- Decision (review, a reproduced crash): the panel's Save, Save as, Delete and Reset only record a request (`Touch_Layout_Editor.request`), which the frame loop serves between frames (`apply_touch_layout_request` in `serve_touch_layouts`). Serving them inside the screen started the draft again and freed its arena while text commands pushed earlier in the frame still pointed into it; `draw_text` does not copy, and `execute_draw_list` read freed memory.
- Decision (review): the panel has a Double tap latches toggle for buttons, since a rebind keeps `double_tap_toggles` and a B rebound to RT would otherwise latch RT with no way to turn it off.
- Decision (review): the texture editor's seed stepper and the touch layout editor's steppers are one widget, `ui_stepper` in `ui_widgets.odin`, which returns the step's direction.

## Work item 0122 implemented: haptics on the phone

Tags: #input #android #haptics #decision

- Goal (approved 2026-09-29, the last phase of the Android spitball): the magnetometer's haptic request reaches the phone's vibrator, since the Android build has no SDL.
- Decision: the vibrator is called through JNI from Odin, with only the table slots the game calls declared as index constants (`src/jni_indices.odin`), counted from the NDK 27.3.13750724 `jni.h` and checked by a test against the numbers in the work item. No Java code: the app stays `hasCode="false"`.
- Decision: the `Call...MethodA` variants instead of the variadic `CallObjectMethod`, `CallBooleanMethod`, `CallVoidMethod` and `CallStaticObjectMethod` the work item named, so no call from Odin goes through C varargs.
- Decision: attach the game thread before every use instead of once. raylib's `GetCurrentMonitor` (`rcore_android.c`, raylib 6.0) attaches and then detaches the calling thread, and the game calls it at start and in the display diagnostics, so a `JNIEnv` kept from start could belong to a detached thread. Attaching an attached thread only returns its environment.
- Decision: detach at the end of `run_game` instead of never. The activity can end while the process lives (a system destroyed activity returns from `main`, `main_android.odin`), and a thread attached through JNI must detach before it exits.
- Decision: a failed call (a thrown exception, cleared) logs one line and turns the vibrator off for the run, so a call that keeps failing does not log sixty times a second.
- `HAPTIC_RUMBLE_MILLISECONDS` moved from `input_sdl3.odin` to `input_actions.odin`, since the SDL3 file is left out of the Android build.

## Work item 0126 implemented: high precision in raylib's default shader on Android

Tags: #android #rendering #bug #decision

- Symptom (user, version code 222): on the phone every camera or player movement makes voxels shift slightly each frame; a held block's corners move independently and the block ends skewed when the camera stops.
- Cause: raylib 6.0's `rlLoadShaderDefault` (`src/rlgl.h`, lines 5020 to 5022 for the vertex shader, 5073 to 5075 for the fragment shader) declares `precision mediump float;` in the OpenGL ES3 default shaders, kept for WebGL browsers. Mali's mediump is 16 bit, so world space positions near 200 blocks land on a 0.125 grid that shifts as the camera moves. Everything raylib's batch or default shader draws is affected (the arm and held block, models, particles, billboards, items, entities, weather, icons); the chunks are not, since `shader_source_for_gles` gives the game's own shaders highp.
- Decision: `tools/build_raylib.sh --android` rewrites those two lines to `precision highp float;` in the fresh clone before cmake, found by their `OpenGL ES3 (WebGL 2)` comment, and fails unless it rewrites exactly two, so a raylib upgrade that moves the text is noticed. OpenGL ES 3.0 guarantees highp in both stages. The ES2 lines are left alone (not compiled for ES 3.0). The desktop and Windows archives are untouched: desktop GL has no precision qualifiers. The Android archive is rebuilt with the patch.

## Work item 0124 implemented: drag and drop for item slots with a pointer

It applies to the screens that do not pause the simulation (inventory, recipes, technologies, machine, journal, power, statistics, map) and not while the on-screen keyboard is open; the pause menu, the settings, the editors (which take presses all over the screen) and the title screens keep their own Back. It sets Back for the frame, so the screens close as they do on B.
- Decision (review): a drag whose pick up lifted nothing (a filter slot, a hand slot's hold, a slot a machine emptied before the slop) ends at once, and a release drops only while a stack is held, so an empty hand never picks up the stack under the release. Left Control with a click quick moves the slot under the pointer and starts no drag. Confirm sounds on the pick up and on the drop, not on a tap; the outside tap plays Back's sound.

Report: `doc/audit/presentation.md`. Spot checked five claims against the code, all hold.

- Only chunks and water are culled against the view: `draw_entities` draws every live entry of ten pools, and the frustum is built three times a frame (chunks, water, diagnostics).
- 23 of the renderer's 35 direct pool loops read only parts every kind shares (cell, rotation, progress, held item, state); 4 need a per kind table and 8 need kind specific fields (arm, bit, rocket, pipes, poles, belts, splitters). A per frame machine view removes about 100 of the 289 references into the simulation and is the seam a plugin would hand the engine.
- "What happened since last frame" is detected in several memories: the footstep cadence and the place count are diffed twice (`advance_player_animation_memory` and `advance_sound_memory`), the quest messages are scanned twice, the dig memory twice. One pure detector gives the per tick event list a plugin would emit.
- `Model_Frame` carries `^World` for one light lookup; moving the lookup to the engine side frees the models from the world.
- The shaders and their Odin copies drift unchecked: the variation hash is written three times (`texture_variation_hash`, `chunk.fs`, `water.fs`) and the light curve three times (`chunk.fs`, `water.fs`, `light_curve` in `model_motion.odin`), with no test comparing them.
- Found on the way: `write_texture_edits_file` writes in place with `os.write_entire_file` instead of `write_file_replacing`, against the hand-back rule (queued in `SUGGESTIONS.md`); belt items are drawn at their tick position while the belt surface under them interpolates, so at more than 60 frames per second the items should step (read in the code, not seen; the user can check on the couch).
- Engine or game: the atlas, mesh upload, shaders, frustum, display, audio device, particle and model machinery are engine; the per kind draws, the sound choices, ambient life, weather and the day colours are game. Today's 67 raylib draw calls of 12 shape kinds could become appends to a draw list, the pattern the UI toolkit already uses with `Draw_Command`, without a rewrite.
- `weather.odin` and `player_animation.odin` are presentation; `render_fly_camera.odin` splits between the player tick's look physics and the view.
- Refactors queued for after the audits (ranked in the report): the texture edits through `write_file_replacing`; pure moves and the cluster table; one detector for the per tick events; the per frame machine view; the light lookup out of `Model_Frame`; one frustum per frame with entity culling; the shader copies under test.

## Audit 0143: the content cluster

Tags: architecture, audit, content, loading, configuration, platform

Report: `doc/audit/content.md`. Spot checked five claims against the code, all hold.

- The graph's content cluster is five groups: registries and game rules (4853 lines), loading (1429), tools (2575: the command socket, the data browser, the export), configuration (974) and platform (1049). The audit's verdict: `quest_runtime.odin`, `recipe_unlocks.odin` and `venture.odin` are simulation, `hot_reload.odin` is loop, and `platform` and `tools` are clusters of their own.
- The content tables accept unknown keys: the loaders are `json.unmarshal`, which skips a key with no field, while the configuration refuses one. A typo in `items.sjson` is silent. Name keys are checked only by tests, never at load. One loader body is written fifteen times with two failure conventions, and twelve id lookups are hand written beside the generic `find_definition_index`.
- Two id lookups run every tick: the sapling for tree felling and the launch pad for the venture. Resolved once at load they go away.
- Hand-back rule breaches found: `write_settings_file` writes the settings in place, and `main` exits on a configuration problem, so a settings file cut short by a crash stops the game from starting; the touch layouts file is written in place too. With the texture edits file from the presentation audit, three files the game writes bypass `write_file_replacing`. Queued in `SUGGESTIONS.md` as one fix.
- `validate_settings` checks no volume although `VOLUME_RANGE` exists; the audio clamps at use. The generator names six blocks by id in code (`generation.odin`), against the rule that content stays in data.
- A loader's problem reaches the reload through the log: `log_printf` captures the last error line and `end_log_capture` reads it back, so the reload's report depends on the log format.
- For 0145, the true leaves once name noise is removed: `local_zone.odin` and its two platform files, `jni_indices.odin`, `run_length.odin`, `export_access_desktop.odin`, `platform_android.odin`, `logging_windows.odin`, `platform_paths.odin`. One edge away: `logging.odin` (the build stamp), `logging_posix.odin`, `sjson_text.odin` (`sorted_object_keys` in the configuration), `data_strings.odin`, `export_access_android.odin` (the JNI helpers in a ui file), `command_socket.odin`, `command_socket_windows.odin`. Cutting those edges leaves 13 files with no edge into the big component.
- Engine or game: the loader framework, strings, configuration, settings, logging, the command transport, the data browser and export, the platform pairs are engine; the registries' semantics, the quest runtime, contracts, the venture, discovery and the dev kits are game.
- Refactors queued for after the audits (ranked in the report): the settings file through `write_file_replacing` with one home expansion; cut the platform leaves' edges (the 0145 prerequisite); the two per tick lookups resolved at load; one loader body with unknown key refusal; the hand written lookups on `find_definition_index`; the generator's block ids in data.
