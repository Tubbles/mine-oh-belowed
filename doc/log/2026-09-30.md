## Android app: the first phone run (0114 follow up)

Tags: #android #bug #decision

- Symptom: the game APK (0114, version code 208) loaded on the phone, read the asset list and the first file, then logged `error: cannot copy data/bindings.sjson from the app: Permission_Denied`. The logcat showed an SELinux denial right before it: `avc: denied { read } for name="/" ... tclass=dir`.
- Cause: `os.make_directory_all` opens `/` with `O_DIRECTORY` to walk an absolute path component by component (`core/os/path_linux.odin`), and Android's policy refuses an untrusted app that read. A plain `mkdir` below the app's own folder is allowed.
- Decision: `make_directories_below` (`data_load.odin`) makes each directory of the asset's relative path under the app folder with `os.make_directory`, tolerating existing ones. No general replacement of `make_directory_all` elsewhere: the desktop builds keep it.
- Also in that logcat: `libsigchain: Setting SIGSEGV to SIG_DFL` from `install_crash_handlers`. bionic's `struct sigaction` on 64 bit puts `sa_flags` first and the handler second, `core:sys/posix` follows glibc (handler first), so bionic read the handler field as SIG_DFL and the flags from the handler pointer. Decision: the handlers are not installed on Android (`when ODIN_PLATFORM_SUBTARGET != .Android`), since the back trace is a stub there (0114) and Android's crash reporter writes the native trace to logcat.

## Work item 0115 implemented: the touch overlay as a virtual gamepad

Tags: #input #android #decision

- Goal (user, 2026-09-29): the Android app needs a way to move without a physical gamepad. The game draws its own overlay: a floating stick on the left half and a look drag on the right half wherever no button is, GameNative's button layout kept ("Keep the diamond positions, it's comfortable as it is"), sprint by pushing the stick past its rim at the top, direct touch in menus.
- Decision: the overlay is a virtual gamepad. It fills a `Raw_Gamepad` and a look delta, and the backend merges that gamepad into the physical one, so the bindings, the diagnostics and the simulation see a gamepad and nothing downstream learns a new device. Buttons latch until the finger lifts, like a game gamepad's. The layout is data (`data/touch_overlay.sjson`), scaled by the screen's height and anchored to corners. GameNative's Back and Start pills sit at the bottom centre, over the hotbar's middle slots, so they moved to the top centre (a `top_center` anchor), and a test keeps every element off the hotbar. There they overlap the discovery card while it shows, accepted since the card is transient and takes no input.
- The overlay merges into both backends, not only the raylib one the plan named: the couch and the Deck check it with `--touch-overlay`, and their default backend is SDL3.
- Sneak on B and Sprint on the stick click were bound for SDL3 only, because the raylib table never had them. On the Android build (raylib) the overlay's B would not sneak and the rim sprint would do nothing, so both bindings now act on both backends; a physical gamepad on the raylib backend gains them too, as it has on SDL3.
- While the overlay drives the world, the pointer's delta and the mouse buttons read nothing: the first touch holds raylib's left mouse button (Mine) and moves the mouse delta (look), which would double every stick drag. With a screen open the overlay draws and reads Start and Back alone, and nothing else of it. The first plan read Start and Back without drawing them, so a tap on the bottom centre of the inventory closed it; reading nothing at all over screens was tried next and left the inventory, the machine panels, the map and the other screens without a way to close by touch, since they have no close widget a pointer can hit and raylib keeps Android's back key (`rcore_android.c` consumes `AKEYCODE_BACK`). The pills now sit at the top centre and draw over the screen. A rim crossing under a screen does not latch the sprint. The overlay's gamepad alone is marked `on_screen`, so its presses leave touch the active device and a screen opened by X or Start keeps the pointer. On the desktop the cursor stays free in the world while the overlay is on, since the mouse is its touch point.
- The rim sprint latches: the first crossing of the rim within 45 degrees of straight up holds the stick click until the finger lifts (Bedrock's feel: push to the rim to sprint, keep walking, lift to stop). A press per crossing would, in the default toggle mode, switch sprinting off when the drag eased back and pushed out again, and a wobble across the rim would flicker it.
- No `dead_zone` key: the backend applies its stick dead zone (0.15) after the merge anyway, so the file's value could never go below it. The overlay hands the raw vector on. Its look delta is in the mouse delta's window coordinates, so a scaled desktop looks at the mouse's speed.
- The Accessibility tab's Touch controls row (`settings.touch_overlay`, `auto`, `on`, `off`) chooses it, `auto` meaning on for the Android build.

## Work item 0116 implemented: the Android runtime starts once per process

Tags: #android #bug #decision

- Symptom (user): the phone build (version code 211) crashes on every other launch. Logcat: two `wm_on_create_called` lines for one pid, the crash right after the second. Tombstone: `SIGTRAP` in `runtime::default_assertion_contextless_failure_proc` from `png::_register` from `__$startup_runtime` from `__wrap_main` from `android_main`.
- Cause: after Back or Home the activity ends but Android keeps the process. The next launch runs raylib's `android_main` on a new thread in the same process, and `__wrap_main` started the runtime again, which runs every `@(init)` procedure again. `core:image`'s `register` asserts that no loader of that kind is registered yet, the first run's PNG loader is, and a contextless assertion traps. The process dies, the next launch gets a fresh one, hence every other time.
- Decision: `__wrap_main` starts the runtime only once per process (a file private flag) and never calls `_cleanup_runtime`. Android ends the process without notice, and the `@(fini)` procedures among the dependencies only free the temporary allocator and `os.args` and restore a terminal the app does not have.
- A second `main` runs without the global initialisers, so each mutable global was checked. `global_string_table` is assigned by `main` before anything reads it, `thread_string_table` is thread local and the second run is a new thread, `captured_log_error` is set and restored around each data reload, and `close_log_file` (deferred in `main`) clears `global_log.file`. `global_console` was not safe: stderr still pointed at the first run's log, so the second redirect duplicated that log as the "original" stderr and the game's console lines went into the log twice. `redirect_stderr_to_log` now only moves stderr to the new log when an earlier run already redirected it, keeping the original stderr.
- Accepted: the previous run's game state stays allocated (`run_game` frees no arena at its end), one run per relaunch. `os.args` keeps the first run's slice (built once at `@(init)`), whose `[0]` points at the first launch's `arg0` bytes on raylib's stack; the game reads only `os.args[1:]`, which is empty on Android. raylib resets its own state for a relaunch after a destroyed activity (`rcore_android.c`, `ClosePlatform`, when `destroyRequested` is set).
- Correction to the Android toolchain notes of 0114 (`doc/build.md`): they said `core:os` finds the environment behind `args__` (`_get_original_env` starting at `argv[argc]`), so every variable reads as unset and nothing reads past raylib's two entry argv. That code exists only under `when ODIN_NO_CRT` (`core/os/env_linux.odin:18`). The Android build links bionic (`build.sh` passes no `-no-crt`), so `os.get_env` is bionic's `getenv` (`env_linux.odin:265`) and reads the process environment Android gives the app, which has none of the XDG variables. raylib's argv feeds `os.args` only. `__wrap_main` keeps `runtime.args__ = argv[:argc]`.
- Two more globals a second `main` would read stale: `last_touch_position` (`input_raylib.odin`, Android only) is now cleared by `start_input_backend`; the `UI_*` colours (`ui_widgets.odin`) are assigned by `apply_ui_theme` in `run_game` before any drawing.
- Decision: Quit ends the process on Android. Quit returns from `main` while the activity is alive, and raylib resets its `CORE` and `platform` state for a relaunch only when `destroyRequested` is set (`ClosePlatform`, `rcore_android.c`), so the next launch in the same process would start on stale raylib state. After `main` returns, `__wrap_main` calls `os.exit(0)` when `destroyRequested` is 0 (`Android_App` in `platform_android.odin` now declares the fields up to it, checked against `android_native_app_glue.h`). An activity the system destroys (Back, Home, then Android ending it) returns normally and keeps the process, the path above.
- If stderr cannot be moved to the second run's log, it stays on the previous run's log, the same path opened for append, so runtime errors still land in the log; the message says so.
