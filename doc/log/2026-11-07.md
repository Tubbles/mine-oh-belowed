## Test tiers (0316)

Tags: tests, build, pipeline, benchmark, 0316, 0318

The user asked whether to split the suite after one item in about twelve hours. The measurement, taken while a hung capture game loaded the machine, found the time in a few places: 237 tests of 1 s or more held 95 percent of it, mostly field sessions ticked for hundreds of ticks unoptimised, and one crater test of 346 s ran alone at the end because the runner sorts by name. Each tier also paid a 75 s compile on Odin dev-2026-09. Odin's runner selects only by name and has no exclusion, so a slow test is marked by a comment on its attribute line and a lister hands the runner the tier's names. A mark added late is caught by the run itself: an unmarked test over 10 s fails it. The stages' runs moved with it: the implementer iterates on quick and unit and runs all once, the verifier runs the tests its diff touches and its probes, and the main agent's run on `main` and CI's are the gate, two full runs per item where there were four. The review found that a file holding a report test failed quick although every test passed, and that two benchmark guards could each take the same stale lock and one remove the other's live lock. Both were fixed. Nightly now runs one test at a time so the timings do not skew each other. On dev-2026-11a, which 0315 brought in the same day, the test binary compiles in about 23 s, so quick costs about half a minute and unit about 36 s. Speeding up the slowest tests is 0318.

## Records held instead of refused (0325)

Tags: network, lockstep, ci, 0325, 0178

CI's nix job failed `test_a_joined_machine_adds_and_removes_a_local_player` three times, always on record 245. The host bounded a client's records by its own tick, but a server's tick is no member: nobody waits for it, and a client plays on as soon as its records come back relayed. The second local player's entry at tick 62 moves the simulated set to its spawn, both machines wait for those chunks, and on the runner the server's wait outlasted the client's by 2.5 s, so it sat at 62 while the client ran on to 62 plus the window 2 plus the margin 180 plus 1. A record past the bound now waits on the connection with everything after it until the host catches up, so the client hitches instead of being dropped; the order check stays a refusal. Dropping the bound instead would let every machine's stored records grow while a server lags. The review measured a 13 s stall: the machine held at the bound, stayed connected and played on without a mismatch, with 2.4 KB waiting against the 32 MB cap. Why the server's chunk wait ran so much longer than the client's on the runner was not found.
