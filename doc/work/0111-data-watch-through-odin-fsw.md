# 0111 Data watch through odin-fsw

Status: implemented
Milestone: M11

## Goal

The data watch (work item 0054) stats every file under `data/` once a second on the main thread, 469 files today. On the phone that scan stalls the frame for seconds (0110 switches the watch off after a slow scan), and on the couch it is 469 stats a second for nothing. The user (2026-09-29): "Why are we stating every second? Shouldn't we be using some inotify or something?" and, on the proposal below, "Yes i want that". The user's heimdall repository uses `thetarnav/odin-fsw` (`import fsw "module:odin-fsw"`, `watch_file`, `get_events`, `destroy`) for the same job.

## Change

- Vendor odin-fsw as the collection package `shared/fsw`: the `.odin` files, `LICENSE.txt` and a `README.md` record in the style of `shared/raylib/README.md` (upstream `https://github.com/thetarnav/odin-fsw`, commit `c2674eaa017e9bc6da18cfcc82c7a162b1a7a9df` of 2026-08-01, MIT, the patch below). A clone sits in `tmp/odin-fsw` at that commit; leave out `example/`, `Makefile` and `test.odin`. One patch, recorded in the README: `backend_windows.odin` reads the fields of `windows.FILE_NOTIFY_INFORMATION` as `action`, `next_entry_offset`, `file_name_length` and `file_name`, while the September 2026 Odin nightly spells them `Action`, `NextEntryOffset`, `FileNameLength` and `FileName`. `backend_kqueue.odin` keeps its BSD build tag (its posix import must never reach the Windows link, see CLAUDE.md). `odin check` of the package must pass for Linux and for `-target:windows_amd64` with `-vet -strict-style` (build.sh passes the `shared` collection; the flake needs no change unless the check there fails, in which case say so).
- `src/data_watch.odin` watches through `fsw.watch_dir_recursive(data_directory)` instead of scanning: `Data_Watch` holds the `fsw.Watcher_Recursive` and whether it is open; opening happens when watching starts (mode not `Off`) and `fsw.destroy` when it stops or at shutdown. `poll_data_watch` runs every frame: `fsw.get_events(&watcher, context.temp_allocator)`, each event's path made relative to the data directory (the events carry absolute or watcher relative paths, check `fsw.odin`), mapped through `data_file_category`, every event kind counts as a change (editors save through rename as often as through write). Keep the `Data_File_Categories` result, `content_changed`, the one second content settle (`content_settling`: content files changed, then a second without content events asks for the reload with mode `all`), `Watch_Data_Mode` and `effective_watch_data_mode`. Remove the stamps, `scan_data_files`, `DATA_WATCH_INTERVAL`, `data_watch_poll_due` and the slow scan switch of 0110 (`DATA_WATCH_SLOW_SCAN`, `disabled`, the `data: scanning` line and the `disabled` carry over in `hot_reload.odin`). A watcher that cannot be opened logs one line `data: cannot watch <directory>: <error>` and leaves the watch off for the run.
- `update_data_watch` (`src/hot_reload.odin`) calls the poll every frame; the settle check keeps using `now`.
- Tests (`src/data_watch_test.odin`): the pure mapping from event paths to categories with synthetic paths (a strings file, a shader, a texture, a content table, a directory, an ignored file); the existing file change test (`test_watcher_notices_changed_files`) writes into a temporary directory and waits for the events by polling `poll_data_watch` every 10 ms for up to two seconds, so it is robust to inotify latency and works in the nix sandbox; a test that the settle asks for the reload one second after the last content event, with `now` passed in. Remove the tests of the slow scan switch.
- Documentation in the same commit: the header comment of `src/data_watch.odin`; `doc/architecture.md` (the hot reload sentence, the 0110 clause replaced); `doc/build.md` where the `shared` collection is described (fsw beside raylib, no foreign library); `CLAUDE.md` Stack (a line: file watching through `shared:fsw`, vendored odin-fsw, never a polling scan); a note at the end of `doc/work/0110-data-watch-off-when-scans-are-slow.md` that 0111 replaced the scan; a dated entry in `doc/log/2026-09-29.md` (tags `#hot-reload #decision #windows`).

## Implemented

2026-09-29: `shared/fsw` holds the upstream files at `c2674eaa` with the one field name patch in `backend_windows.odin` (`README.md` records it). `Data_Watch` holds the `fsw.Watcher_Recursive`, `open`, `unavailable`, `content_changed`, `content_settling` and `last_content_event`; `update_data_watch` opens it when the mode is not `Off` (`open_data_watch`, which logs `data: cannot watch <directory>: <error>` once), polls every frame and asks for the reload with mode `all` once `data_watch_content_settled` finds a second since the last content event; `destroy_data_watch` closes it when the mode turns `Off` and at exit. fsw reports absolute paths joined onto the absolute watched directory (`filepath.abs` in `watch_dir_recursive`, `filepath.join` in both backends), so `data_relative_path` strips that prefix and turns the separator into `/`; directory events, paths outside the directory and the path-less `Overflow` are ignored. Verified here: both `odin check shared/fsw` runs, `./build.sh check`, `./build.sh check-windows`, `./build.sh test` (twice, 1056 tests, the file change test stable) and `./build.sh release` pass. Not verified: the Windows backend at runtime. Reading it, upstream waits up to 50 ms in `GetQueuedCompletionStatus` on every `get_events` call (while its header says 0 ms) and re-issues `ReadDirectoryChangesW` with `bWatchSubtree` false after the first batch; both are patched in the vendored copy (README) and worth an upstream report. An `Overflow` event does not mark every category. The couch and phone checks are the user's.
