# 0085 A Wayland native window at the panel's full size

Status: implemented
Milestone: M11

## Goal

On a scaled Wayland desktop the game gets the scaled screen through XWayland (0084). A raylib built with GLFW's Wayland backend opens a native window, and with the high DPI flag its framebuffer is the panel's full size under a fractional scale, so a 2880 by 1920 laptop panel renders 2880 by 1920 without any desktop setting. Decided by the user on 2026-09-28: build raylib from source, Wayland is not optional.

## Deliverables

- A raylib 6.0 static library built from the upstream tag with both GLFW backends (`-DGLFW_BUILD_WAYLAND=ON -DGLFW_BUILD_X11=ON`; GLFW 3.4 picks Wayland at run time when the session offers it and falls back to X11), by `tools/build_raylib.sh` (fetches the tag, needs cmake, the Wayland, xkbcommon and libdecor headers; on Bazzite inside a distrobox), placed under `lib/linux/` and linked by `build.sh` in place of the vendored library through the linker shim directory. The nix flake already links nixpkgs raylib with an external nixpkgs GLFW that has both backends, so CI covers the Wayland build path once the game asks for it.
- `FLAG_WINDOW_HIGHDPI` at window creation, so the framebuffer follows the panel under a fractional scale (GLFW 3.4's fractional scale support on Wayland). The UI lays out in render pixels: `pixels_per_unit` and the pointer come from `GetRenderWidth` and `GetRenderHeight`, raylib's 2D scale matrix is accounted for (or bypassed) so text rasterises at the panel's pixel size and stays crisp, the screenshot command reads the render size, the display settings report the render size and the Resolution row lists the panel's modes as raylib reports them under Wayland.
- Windowed mode under Wayland needs libdecor for decorations; Borderless and Fullscreen do not. The launcher's SDL override is unaffected.
- Tests: the render pixel layout at scale 1 and 1.7 in the UI audit, the pointer mapping, the settings round trip.
- Docs: `doc/build.md` (the build step and the distrobox recipe), `doc/architecture.md`, `doc/ui.md`, `doc/log/<date>.md`, this item.

## Verify

- Builds and tests pass; CI's nix build links the external GLFW.
- User: the laptop shows 2880 by 1920 in Borderless and the text is crisp.

## Notes

Implementation pointers, decisions taken so the item is unambiguous (main agent, 2026-09-28):

- Why a repository collection: the Odin binding names its library by a path inside the toolchain (`vendor/raylib/linux/libraylib.a`, and `../linux/libraylib.a` in the rlgl sub package), so no linker flag can swap the library; nixpkgs patches the binding for the same reason. The toolchain stays untouched: `shared/raylib/` holds a copy of `~/opt/odin/vendor/raylib/raylib.odin`, `rlgl/rlgl.odin` and `LICENSE` (nothing else is imported; `raymath`, `easings`, `raygui` stay out), unchanged, plus `linux/libraylib.a` from the build script and a `README.md` (the Odin release the binding came from, the raylib tag, the cmake flags, the build date, how to redo it after an Odin upgrade). `build.sh` passes `-collection:shared=shared` to build, check, test and bench, and the 41 imports become `import rl "shared:raylib"` and `"shared:raylib/rlgl"` (a mechanical sed over `src/*.odin`). Every verify command goes through `build.sh` from now on, since a bare `odin check src` no longer knows the collection; `CLAUDE.md` says so.
- The library: `tools/build_raylib.sh` clones raylib tag `6.0` from https://github.com/raysan5/raylib (shallow, `--branch 6.0`) into `tmp/raylib-src/`, configures with cmake in `tmp/raylib-build/` (`-DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF -DBUILD_EXAMPLES=OFF -DPLATFORM=Desktop -DGLFW_BUILD_WAYLAND=ON -DGLFW_BUILD_X11=ON -DCMAKE_POSITION_INDEPENDENT_CODE=ON`, plus what the fetched `CMakeLists.txt` needs for both backends; read it and `src/external/glfw/CMakeLists.txt`), builds, copies `libraylib.a` into `shared/raylib/linux/` and rewrites the README's build record. The host lacks cmake and every development header (checked: no `cmake`, no `/usr/include/wayland-client.h`, no X11 headers; Bazzite is Fedora 44 based, `distrobox`, `toolbox` and `podman` exist, `nix` does not), so on Bazzite the script builds inside a distrobox named `mine-oh-belowed-raylib` from `registry.fedoraproject.org/fedora-toolbox:44`, created on first use (`distrobox create`, then `dnf install cmake gcc gcc-c++ make git wayland-devel wayland-protocols-devel libxkbcommon-devel libdecor-devel mesa-libGL-devel libX11-devel libXrandr-devel libXinerama-devel libXcursor-devel libXi-devel libXext-devel`); `--host` runs the same steps on the host for a machine that has the tools (the laptop may). The archive is committed (about 3 MB, rebuilt rarely), so a fresh checkout builds without cmake or a container. Prove the archive: `nm shared/raylib/linux/libraylib.a | grep -c _glfwConnectWayland` and `_glfwConnectX11` both nonzero; `./build.sh release` links with the binding's existing list (`system:dl`, `system:pthread`, `system:X11`), since GLFW 3.4 loads libwayland-client, libwayland-cursor, libwayland-egl, libxkbcommon and libdecor with dlopen at run time; `ldd build/mine-oh-belowed` shows no new library. The link keeps the shim directory.
- Platform at run time: GLFW 3.4 with both backends takes Wayland when `WAYLAND_DISPLAY` is set and X11 otherwise. The binding has no `glfwGetPlatform`, so `shared/raylib/platform.odin` (ours, in the collection, not a copy) declares it from the same archive (`foreign import lib "linux/libraylib.a"`, `glfwGetPlatform :: proc "c" () -> c.int ---`, `GLFW_PLATFORM_WAYLAND :: 0x00060003`, `GLFW_PLATFORM_X11 :: 0x00060004`), and `display.odin` reports the platform truthfully: the log line's `session` becomes `wayland`, `x11` or `xwayland` (X11 platform with `WAYLAND_DISPLAY` set), read once after `InitWindow`. Under gamescope (the couch) the game may now be a native Wayland client of gamescope; the launcher written by `tools/install_play_build.sh` unsets `WAYLAND_DISPLAY` for the game when `MINE_OH_BELOWED_X11=1`, documented as the way back to X11 if gamescope misbehaves, default GLFW's choice. The `MINE_OH_BELOWED_GAMESCOPE` variable stays.
- High DPI: `window_config_flags` adds `.WINDOW_HIGHDPI`. Read the fetched `src/platforms/rcore_desktop_glfw.c` for what raylib 6.0 does with it (the `GLFW_SCALE_FRAMEBUFFER` hint, `CORE.Window.screenScale` multiplied into the modelview in `BeginDrawing` and after `EndMode3D`, the mouse scale) and lay the UI out in render pixels: the frame passes `GetRenderWidth` and `GetRenderHeight` as `screen_pixels` to `ui_begin` (`loop.odin:749`), so `pixels_per_unit` and the font pixel sizes follow the panel; the pointer position from the window (`GetMousePosition`, in window units) is scaled to render pixels by render over window per axis (`pointer_to_render_pixels`, pure, tested; find every place a window position enters the UI, the SDL trackpad pointer included); the 2D passes (the UI draw list, the diagnostics pages, the underwater rectangle in `render_water.odin`, anything drawing with `GetScreenWidth`) draw after `rlgl.LoadIdentity()` on the modelview and use the render size, so raylib's screen scale does not upscale them a second time and text rasterises at the panel's pixel size; the 3D pass is untouched (the viewport is the framebuffer already). The screenshot (`LoadImageFromScreen`) already reads the framebuffer. On X11 (the couch, scale 1) all of this is the identity; check the couch's display log line after the install says `render` equals `window`.
- The Resolution row: `display_is_desktop_scaled` becomes true only for the `xwayland` platform (the framebuffer follows the scaled screen); a native Wayland window with the high DPI flag reaches the panel, so the row lists the choices up to the monitor's size as on X11. raylib lists no video modes, so the fixed list stays; the tooltip texts follow.
- The flake: with the binding in the repository the nixpkgs patch of `vendor:raylib` no longer applies; the flake instead patches `shared/raylib/raylib.odin`, `rlgl/rlgl.odin` and `platform.odin` in `postPatch` to `"system:raylib"` (and `"system:glfw"` for `platform.odin`, `pkgs.glfw` added to the inputs, since nixpkgs raylib links an external GLFW), drops the `odinForNix` override, and passes the collection flag to both odin calls. CI validates it.
- Tests: `pointer_to_render_pixels` and the platform to session mapping (`display_test.odin` or wherever `display_diagnostics_text` is tested), `display_is_desktop_scaled` for x11, wayland and xwayland, the UI audit gaining a 2880 by 1920 entry at scale 1.7 (render pixels; the existing 1920 by 1080 and 1280 by 800 stay), the settings round trip of `window_mode` and `resolution` if it is not covered.
- Docs: `doc/build.md` (the toolchain section rewritten: the collection, `tools/build_raylib.sh` and its distrobox, `--host`, the committed archive, `MINE_OH_BELOWED_X11`, the gamescope variable now optional on the laptop), `doc/architecture.md` (line 6), `doc/ui.md` (render pixels, the platform line), `CLAUDE.md` (the stack line and the verify commands through `build.sh`), `doc/log/2026-09-28.md`, this item's Status and an Implemented paragraph naming the raylib commit the tag resolved to and the archive's size.

## Implemented

2026-09-28. `tools/build_raylib.sh` built raylib tag 6.0, which resolved to commit dbc56a87da87d973a9c5baa4e7438a9d20121d28, inside the distrobox `mine-oh-belowed-raylib` (GCC 16.2.1); `shared/raylib/linux/libraylib.a` is 3390886 bytes and holds `_glfwConnectWayland` and `_glfwConnectX11`. The game links it with the binding's existing library list and `ldd` shows no new library. Beyond the notes: the collection also carries `raymath.odin` (part of package `raylib`, the game uses it), the build script names the cmake generator (the environment sets Ninja), `platform.odin` also declares `glfwGetCurrentContext` and `glfwGetWindowSize` (the pointer maps with GLFW's window size, since raylib 6.0's `rcore.c` is compiled without `_GLFW_WAYLAND` and gets its mouse scale and its fullscreen screen size wrong on Wayland; the mouse scale is reset to 1 every frame), `ui_draw.odin` clips through rlgl (raylib's `BeginScissorMode` scales its box under the high DPI flag), `diagnostics_test.odin` follows the Render facts' platform field, and the launcher's `MINE_OH_BELOWED_X11` also sets `XDG_SESSION_TYPE=x11` (GLFW otherwise still reaches Wayland through the `wayland-0` socket). Decisions and findings in `doc/log/2026-09-28.md`. Not verified here (headless session, no nix): the window on the laptop and the couch, and the flake in CI.
