# 0156: The recipe browser counts crafts the planner can make

Status: implemented

## Goal

User report (2026-10-01): "when crafting recipes, the can craft X doesn't take into consideration that we now automatically craft needed intermediates, and the missing items are still marked red even though I have materials for the intermediates." Since 0138 the hand crafting queue crafts missing intermediates on demand (`plan_crafts`, `crafting.odin`), but the recipe browser still judges a recipe by the inventory alone: `recipe_craftable_now` (`crafting.odin`) and `crafts_covered` (`ui_recipe_browser.odin`) count direct inputs, `craftable_recipes` feeds the "Can craft" filter and the row colour from them, and `ingredient_color` (`ui_recipes.odin`) paints an input red whenever have is below need, even when the planner would make it from what the player holds.

## Change

- One pure procedure beside the planner answers the browser's question: how many crafts of a recipe the planner can make now, intermediates included, from the inventory and the available recipes, and for each direct input whether it is held, craftable from held materials, or missing. It reuses `make_craft_plan` and `plan_recipe` (or their inner steps) with a count search (plan one craft, then more until the plan refuses; or compute from the plan's virtual counts), bounded by the queue's depth and the plan limits (`Plan_Too_Deep`), so the browser and the queue never disagree about what can be crafted.
- `craftable_recipes` and `crafts_covered` use it: the "Can craft" filter and the row colour follow the planner; the "can craft X" count shows the planner's count.
- `draw_ingredient_rows` shows three states: held (the accent colour as today), craftable from held materials (the dim text colour, the line ending with ", craftable", for example "0 / 2 Iron gear, craftable"), missing (red as today). The theme's colour set may gain one entry if no existing one fits; the UI audit cases that show the recipe detail cover the three states.
- `doc/ui.md` (the recipe browser) states the rule: craftable means the queue would make it, intermediates included; `doc/content.md` or `doc/quests.md` only if they describe the count.

## Verify

- Tests: a recipe whose input is an intermediate the player can craft from held raw materials counts as craftable with the planner's count, its input row is marked craftable not missing; a recipe missing a raw material stays uncraftable with the input red; a recipe whose intermediates exceed the plan depth is refused as the queue refuses it; the UI audit draws the detail panel in all three states.
- `./build.sh check`, `./build.sh check-android`, `./build.sh test`, `python3 tools/check_docs.py`.

## Implementation notes

- `crafting.odin`: `plan_queue_crafts` is what `queue_crafts` does without changing the queue (the recipe's own refusal, `plan_crafts`, the run capacity `HAND_CRAFT_QUEUE_RUNS`); `queue_crafts` now calls it, so the browser and the queue share one decision. `queue_accepts_crafts` asks it for a count. `make_plan_after_queue` (the front repair and the queued runs, shared with `plan_crafts`) and `plan_input` (one ingredient, split out of `plan_inputs`) are the inner steps the browser reuses.
- `planned_crafts(queue, inventory, recipes, unlocks, recipe, allocator) -> Planned_Crafts{count, inputs}`. The count (`planned_craft_count`) is a search, not derived from the virtual counts: rounding up per intermediate, byproducts and the depth bound make a closed form inexact. It doubles from 1 until `queue_accepts_crafts` refuses, then halves the gap, capped at `PLANNED_CRAFT_COUNT_LIMIT` (999, since a recipe whose chain ends without inputs would accept any count). Every returned count was accepted by the same procedure the queue runs, so the browser never shows a count the queue refuses. Should acceptance ever not be monotone in the count (a byproduct of a larger batch covering another ingredient), the search can return less than the largest accepted count, never more. At most about 20 plans per recipe.
- `Planned_Input{state, available}` per direct ingredient of one craft after the queue (`planned_input_states`, state `Held`, `Craftable` or `Missing`): each ingredient is judged once the earlier ingredients that are not missing took theirs, as `plan_inputs` takes them, so with none missing `plan_inputs` plans the craft. `available` is the count it was judged against (the inventory after the queue's runs and the earlier ingredients), and the row shows it as the have number, so number and colour agree: five planks the queue will use read "0 / 1 Plank", and nine plates after a drill's gears took six read "3 / 3 Iron plate" (review fix).
- `craftable_recipes` (`ui_recipe_browser.odin`) asks `queue_accepts_crafts` for one craft per recipe; `crafts_covered` and `recipe_craftable_now` (and its only helper `inventory_holds_inputs`) are gone.
- Cadence: `recipe_screen` called `craftable_recipes` every frame (direct inputs only, cheap). A plan per recipe per frame is too much, so the answers are kept on the browser (`Recipe_Plans` in `Recipe_Browser`): the craftable marks are planned again when `recipe_plan_key` changes (a hash of the inventory slots, the queued runs, the front's started and waiting_for, and the available recipes; not the front's progress, which moves every tick) or the registry's length does, and the detail's count and ingredient states when the key or the focused recipe changes. The browser now owns memory: `destroy_recipe_browser` (`end_session`, the UI audit) and `reset_recipe_browser` (`reset_session_views` on a data reload).
- Colours: held `.Accent`, craftable `.Text_Dim`, missing `.Danger` (`planned_input_colors`); the theme is unchanged. The craftable line is `recipes_ingredient_line_craftable = "{have} / {need} {name}, craftable"`, drawn fitted.
- Tests: `test_planned_crafts_count_the_intermediates`, `test_planned_crafts_without_a_raw_item`, `test_planned_crafts_honour_the_plan_depth`, `test_planned_crafts_count_after_the_queue` (queued runs and a full queue), `test_planned_craft_count_stops_at_the_limit` (`crafting_test.odin`); `test_recipe_plans_follow_what_the_planner_reads`, the Can craft filter now listing plank, plank_slab, plank_stairs and stick for one log, the craftable line in `test_recipe_detail_lines` (`ui_recipe_browser_test.odin`); `test_recipe_detail_shows_how_the_queue_gets_each_ingredient` and the audit case "recipes, ingredients held, craftable and missing" (a burner mining drill over nine iron plates: gears craftable, plates held, stone furnace missing) in `ui_audit_test.odin`.
