# 0102 Windows build and CI artifact for GameNative

Status: implemented
Milestone: M11

## Goal

The user (2026-09-28) wants to run the game on their Android phone in GameNative, which runs Windows x86-64 programs through Wine and Box64. CI must produce an artifact the user downloads, unzips and points the app at: the Windows x64 executable, `SDL3.dll` and `data/`, side by side.

## What stands in the way today

`odin check src -target:windows_amd64` (with the shared collection) fails in two files only: `src/command_socket.odin` (Unix domain sockets, `fcntl`, `chmod` through `core:sys/posix`) and `src/logging.odin` (`posix.write`, `dup2`, `isatty`, the signal handlers), plus the socket test in `src/command_test.odin`. Everything else checks. The paths come from `$XDG_*` and `$HOME`, which Wine does not set. `shared/raylib` holds a Linux archive only, `platform.odin` links it unconditionally, and the toolchain's `vendor/sdl3` links `SDL3.lib` on Windows, a file the Linux toolchain does not ship. CI has one nix job on Linux.

## Deliverables

- The source checks and builds for `windows_amd64`:
  - `src/logging.odin`: on Windows the console write goes through `os.write` to stderr, there is no stderr redirect and no crash trace (no signals); the log file works as on Linux. Guard with `when ODIN_OS == .Windows`, keep the Linux path as it is.
  - `src/command_socket.odin`: on Windows the server never opens; `open_command_server` returns a problem line ("no command socket on Windows") that the frame loop logs once, polling is a no op. The posix test in `src/command_test.odin` is guarded. `tools/moc` stays Linux only.
  - Directories: one place, `platform_directories()` (or a name of your choice) in a new `src/platform_paths.odin`, gives the config home, the state home and the data home the existing pure helpers take. Linux: `$XDG_CONFIG_HOME`, `$XDG_STATE_HOME`, `$XDG_DATA_HOME` and `$HOME` as today. Windows: `%APPDATA%\mine-oh-belowed` stands in for the config home and the data home (configuration and saves roam), `%LOCALAPPDATA%\mine-oh-belowed` for the state home (log, screenshots, texture edits); `MINE_OH_BELOWED_SAVES` still wins. Every caller that reads those environment variables today (`src/configuration.odin`, `src/logging.odin`, `src/loop.odin`, `src/save_world.odin`, `src/render_atlas.odin`, `src/command.odin` and their problem lines) goes through it. The absolute path rule of the XDG helpers stays.
  - Data lookup (`src/data_load.odin`, `src/main.odin`): after `./data` and before the installed layout, `<executable directory>/data`, so the unzipped folder runs from any working directory.
- Libraries:
  - `shared/raylib/windows/raylib.lib`: the static MSVC library from raylib's 6.0 release asset `raylib-6.0_win64_msvc16.zip` (https://github.com/raysan5/raylib/releases/tag/6.0), committed like the Linux archive; record the asset, its URL and the file's SHA-256 in `shared/raylib/README.md` beside the Linux build record. `platform.odin` imports `windows/raylib.lib` on Windows and the Linux archive otherwise (GLFW's functions are in raylib's static library on both). Keep the nix flake's `substituteInPlace` lines matching, since the flake rewrites the Linux paths; CI validates the flake.
  - SDL3 on Windows: the toolchain's `vendor/sdl3` imports `SDL3.lib` relative to its own directory. CI downloads `SDL3-devel-3.4.16-VC.zip` (https://github.com/libsdl-org/SDL/releases/tag/release-3.4.16), copies `lib/x64/SDL3.lib` into the toolchain's `vendor/sdl3/` and ships `lib/x64/SDL3.dll` in the artifact. Nothing of SDL is committed.
- `build.sh`: on a Windows host under Git Bash (`uname -s` starts with `MINGW` or `MSYS`) no linker shims, the output `build/mine-oh-belowed.exe`, and `release` passes `-subsystem:windows` so no console window opens beside the game; `ODIN` names `odin.exe`. A new mode `check-windows` runs `odin check src -target:windows_amd64 -vet -strict-style` with the collection on any host, so agents on Linux catch regressions; add that check to the nix derivation's check phase too (`flake.nix`), so the Linux CI job guards it on every push.
- CI (`.github/workflows/ci.yml`): a second job `windows` on `windows-latest`: checkout; MSVC environment (`ilammy/msvc-dev-cmd@v1`); Odin from the release asset `odin-windows-amd64-dev-2026-09.zip` (https://github.com/odin-lang/Odin/releases/tag/dev-2026-09; find `odin.exe` wherever the zip puts it); the SDL3 step above; `MINE_OH_BELOWED_COMMIT=<short sha> ./build.sh release` under `shell: bash` (the commit passed in, so a line ending difference never marks the build dirty); a package step that lays out `dist/mine-oh-belowed/` with `mine-oh-belowed.exe`, `SDL3.dll`, `data/` and a short `README.txt` (what it is, the build stamp, where the log and saves land under Wine); `actions/upload-artifact@v4` (check the current major on GitHub) named `mine-oh-belowed-windows-x64-<short sha>` from `dist/`. The job builds only: the test suite stays on Linux (the tests assume Unix paths and sockets; a Windows test run is a later item). Pin every download by version; a checksum where the release page gives one.
- Docs: `doc/build.md` (a Windows section: what CI builds, how to fetch the artifact with the browser or `gh run download`, GameNative pointed at the executable, what the Windows build lacks: command socket, crash traces, the couch launcher; where files land under Wine), `doc/architecture.md` (the logging line, the directories), `doc/commands.md` (Linux only), `DESIGN.md` Technical (the phone as a further target through GameNative), `doc/log/2026-09-28.md`, this item.

## Verify

- `./build.sh check`, `./build.sh check-windows`, `./build.sh test`, `./build.sh release` pass on this machine.
- CI: the nix job stays green with the new check; the windows job is green and its artifact holds the executable, `SDL3.dll` and `data/`. The main agent watches CI and iterates on the workflow if the runner disagrees.
- User: on the phone, GameNative pointed at `mine-oh-belowed.exe` starts the game, the title screen shows the build stamp, a world can be made and saved, the log lands under `%LOCALAPPDATA%\mine-oh-belowed\log.txt` in the container.

## Implemented

2026-09-28. `src/platform_paths.odin` holds `platform_directories` (Linux: the XDG variables and `$HOME` as before; Windows: `%APPDATA%` as config and data home, `%LOCALAPPDATA%` as state home, no home, no runtime directory, no system configuration directory) and every former environment reader goes through it. The command socket and the POSIX parts of logging live in files tagged `#+build !windows` (`command_socket_posix.odin`, `logging_posix.odin`, `command_socket_posix_test.odin`) with `#+build windows` counterparts (stubs and the console write), after the second CI run showed that a `when` block leaves the `core:sys/posix` import, and with it the static C runtime, in the Windows link; `test_static_runtime_imports_stay_out_of_windows` guards the rule. `<executable directory>/data` joins the data lookup. `shared/raylib/windows/raylib.lib` is committed (SHA-256 `e979fda995ea6b4ac0162156c6bc5d44c1ef6d995941f648a4f05ee19f3e00cb`). `build.sh` has `check-windows` and a Git Bash branch; the flake runs the Windows check; CI has the `windows` job, with `actions/upload-artifact@v7` (the current major on 2026-09-28, not v4). Verified here: `./build.sh check`, `./build.sh check-windows`, `./build.sh test` (1050 tests) and `./build.sh release`. Not verified: the flake (no Nix here), the `windows` job on the runner, the game on the phone. Decisions and the untested runner assumptions are in `doc/log/2026-09-28.md`.

Third CI run (main agent, 2026-09-28): green, the artifact `mine-oh-belowed-windows-x64-<commit>` holds the GUI executable, `SDL3.dll`, `data/` and a README. Under Proton 11's Wine here (`tools/wine_smoke_test.sh`) the executable printed its version and wrote its log under `AppData\Local`, then Wine aborted on `icu.dll.ucal_getDefaultTimeZone` from `core:time/timezone.region_load("local")` (the title screen's save dates). `local_zone.odin` with its posix and windows sides replaces that: a region on Linux, an offset from `GetTimeZoneInformation` on Windows. Left for the user: the phone.
