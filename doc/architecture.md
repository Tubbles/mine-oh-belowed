# Architecture

## Stack

- Odin dev-2026-09. Data oriented, procedures and structs, matching the code rules in `CLAUDE.md`.
- raylib 6.0 through the repository collection `shared:raylib` (0085: the toolchain's binding copied, linking a static raylib built from source by `tools/build_raylib.sh`, see `build.md`) for the window, OpenGL rendering through rlgl, textures, fonts and audio. Its GLFW has the Wayland and the X11 backend and takes Wayland when the session offers it; the window asks for high DPI, so the framebuffer has the panel's pixels on a scaled Wayland desktop. Fonts are built from their TrueType files the way raylib's `LoadFontFromMemory` does (`ui_font.odin`), with the glyph atlas uploaded as RGBA instead of raylib's two-channel format, because Winlator's Gladio drops the texture swizzle raylib sets for it and the glyphs render in red boxes on the phone (0106).
- SDL3 through `vendor:sdl3` for controller input only (joystick, gamepad and sensor subsystems). SDL video is never initialised. raylib's GLFW gamepad path remains as the fallback for generic controllers.

## Process structure

- Main loop: render at vsync or at the frame rate cap from the settings (0080, both optional), simulate at a fixed 60 ticks per second with an accumulator. Only the camera interpolates between ticks, from the previous tick's player state to the current one.
- Frames and ticks run at different rates, so frame input is accumulated between ticks: `look_delta` (pixels) and `just_pressed` (edges) are events that sum up and the first tick after them takes the whole sum, held state (move, look, pressed) is a level and every tick reads the latest frame. A second tick in the same frame sees zero events.
- The simulation owns the `World` and the players. The player body is ticked in the simulation, never per frame, with axis separated swept collision against the collision boxes of blocks (0061: a cube's cell, a slab's half, the two boxes of stairs, none for torches; `block_shape.odin`) and whole cells of entities other than belts and splitters; the raycast hits a shaped block only where it meets its boxes, or a post's bounds. Player physics is the one place plain `f32` is allowed to accumulate, until the world scale is settled; it stays deterministic for the same binary and input.
- The simulation never reads the wall clock. Random numbers come from generators seeded by world seed, chunk coordinate or tick.
- Fixed point everywhere a simulation quantity accumulates: belt positions, fluid volumes, energy buffers, crafting progress, vein reservoirs are integers with a fixed scale. Floats stay in rendering and input. Debug builds hash the simulation state every tick, and a test runs two simulations from one seed and compares the hashes.
- Players are an array in the world state, each with its own camera and input frame. The alpha runs one player. Split screen co-op adds more without a redesign.
- Chunk generation and meshing run on worker threads (`core:thread`, processor cores minus one, at most six) and hand results to the main thread through mutex protected queues. Workers never touch the `World`: a generate job carries only a coordinate, a mesh job carries private copies of the chunk and its six neighbours. Per frame limits keep the main thread smooth (16 generated chunks inserted, 8 mesh jobs submitted, 6 non empty mesh uploads, 48 jobs pending). A chunk is meshed once all neighbours inside the load volume are loaded, and stale mesh results are dropped by revision. The simulation is single threaded in the alpha.
- Generation is a pure function of the world seed and the chunk coordinate. Features that cross chunk borders (trees, vein outcrops) come from per column and per region hashes any chunk can recompute, so load order and thread count never change the world. Each purpose (height, moisture, caves, trees, veins) has its own sub seed derived from the world seed. The surface height (`terrain_height`, 0057) is one pure function of the sub seeds and a column, at most eight 2D noise samples: continental swell shaped into lowlands and raised masses, ridged ranges and hills sampled at a domain warped position (only on raised ground), plateaus pulled up to multiples of 12 blocks above sea level with a cliff band, damped detail, and river valleys (banks lowered towards sea level, walls of bounded slope, the bed). `GENERATOR_VERSION` counts terrain changes.

## Sessions

The window, renderer, UI and input backend are created once per process. A `Session` holds one world: the simulation, a copy of the generator with the world's seed and richness, the streaming state, the save location and the tick accumulator. The title state has no session; starting or loading a world creates one, quit to title saves and destroys it and drops the chunk meshes. Menus request session changes on the title state and the frame loop applies them after the frame, so a failed start shows a toast and leaves the menus in place. Biomes and vein tables load once and are copied per session; the research cost setting is a per session scaled copy of the technology registry.

## Packages

One `game` package under `src/`, split into files by concern: `world_*.odin`, `generation_*.odin`, `simulation_*.odin`, `render_*.odin`, `input_*.odin`, `ui_*.odin`, `data_*.odin`, `save_*.odin`. Odin forbids import cycles and a game's concerns are tightly coupled, so packages are only split off for leaf utilities with no back references (configuration loading, noise helpers). `odin test src` runs the tests of the package.

## World storage

- A chunk is 32 by 32 by 32 blocks in flat arrays: block id (`u16`), light (`u16`, four nibbles from the highest: sky, red, green and blue block light, 0072). Chunks live in a hash map keyed by chunk coordinate.
- Water levels are block ids: the source block plus seven flowing water ids marked by a `water_level` field in the block data. This keeps the chunk layout and serialisation unchanged and saves water levels for free.
- Light: generation workers compute a chunk's initial sky light from its own columns. Everything that crosses chunk borders or follows an edit runs on the main thread inside the simulation tick through bounded queues (a removal queue and an addition queue, removals first), so the final values never depend on visiting order. Since 0072 block light is coloured: the queues carry the channel (sky, red, green, blue), every channel spreads alike and never mixes with another, so two emitters of different colours mix by taking the larger level per channel; the step budget per tick counts nodes over all channels, so a white emitter costs three times one channel. Emitters take their colour from `light_color` in the data (`block_light_color`, the lamp's `Machine.light_color`), and entity lights map a cell to a colour. Every `world_set_block` is recorded as a block change that the next tick turns into light updates and, next to water, water updates.
- Water flow is Minecraft style cellular flow, scheduled per cell with a fixed delay, run in scheduling order and bounded per tick, on the main thread.
- Mesh jobs copy the chunk plus a one cell shell of blocks and light from all 26 neighbours, because smooth lighting and ambient occlusion need edge and corner neighbours. The vertex colour packs sky light into red and occlusion into blue, green carries the face's tile variation (0088, 0101: 0 turn and slide, 128 turn only for framed blocks, 255 keep upright), and alpha marks the vertices the wind sways (0063); the red, green and blue block light go into the mesh's normals (0072, `block_light_normal`), averaged per channel over the same cells. The fragment shader scales sky light by the day factor and colours it by the sky tint (0064: white by day, warm at dawn and dusk, blue grey at night); block light is neither scaled nor tinted, keeps its colour per channel and is multiplied by a flicker uniform (0072, `light_flicker`: two sines of the render time with periods 0.17 and 0.41 seconds, 0.96 to 1, the same for every block light, lamps included). Models tint the sky share of their light the same way and take the block light per channel (`model_light_tint`), without the flicker.
- Entities (machines, belts, inserters, chests) are not blocks. They occupy block volumes and each occupied cell holds the entity handle, so a raycast hits the entity and placement checks are cell lookups.
- Meshing: greedy meshing per chunk into a raylib `Mesh` with a texture atlas, uploaded with `UploadMesh`. Only cubes join the greedy pass; blocks of other shapes (0061: slabs, stairs, posts, crosses) are meshed cell by cell from their quads in a second pass, border quads hidden by opaque neighbours, and a cube face shows against them. Texcoords run in blocks from the face's rectangle and repeat with `fract()` (0083, `face_texcoord`): on a side face x runs along the horizontal axis and y down from the face's top, so the tile's top row is up on every side; top and bottom faces run x along x and y along z; a shaped quad maps its corners the same way within its cell, so a slab side shows the lower half of its tile. Light emitting posts are collected as flame cells, drawn as flickering camera facing quads (`render_flames.odin`). The atlas has a 16 by 16 tile per block and face group, generated for the blocks listed in `data/textures/procedural.sjson` with the texture edits from the state directory over them (0099, `texture_generate.odin`: periodic noise blurred on the torus, the ores), else from `data/textures/blocks/`, else the block's colour (0060, `render_atlas.odin`); the item icons have an atlas of their own (`render_icons.odin`). Remesh on edit, frustum culling per chunk, fog hides the load boundary: its end lies one chunk inside `LOAD_RADIUS_HORIZONTAL` and its start at 60 percent of the end (`fog_distances`), in the horizon colour, so chunks fade into the sky. The sky pass (0064, `render_sky.odin`) draws first inside the 3D mode, centred on the camera without depth test or depth writes: a 24 by 8 segment hemisphere dome (193 vertices) whose vertex colours blend the horizon into the zenith colour and are rewritten each frame with `UpdateMeshBuffer`, up to 500 stars from a hash as one batch of quads, turning with the day about the sun path axis and fading in with the night, then the sun and the moon as discs, the moon's phase from the day count as a second disc in the sky colour. The discs and the satellite quad face the camera along their own direction (0092, `disc_axes`: right level, up towards the zenith, drawn through rlgl), since raylib's billboards take the world's up and squash a disc high in the sky into an ellipse. `render_day.odin` derives all of it (`Day_Sky`: day fraction, day number, blend, `Sky_Colors`) from the tick and the day length; the clear colour is the horizon colour, which shows below the dome. A custom shader applies per vertex light and ambient occlusion and discards texels with alpha below 0.5, which only the ground cover tiles (0082) and the torch have. The shaders under `data/shaders` are GLSL 330 and every integer literal in them carries the `u` suffix (0105), because Winlator's Gladio rewrites the GLSL line by line and appends `.0` to every bare integer on a line with a float variable (`hash >> 8` became `hash >> 8.0`, which does not compile); `shader_source_test.odin` fails on a bare integer literal. Gladio also fails a compile now and then and compiles the same files on the next start (0109), so `load_shader_pair` tries every shader up to three times (`SHADER_LOAD_ATTEMPTS`), logging `shader: <name> failed to load, attempt <n> of 3` after each failure and releasing nothing in between, since a failed `LoadShader` returns raylib's default shader; the chunk and water shaders, hot reload included, all load through it. Per block variation (0088, `texture_variation.odin` mirrors the shader's choice for the tests): a hash of the block's integer position (the cell a hundredth of a block behind the face, away from the viewer by the screen derivatives' cross product, so a face on a block boundary reads one cell) picks one of eight orientations of the tile inside the block (a mirror of x, then zero to three quarter turns, applied to the `fract` of the texcoords, so the 0083 rule still sets which texcoord is where), then slides the tile by a whole texel offset, 0 to 15 on each axis from hash bits 3 to 6 and 7 to 10, wrapped inside the tile and clamped to its last texel (0101: two neighbours whose orientations mirror across their shared edge still show different crops, so no symmetric motif forms), and a brightness jitter of plus or minus 4 percent; the side faces of blocks with `keep_orientation` (green 255) stay upright and unshifted, their tops and bottoms vary; the faces of `framed` blocks (green 128, the log ends) turn and mirror but never slide (`Tile_Variation`, `face_tile_variation`; the shader splits green at 0.25 and 0.75). A tile that slides must be periodic, so the offset shows no seam inside the block (`texture_periodicity_test.odin`). The water shader takes the jitter only: its tile keeps its orientation, since the flow scrolls along the face's own axes (0065), and it takes no offset, since the seamless repeat of its isotropic tile shows no block grid where per block crops would. Every face of a water block goes to separate water parts (0065), which the opaque pass no longer draws.
- Texture uploads (0106): every texture goes up through `load_rgba_texture` (`render_atlas.odin`), which converts a copy of any image that is not RGBA before `LoadTextureFromImage`, since raylib uploads gray and gray alpha images with a texture swizzle that Gladio drops.
- Weather (0063): `weather_at(seed, tick, day_length_ticks)` (`weather.odin`) is a pure schedule, not state: each game hour (a twenty fourth of the day) gets a kind (clear 50 percent, overcast 25, rain 15, fog 10) and a peak intensity from a hash of the seed and the hour index, ramped over the first and last tenth of the hour. Nothing is saved; the weather command's forced kind lives in `Session.weather_override`. The renderer reads it once per frame (`session_weather` in `loop.odin`, clear with the `weather` setting off) and `render_weather.odin` turns it into what is drawn, from the render time and the camera alone: the fog distances scaled by 0.8 (overcast), 0.5 (rain) or 0.25 (fog) blended by the intensity, the sky colours greyed and darkened in overcast and rain, the sky tint darkened by up to 25 percent in rain (wet ground); rain as streaks (`DrawLine3D`) and snow, where the camera's column is colder than -0.45, as small billboards, up to 600 particles fixed in the world and wrapped into a 12 block cylinder around the camera, their count scaled by the intensity and by the sky light at the camera, so none fall under a roof; the chunk vertex shader sways vertices whose colour alpha is below 1 (the upper vertices of cross shaped blocks, `sway_vertex_light`) by up to 0.15 blocks, wind strength 0.3 clear to 1 in rain; the chunk fragment shader dims the sky light term by a 64 by 64 tiling value noise texture (generated once, bound as the material's second map) laid over every 96 blocks and drifting with the render time, strength 0.15 clear, 0.35 overcast and rain, 0 at night.
- Water pass (0065, `render_water.odin`): the mesher routes every water face into `Chunk_Mesh_Data.water_parts`, the same layout plus a tangent per vertex holding the cell's flow direction (the level differences to its horizontal water neighbours, pointing downhill, zero for a source) and the vertex's shore value (1 where a solid cell in the water's layer touches the vertex); flow and shore are part of the face key, so water merges only where they match. The parts upload as `Chunk_Render.water_meshes` and are drawn by `draw_water_chunks` after the solid chunks, the models, the belts, the loose items and the flames, before the weather particles and the player overlay, with a material of its own (`data/shaders/water.vs` and `water.fs`, sharing the atlas, hot reloaded with the chunk pair), alpha blending, depth test on, depth writes and backface culling off. The fragment shader draws the texel at alpha 0.6, lightens it by up to 15 percent with two sines scrolling over the world x and z, runs the texture along the flow and lays a lighter, faster scrolling foam band along the shore. When the camera's cell holds water, both materials take a fog from 2 to 14 blocks in a blue green over the weather's, and a blue green rectangle at alpha 0.35 tints the view after the 3D pass; the sky pass still draws.
- Ambient life (0075, `ambient_life.odin` pure, `render_life.odin` drawing): stateless like the weather, a function of the world seed, the tick, the render time and the camera; nothing is saved and the simulation never reads it. Birds: flock cells of 96 blocks on a world aligned grid; a cell holds a flock when a hash of the seed and the cell lies below the `bird_density` of the biome at the loop's centre (the cell's centre moved up to 20 blocks by the hash, sampled with `sample_column`, which also gives the surface). A flock of 5 to 9 birds flies a rounded rectangle 40 by 24 blocks (corner radius 8) turned about y by the hash, 18 to 26 blocks above that surface, one way round or the other, once per 54 to 66 seconds of tick time (`loop_seconds`, the tick plus the interpolation alpha), so a flock is at the same place at the same tick on every run. The birds trail each other 0.5 to 1.5 percent of the loop apart, up to 2 blocks to either side of the path, bobbing 0.8 blocks over 4 to 7 seconds; each is a dark body quad and two wing quads whose tips beat at 2.4 to 3.6 Hz of the render time, faded in and out over a glide wave of 5 to 11 seconds. Every period and phase comes from a hash of the flock and the bird. The cells within 160 blocks plus the loop's reach are found every frame (about 40, most rejected by the largest density before any column is sampled); a bird draws within 160 blocks, faded by the fog, and only by day and not in rain (`life_presence`: the daylight blend from 0.2 to 0.6, rain intensity above 0.25 grounds them). Insects: the mesher lists the cells of cross shaped blocks (`Chunk_Mesh_Data.covers`, kept per chunk in `Chunk_Render.covers`); one in two cells of a block a biome's ground cover marks with `insects` gets two motes on Lissajous paths within 0.3 to 0.6 blocks of it, three angular speeds and phases from a hash of the cell and the mote, drawn within 24 blocks by day as small bright billboards. Fish: the mesher lists the source water cells under an open cell with water in the two cells below (`water_surface_cell`; the shell reaches one cell past the chunk, so a surface on the chunk's bottom layer, where the sea level lies, needs one); `apply_chunk_mesh` keeps the one in eight a hash picks (`Chunk_Render.fish`). A fish shadow is a dark ellipse half a block long 0.2 below the surface, gliding a lemniscate 1 to 1.6 blocks wide in 16 to 26 seconds of render time, turned and phased by the cell's hash, drawn within 32 blocks, dimmed at night, before the water pass so the surface tints it. Birds and motes draw after the water pass. Every pass is depth tested without depth writes. A forest lake view (seed 20260927, camera at -176, 36, 240) draws 2 flocks with 10 birds in reach, 4 motes (the forest has no flowers; plains flowers at its edge) and 63 fish out of 543 surface cells.
- Particles (0067, `particles.odin`, `render_particles.odin`): render state in `Frame_State`, never read or written by the simulation, reset on a session change. A pool of 2048 particles whose next index wraps, so a new one replaces the oldest; each kind (debris, puff, smoke, steam, spark, flame, exhaust) has its gravity, drag, launch speed, lifetime and growth, and the pool advances by the frame time capped at a tenth of a second. Each frame `emitters_for_frame` reads the entity states: a burning furnace and a producing boiler smoke, a producing steam engine steams, a generating combustion generator gives thin exhaust, a flaring flare stack a flame, a working alloy furnace sparks, a launching pad exhaust under the rocket and smoke on the platform, a player digging a block debris in the block's top colour. The spawn count per emitter is its rate times the frame time, the fraction rounded by a hash of the frame count and the emitter's cell, so no emitter keeps state. `Particle_Memory` keeps the last frame's dig (past half way and the block gone gives a burst of 24 puffs) and shipment count (a new shipment drops a capsule under a parachute from 60 blocks onto the drop capsule over 8 seconds, then a puff). Drawn after the water pass and before the weather, depth test on and depth writes off: debris as tiny cubes, the rest as soft 16 texel disc billboards fading over the last third of their life, darkened by the sky light unless they glow (sparks, flames, exhaust).
- The player (0066, `player_animation.odin`, `render_player_model.odin`, `render_player.odin`): six limb models (`data/models/player_*.vox`), each the whole 10 by 29 by 10 voxel frame with its limb filled, meshed like the machine models and swung about a pivot read from the limb's voxel bounds (the shoulder one voxel under the top of an arm, the hip at the top of a leg, the neck at the bottom of the head); they reload with the machine models, and without them the capsule stands in. The walk phase is a cadence distance the render memory adds up tick by tick from the walked distance the statistics count (`distance_walked_millimetres`), divided by the cheat speed factor (0087), so the developer cheat never quickens the steps or the bob, over 4.8 metres per cycle (0089: about two steps a second at walking speed), arms and legs swing in opposition by up to 35 degrees (50 sprinting), the mine chop runs on the render time every 0.4 seconds while `Mining_State.active`, and a place swing of 0.25 seconds starts when the summed placed counters (`placed`, `blocks_placed`) grew. `Player_Animation_Memory` in `Frame_State`, render state reset with the session, holds the last distance and counters; whether the player moves is decided per new tick, not per frame, so a display faster than the tick rate does not stop the walk every other frame. Third person draws the body in the world pass at the interpolated pose; first person closes the world's 3D pass and opens a second one with the depth test off for the right arm, held forward from the lower right of the view, and the held stack's icon billboard at the hand, over the bobbed camera. Each half cycle on the ground and out of water spawns 6 puffs in the colour of the block under the feet into the particle pool.
- Sound (0068, `audio.odin`, `sound_events.odin`): raylib audio opened after the window; without a device a log line says so and every call is a no op. The mixer loads the table `data/sounds/sounds.sjson` into an arena of its own: effects as `Sound`, loops as `Music` streams. An effect id plays at most once per 40 milliseconds, so repeats never stack (raylib plays a `Sound` on one voice, a replay restarts it). A loop has a target volume that the frame sets and the mixer approaches linearly, silent to full in half a second, then the targets clear, so a loop nobody asks for fades out and stops; `UpdateMusicStream` runs every frame for every playing loop. Effects scale with the effects volume, loops with the ambience volume, both with the master volume. The triggers read the world after the particles each frame against `Sound_Memory` in `Frame_State` (render state, reset with the session, the first frame only learns): a footstep per half walk cycle at tick granularity like the animation, on the ground or wading, in the material of the water at the feet or the block under them, pitched 0.9 to 1.1 from a hash of the step count; a mining hit when the dig crosses a quarter (the effective tool tier picks the sound); the break when `blocks_mined` grew, the place thud when the placed counters grew; the launch when a pad entered `Launching`; the landing when the particles' capsule descent ended; the chime when a new quest message is an `item_discovered` one. The nearest working machine (the bottleneck marker is green) within 12 blocks of the eye picks its family's hum (fluid machines hum as fluid, the others electric with an electric draw, else burner), loud at the eye and silent at 12 blocks; the biome under the player (`sample_column`) picks its ambience loop, and rain plays at the weather's intensity times the open sky at the eye. The simulation never sees any of it.

## Simulation

- Entity pools per type (`[dynamic]Mining_Drill`, `[dynamic]Inserter`, and so on) with generational handles. Each type has its own update procedure over its own array. No general entity component system.
- Belts follow the transport line model: items are fixed point offsets along a line, lines merge and split at belt junctions. Ramps and lifts are lines with a different geometry, not special cases in the item logic.
- Fluid and electric networks are rebuilt on topology change and evaluated per tick in fixed point.
- Recipes have any number of inputs and any number of outputs, each an item or a fluid, from the very first recipe. Machines have typed slots. There is no single output fast path to retrofit later.
- Crafting machines hold a recipe id and a progress counter. Recipes are prototypes resolved to dense indices at load time.
- Veins are entities, not block data: a reservoir struct with per ore amounts, centre, radius and size class, placed per region of 8 by 8 chunk columns so that every footprint lies inside its region. Generation threads compute footprints, the main thread registers each vein once when the first chunk of an overlapping column loads. Drills hold a vein handle. There are no per block ore counters. `vein_at_column` finds the registered surface vein under a column and drill placement and the HUD use it (0048); only the geologist's hammer still asks for an outcrop block. While the landing pad is present, the surface veins of a region also include the starter veins whose centre lies in it (0045), after the natural veins and without the natural veins they overlap, so every consumer of veins sees them through the same procedure. Chunk generation runs terrain, then trees and boulders, then outcrops, then clears the column above every outcrop, then sets the ground cover (0082, one cross per column at most from a column hash, never in a vein footprint), then stamps the pad; vein footprint columns are open to the sky, and cover is not opaque, so it changes no sky light.
- Fluids use one network model with a phase per fluid. Segments balance by fill fraction per connection with a per tick flow cap; a liquid segment only feeds neighbours at its height or lower, a running pump lifts its output network above that rule, and gas networks ignore height.
- Production statistics counters (produced, obtained, delivered per item, placed per machine, machine stalls, fuel burned, blocks mined, distance walked, and three rings per item for produced and consumed rates: 60 per second buckets, 60 per ten second buckets and 60 per minute buckets, the coarser fed from the finer, all saved) live on the `World` next to the entity pools. Furnaces, crafting machines and drills carry a 60 bucket ring of their own output for the panel rate readout. The quest runtime, the statistics screen and the bottleneck overlay all read them.
- Shipments (tick and cargo of every rocket launched) live on the `World` next to the statistics and are saved; launch requests from the UI are served inside the simulation tick because the shipment needs the tick.
- The venture state (0041: the open contracts with their deliveries and offer counts, the venture credit, and catalogue orders waiting for the next tick) lives on the `World` and is saved; the levels of infinite technologies live in the research state next to the queued technology, since drills and labs read them every tick. Shipments are served right after the launches in the same tick: contracts oldest first, then free trade. `Simulation_Content` carries a read only pointer to the session's generator, set per frame and nil in tests, so the orbital survey can chart veins in chunks that were never loaded.
- Developer requests (0043) are a list on the simulation state filled by the Developer screen and by `--chapter` and `--give`, served at the start of the next tick and never saved, so the UI frame changes no simulation state itself. The command socket (0053, `doc/commands.md`) builds the same requests from lines a client sends over a Unix domain socket in developer mode and serves them on the main thread between ticks, after the frame's ticks, so each response can report a refusal; the simulation never reads the socket. Veins added by command live in `World.veins` with `added` set and are stamped into chunks as they arrive. The developer cheat speed (0044) is a flag on the simulation state, not saved, that triples movement speed and divides hand mining ticks by ten. The day cycle reads the tick plus a day offset the developer menu can set; the offset is saved through the world file's day time field, so the save format is unchanged and older saves load with offset 0.
- Logging (0043): when stderr is not a terminal, as under Steam, the log file is put on the stderr descriptor so Odin's runtime reports (bounds checks, type assertions) land in `log.txt`; the game's own lines go once to the log and once to the original stderr, and raylib's trace log (its warnings and GLFW's errors) takes the same path through a trace log callback (`raylib_log.odin`), which drops GLFW's feature unavailable errors: on Wayland every window position query and placement raises one, raylib makes them at start and on every current monitor lookup, and nothing is wrong or can be done about them. After the display line the start logs one `gl:` line with the GL vendor, renderer, version and GLSL version (0104, `log_gl_info`, `glGetString` through `glfwGetProcAddress`, so nothing links libGL or opengl32; on Android, 0114, straight from `libGLESv3`), because a translation layer under Wine can reject a shader without naming itself. The main thread's assertion failures and SIGSEGV or SIGILL write a back trace to the log before the process ends. The descriptors, the redirect and the signal handlers are in `logging_posix.odin` (`#+build !windows`), the platform neutral rest in `logging.odin`. On Windows (0102, `logging_windows.odin`, `#+build windows`) the console lines go to stderr through `os.write_string`, stderr is never redirected and no signal handler is installed, so only the assertion back trace remains; the log file works as on Linux but sits beside the executable (0103, `platform_log_directory`). Build tags rather than `when` blocks, because importing `core:sys/posix` links the static C runtime on Windows (see `build.md`, Windows). The command socket is split the same way: `command_socket.odin` (paths, queued line, command log), `command_socket_posix.odin` and the stubs in `command_socket_windows.odin`. On Windows `COMMAND_SOCKET_SUPPORTED` is false, so developer mode leaves the socket out silently: no open is attempted and nothing is logged (0108). The Android build (0114) is split by the subtarget tags `#+build linux:android` and `#+build !linux:android`: `main_android.odin` (the exported `__wrap_main` that raylib's `android_main` reaches), `platform_android.odin` (the NDK structures, `GetAndroidApp`, logcat through `__android_log_write`, where `log_printf` sends every line too), `input_sdl3_android.odin` (the stand ins for `input_sdl3.odin`, which is left out) and the leaf package `android_libc/` (glibc functions bionic lacks), see `build.md`, Android app.
- The title's save list (0044, 0047) reads each save's world file version and the entities file's header and content tables, so saves of another format version are listed as not loadable instead of failing at load.
- Quests are data: chapters of objectives whose predicates are evaluated against the statistics counters, placed entity counts and research state every tick. The journal reads the same state.

## Data driven content

`data/*.sjson` holds blocks (each with a `name_key`, `discoverable` marking an ore that reads "Unknown ore" until its drop was obtained, 0052), items, recipes, machines, technologies, vein types and ore tables, biomes, tree species (0059), quest chapters, the touch overlay's layout (0115, `touch_overlay.sjson`, loaded with the content tables though only the input layer reads it). Files are parsed with `core:encoding/json` (`Specification.SJSON`) into prototype tables at startup through `load_game_data`, into a per generation arena the frame state owns. String ids are resolved to dense integer indices once. Hot reload (0054): the operating system reports the changes under the data directory (0111: the vendored odin-fsw in `shared/fsw`, inotify on Linux, ReadDirectoryChangesW on Windows), and the main thread takes the events every frame without stat'ing a file (the once a second scan it replaced stalled the phone for seconds, 0110); a watcher that cannot be opened logs one `data: cannot watch` line and leaves the watch off for the run; strings, bindings, developer kits, shaders, fonts, machine models, sounds (0068), textures (both atlases rebuilt, the chunk meshes kept since the layout depends on the block count alone) and the UI theme (0071: `ui/theme.sjson` and the icons under `ui/icons/`, the UI atlas rebuilt and the theme applied) reload in place on change (a failed parse keeps the old data and says so), while the content tables reload only on request (the `reload` command, F8 or the Developer screen, or automatically with `watch_data = all` after a quiet second): the world is encoded through the save codec in memory, the data loads and validates as at start, and the world is decoded back with the content remap (0047), loaded chunks kept with their blocks remapped and remeshed. A generator change affects only chunks loaded afterwards.

## Strings and units

Every player facing string lives in `data/strings/en.sjson` and is referenced by key, from the first screen that shows text. One procedure formats quantities with their units (per minute, kW, MW, L), so the realism units stay consistent and localisation later is a data change. The developer diagnostics screen is the one exception and may use literal strings.

## Save format

Worlds live under `$XDG_DATA_HOME/mine-oh-belowed/saves/<world>/` (override with `MINE_OH_BELOWED_SAVES`): a `world.sjson` with format version, generator version (0057: a file without one reads 1; an older version still loads, is marked "terrain changed" in the load list, and its unmodified chunks regenerate with the new terrain), name, seed, world settings, tick, day time and the landing pad's centre (0049, so a loaded world keeps its pad and starter veins when the spawn rules change; a file without one falls back to the spawn search); `entities.bin`, a hand written little endian file holding every entity pool and the world's simulation state (players, research, quests, statistics, unlocks, pending block and water updates, loose items, leaf decay) driven by Odin type information so a new field cannot be left out silently. Since 0047 (format version 2) structs are written with a per container schema of field names, shallow kinds and sizes, so fields can be added, removed or reordered and only a retyped field refuses; enums and bit sets are written by name (an unknown name reads as zero); a fixed array saved shorter than the current one fills the start and a longer one refuses. Tables added after format version 2 follow the players at the end of the file, in the order they were added, each read only while bytes are left (`write_later_tables`, `read_later_tables`), so an older file loads with them empty without a format version step; the first is the loose item list (0062), whose stacks of a vanished item are dropped, the second the leaf decay queue (0059). After the header come the id tables of the game data (blocks, items, fluids, machines, recipes, technologies, quests, contracts, vein types, catalogue) and loading maps every saved id to this build's by name (`save_remap.odin`): values of the distinct id types inside the codec, every id indexed array and plain index explicitly. What vanished is dropped (an item stack empties, a queued technology dequeues, a gone active quest gives way to the first quest not done); only a placed machine, a registered vein type or a chunk block that vanished refuses the file. Not remapped yet: vein size classes, quest hint and objective arrays, contract deliveries, all by index; fixed length slices such as the inventory still refuse on a length change. Then `regions/<x>_<z>.bin` holding only modified chunks as a per chunk palette plus run length encoded indices, the palettes remapped through the block table as a region loads. Unmodified chunks regenerate from the seed. Light is not saved: a loaded chunk recomputes its sky light with the generation column procedure and re seeds block and entity lights. Networks are rebuilt after load. Saving pauses the simulation, writes to a `.saving` directory and swaps it into place through a `.previous` directory, so a crash never leaves a half written save. Autosave counts simulated ticks. Odin's `core:compress/zlib` only inflates, so there is no zlib compressor in the standard library; palette plus run length encoding suits voxel data and needs no dependency.

## Input abstraction

Actions, not buttons. An `Action` enum (move, look, jump, mine, place, rotate, pipette, hotbar radial, inventory, map, pause, and so on) and an `Input_Frame` struct that a backend fills every frame. Backends: SDL3 for the Steam Controller with its full feature set, raylib gamepad for generic controllers, keyboard and mouse for development. Bindings live in configuration, not in code. The SDL3 backend logs how many joysticks SDL sees at start and one line per joystick added or removed (name, vendor, product, GUID and whether SDL has a gamepad mapping for it), so a controller SDL sees but does not take for a gamepad is told apart from one it never sees. Details in [input.md](input.md).

## Configuration

SJSON with the layering from the global preference: `$XDG_CONFIG_DIRS`, `$XDG_CONFIG_HOME/mine-oh-belowed/config.sjson`, `config.d/*.sjson`, then `--set=<key>=<value>` flags. No per project layer, the game has no project dimension. Files are parsed as generic SJSON trees and merged with provenance per key (objects merge, scalars and arrays replace), then mapped onto the typed `Configuration` (settings, bindings, paths) with strict checks: an unknown key, a wrong type or an out of range value is an error naming the file. `mine-oh-belowed config` prints the files in precedence order and the effective values with their source. The settings screen writes `config.d/90-settings.sjson`. The touch layout editor writes `touch_overlay.sjson` beside `config.d/` in the user directory (0121, `input.md`), a file of its own that is no configuration layer. Saves go to `$XDG_DATA_HOME`, the log to `$XDG_STATE_HOME/mine-oh-belowed/log.txt` through one logging procedure that also prints to stderr. Directories (0102): `platform_directories` (`platform_paths.odin`) is the one place that reads the base directories from the environment, and every caller (configuration, log, saves, command socket, screenshots, texture edits) passes its fields to the pure path helpers, which keep the XDG rules (a relative value is ignored, `$HOME` fallbacks). On Linux the fields are `$XDG_CONFIG_HOME`, `$XDG_CONFIG_DIRS`, `$XDG_DATA_HOME`, `$XDG_STATE_HOME`, `$XDG_RUNTIME_DIR` and `$HOME`. On Windows `%APPDATA%` is the config home and the data home (configuration and saves roam), `%LOCALAPPDATA%` the state home (screenshots, texture edits; the log goes beside the executable, 0103), and there is no runtime directory, no system configuration directory and no home, so a missing variable means no directory. On Android (0114) there is no environment at all: `android_platform_directories` puts `config`, `share` and `state` under the activity's external files folder (the internal one when there is none), with no runtime directory and no home.

## Testing

Machine models (0055): a machine may name a MagicaVoxel `.vox` file in `data/models` through its `model` key; the file is read (`model_vox.odin`: the `SIZE`, `XYZI` and `RGBA` chunks of the first model, MagicaVoxel's z up mapped to the game's y up with handedness kept), meshed once per machine with greedy merging and a fixed shade per face direction (`model_mesh.odin`), uploaded once and drawn with `DrawMesh` scaled to the footprint and rotated with the entity (`render_models.odin`) in place of the box `draw_entity_cells` draws; a machine without a model keeps its box. Since 0056 every machine but belts and pipes has a model; a model takes the world light of one cell (above the footprint's centre, or in front of a 1 by 1 machine) through the material's diffuse colour, combined as the chunk shader does; palette indices 240 to 255 are emissive in their own mesh, lit when idle and full or pulsing while the machine works; an optional `<model>_part.vox` moves per the machine's `motion` (pump, spin, swing, bob, glow) as a function of tick, interpolation alpha, entity state and a per entity phase offset from its origin, never of the simulation; the bottleneck markers sit on the model top. Model files are a presentation hot reload category.

Pure procedures (noise to strata mapping, belt line arithmetic, recipe resolution, run length coding) get unit tests run with `odin test`. A determinism test runs the simulation twice from the same seed for a fixed number of ticks and compares state hashes. Rendering and input are verified by playing.

## Performance target

1080p at 60 frames per second on the couch machine (AMD Navi 10, Radeon RX 5700 class), 60 ticks per second with several thousand belts and hundreds of machines. Chunk generation must keep up with a sprinting player.

Measurement (0050): the headless factory benchmark (`benchmark_factory.odin`), run by `test_factory_benchmark` (sizes 1 and 4, `./build.sh bench` optimised with the size 4 budget of 8 milliseconds per tick) and by `--benchmark=<size>` (`doc/build.md`).

- The profile: `simulation_tick` and `tick_entities` take an optional `^Tick_Profile` (`tick_profile.odin`) and add each step's wall time (`time.tick_now`) to its `Tick_Section`: players (with the developer requests), unlocks, belts (with items falling off belt ends), loose items, power, drills, inserters, furnaces, assemblers (every crafting machine), labs, core sample drills, launch pads, fluids, lamps, outcrops and crates, venture, research, statistics (the clock, belt dead ends, holdings) and quests, and world (`tick_world`: block changes, water and light queues, leaf decay). Without a profile no clock is read, so the game pays nothing. The runner also times each whole tick for the average and the worst.
- The flat world: no generation and no streaming. `build_benchmark_world` makes every chunk column under the layout plus one chunk of margin: chunk y -1 and 0 stone with grass on top (world y 31), y 1 and 2 air, all under full sky light, registered like streamed columns with empty vein lists. The generator only serves the vein tables; veins are added where the manifest puts them, checked against each other but not against the generator's own veins, which the floor replaced. The landing pad and the player stand in opposite corners of the floor, outside the grid. Research costs 1000 times its packs (the world setting's multiplier), so the one technology the builder queues outlasts every run.
- The module grid: the layout is content. `data/blueprints/benchmark.sjson` lists module blueprints with a footprint, copies per size and veins; `benchmark_layout` gives each module its own column along x and its copies along z, 4 blocks apart, centred on the origin, and each copy runs its blueprint from its cell through `run_blueprint`. Every module has its own veins and power, so the cost grows linearly with the size and a module never starves another. A machine that shows no progress over the last minute of the warm up is reported idle (drills and furnaces by their output rate, inserters by an idle streak of a whole minute, crafting machines, labs, fluid machines and launch pads by their working state on some tick), and an idle machine fails the test and the command.
