# Build

## Host toolchain (couch machine, Bazzite)

- Odin release dev-2026-09 (nightly build a2fb372) extracted to `~/opt/odin-linux-amd64-nightly+2026-09-01`, with a stable symlink `~/opt/odin`. Source: the `odin-linux-amd64-dev-2026-09.tar.gz` asset of the GitHub release. Odin drives the linker through `clang`, which Homebrew provides (clang 23).
- raylib 6.0 comes from the repository's `shared` collection (work item 0085), not from `vendor:raylib`: `shared/raylib/` holds the Odin binding copied unchanged from the toolchain's `vendor/raylib/` (`raylib.odin`, `raymath.odin`, `rlgl/rlgl.odin`, `LICENSE`), our `platform.odin` (GLFW's `glfwGetPlatform`, `glfwGetCurrentContext` and `glfwGetWindowSize`, which the binding lacks) and `linux/libraylib.a`, a static raylib whose GLFW has both the Wayland and the X11 backend. The game imports `shared:raylib` and `shared:raylib/rlgl`: `shared` is the collection Odin reserves for packages outside its own (the toolchain's `shared/` directory, empty), and `build.sh` re-points it at the repository's `shared/` with `-collection:shared=<repository>/shared` on every command, so a bare `odin check src` no longer compiles: verify through `build.sh`. The copy exists because the binding names its library by a path next to itself, which no linker flag can swap; the toolchain stays untouched. `shared/raylib/README.md` has the build record (the raylib commit, the cmake flags, the compiler, the date, the archive's size) and how to redo the copy after an Odin upgrade. Beside it, `shared/fsw/` holds odin-fsw (work item 0111), the file watcher the data watch reads, vendored from https://github.com/thetarnav/odin-fsw with one patch for the field names of the Windows binding; it has no foreign library (its backends call the operating system through `core:sys/linux` and `core:sys/windows`), so the flake needs nothing for it. `shared/fsw/README.md` records the commit, the patch and how to update it; `~/opt/odin/odin check shared/fsw -no-entry-point -vet -strict-style`, plain and with `-target:windows_amd64`, checks it on its own.
- The archive links against the system `libdl`, `libpthread` and `libX11` as before. GLFW loads `libwayland-client`, `libwayland-cursor`, `libwayland-egl`, `libxkbcommon` and `libdecor` with dlopen at run time, so the executable's `ldd` shows no new library, and a machine without them falls back to X11. Windowed mode on Wayland draws its decorations through libdecor; Borderless and Fullscreen do not need it.
- `tools/build_raylib.sh` builds the archive: it clones the raylib tag `6.0` from https://github.com/raysan5/raylib (shallow) into `tmp/raylib-src/`, configures in `tmp/raylib-build/` with `-G "Unix Makefiles" -DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF -DBUILD_EXAMPLES=OFF -DPLATFORM=Desktop -DGLFW_BUILD_WAYLAND=ON -DGLFW_BUILD_X11=ON -DCMAKE_POSITION_INDEPENDENT_CODE=ON` (the generator is named because the user environment sets `CMAKE_GENERATOR=Ninja`, which the container lacks), builds, copies `libraylib.a` into `shared/raylib/linux/` and rewrites the README's build record. The host has no cmake and no development headers, so by default the script runs inside the distrobox `mine-oh-belowed-raylib` (image `registry.fedoraproject.org/fedora-toolbox:44`, created on first use with cmake, gcc, make, git and the Wayland, wayland-protocols, xkbcommon, libdecor, Mesa GL and X11 development packages; the home directory is shared, so the script calls itself inside it with `--host`). `tools/build_raylib.sh --host` runs the same steps on a machine that has the tools. The archive is committed (about 3.4 MB, rebuilt rarely), so a fresh checkout builds without cmake or a container.
- Bazzite is an immutable image with runtime libraries but without development symlinks: `libX11.so.6` exists, `libX11.so` does not, so linking fails with `cannot find -lX11`. The fix that avoids layering packages onto the image is a shim directory of symlinks to the runtime libraries, passed with `-extra-linker-flags:"-L<dir>"`. `build.sh` creates `tmp/linker-shims/` with `libX11.so -> /usr/lib64/libX11.so.6` and `libSDL3.so -> /usr/lib64/libSDL3.so.0`. Verified 2026-09-26 by compiling and linking a raylib hello world.
- SDL3: the host `libSDL3.so.0` is 3.4.16 (Fedora 44 package). `vendor:sdl3` links `system:SDL3`, so the same shim applies.

Commands (`build.sh` uses the toolchain at `${ODIN:-$HOME/opt/odin/odin}`):

```
./build.sh            # debug build (-debug) to build/mine-oh-belowed
./build.sh debug      # same as above
./build.sh release    # optimised build (-o:speed) to build/mine-oh-belowed
./build.sh check      # odin check src -vet -strict-style (with the collection)
./build.sh check-windows  # the same check for -target:windows_amd64, on any host
./build.sh test       # odin test src (with the collection)
./build.sh bench      # the factory benchmark test, optimised (-o:speed)
```

`./build.sh bench` runs only `test_factory_benchmark` (work item 0050) with `-o:speed`: it builds the benchmark factory at sizes 1 and 4, logs both tables and fails when size 4 averages 8 milliseconds per tick or more, half the 60 Hz budget. The plain `./build.sh test` (and CI) runs the same test unoptimised and only logs the numbers, since an unoptimised build's timings are not the release's.

Every command passes `-collection:shared=<repository>/shared`. Both build modes pass `-vet -strict-style`. Both build modes, `test` and `bench` pass `-extra-linker-flags:"-L<repository>/tmp/linker-shims"`, creating the shim directory first: Odin links a foreign library only when a reachable procedure uses it, and since work item 0129 a test reaches raylib (and with it X11), so the test link needs the shims like the build. `./build.sh check-windows` catches code that does not compile for Windows (work item 0102) without a Windows machine; the Nix build runs the same check, so CI guards it on every push. On a Windows host (Git Bash, see Windows below) `build.sh` makes no shims, writes `build/mine-oh-belowed.exe` and adds `-subsystem:windows` to `release`.

Command line (parsed with `core:flags` in Unix style, `--help` or `-h` prints the usage page and exits): `config` (prints the configuration files found and the effective values, no window), `--set=<key>=<value>`, `--load=<world>`, `--name=<world>`, `--unlock-all`, `--version`, `--input=sdl3` or `--input=raylib` (default: SDL3 with raylib fallback), `--seed=<unsigned 64 bit decimal>` (default a fixed constant so runs are reproducible), `--debug-terrain` (the fixed 8 by 2 by 8 chunk test terrain instead of the generated world, nothing streams), `--touch-overlay` (0115: the touch overlay on for the run whatever `settings.touch_overlay` says; on the desktop the mouse is its touch point while the left button is held, and the cursor stays free in the world, see `input.md`), `settings.font` and `settings.monospace_font` (0077) take family ids from `data/fonts/fonts.sjson`, an unknown id is refused like any other configuration error. `--watch-data=<off|presentation|all>` (0054, also the `settings.watch_data` key with `default` following developer mode) chooses what reloads while the game runs, and the developer flags of work item 0043: `--dev` (a Developer entry in the pause menu, see `ui.md`; the settings screen's Developer mode toggle does the same without launch options), `--chapter=<n>` (a new world with the quests before chapter n completed and their rewards delivered, plus chapter n's kit from `data/dev_kits.sjson`) and `--give=<item>:<count>` (repeatable, items into the inventory on the first tick, the rest into the drop capsule). `--chapter` and `--give` start a world like `--seed`; `--chapter` cannot be combined with `--load`. `--benchmark=<size>` (work item 0050, size 1 to 16) runs the headless factory benchmark instead of the game: no window and no controller, the shipped data, two simulated minutes of warm up and ten measured, then the table on stdout (milliseconds per tick per simulation system, the average and worst tick, the entity counts, the idle machines); it exits 1 when the factory cannot be built or a machine idles, and cannot be combined with `--load`, `--seed`, `--name`, `--chapter` or `--debug-terrain`. Quote its numbers from the release build: `./build.sh release && ./build/mine-oh-belowed --benchmark=16`. Size 16 takes about a quarter of a minute of wall time. Larger sizes are not offered (user, 2026-09-28): the cost per tick is close to linear in the size, so read them off size 16, and a size 64 build took minutes, since every placement rebuilds the belt, fluid and electric networks. A bad command line exits with status 2 (unknown items and chapters included), a failed start with status 1.

At run time the game looks for its data directory in this order: `$MINE_OH_BELOWED_DATA` if set, `./data`, `<executable directory>/data` (the unzipped Windows build, from any working directory), then `<executable directory>/../share/mine-oh-belowed/data` (the layout the Nix package installs). `build/mine-oh-belowed --version` prints the build stamp without opening a window: the version, the short commit (`+dirty` with uncommitted changes) and the UTC build time. The same stamp shows under the title screen's name, at the bottom of the pause menu and in the log's header line, so a bug report from the couch can name the build. `build.sh` passes commit and time as one `BUILD_INFO` define (one string with a space, since a define holding only digits arrives as a number), the play build installer passes the archived commit in `MINE_OH_BELOWED_COMMIT`, and the Nix build uses the flake's revision and last modified date.

## Steam library shortcut

`tools/install_play_build.sh` builds a commit (HEAD, or the commit given as its argument) in release mode from a `git archive` into its own directory `bin/play/builds/<install time>-<commit>/` with its own copy of `data/`, switches the `bin/play/current` link to it in one rename, and writes the launcher `bin/mine-oh-belowed`, which resolves the link at launch. The install never waits for the game (double buffering): a running game keeps its build directory and the next launch takes the newest; the two newest builds stay and older ones are removed unless a game still runs from them. The installed game never reads the working tree, so agents editing `src/` and `data/` cannot break a couch session. The couch always runs the latest build: run the script after every commit that lands on `main` (see `CLAUDE.md`). On a Wayland desktop the game opens a native Wayland window (0085): GLFW tries Wayland first, and with the high DPI flag the framebuffer has the panel's pixels under a fractional scale, so a laptop at 2880 by 1920 and 170 percent renders 2880 by 1920 while the window is 1694 by 1129 in the desktop's units. Under gamescope (the couch) the game may now be a Wayland client of gamescope. `MINE_OH_BELOWED_X11=1 bin/mine-oh-belowed` is the way back to X11 if Wayland or gamescope misbehaves: the launcher unsets `WAYLAND_DISPLAY` and sets `XDG_SESSION_TYPE=x11` for the game (unsetting alone is not enough, GLFW's Wayland connection falls back to the `wayland-0` socket). Under XWayland a scaled desktop hands the game the scaled screen and upscales it (0084); the launcher then runs the game inside gamescope when `MINE_OH_BELOWED_GAMESCOPE` holds gamescope's own arguments, which presents it at the panel's full size without changing a desktop setting: `MINE_OH_BELOWED_GAMESCOPE="-f -W 2880 -H 1920" bin/mine-oh-belowed`. With the native Wayland window the laptop no longer needs it; the variable stays as an option. Without gamescope on the path it prints one line to stderr and runs the game directly. The game logs `display: monitor W x H, window W x H, render W x H, scale X x Y, session <x11|xwayland|wayland>` after the window opens and after every display change; the session is the platform GLFW took (`glfwGetPlatform`), `xwayland` for X11 with `WAYLAND_DISPLAY` set, so the `MINE_OH_BELOWED_X11` route reports `x11`. On the couch at scale 1 the line's render equals its window. `tools/make_placeholder_models.py` (0055) writes the placeholder `.vox` machine models into `data/models` deterministically; rerun it after changing it and commit the files. `tools/moc` (Python, standard library only) sends one command line to the running game's command socket and prints the response; the game must run with `--dev` or the developer mode setting, protocol and commands in `commands.md`. `tools/add_steam_shortcut.py` adds or updates the "Mine oh Belowed" non-Steam shortcut in `~/.steam/steam/userdata/<user>/config/shortcuts.vdf`, pointing at that launcher. It parses the binary VDF, refuses to write unless the existing file round trips through its parser byte for byte, and keeps the other shortcuts untouched. Steam must be closed while it runs (check with `pgrep -x steam`), otherwise Steam overwrites the file on exit. `--dry-run` shows what would be written. Steam Input for the shortcut is disabled by hand in Steam's controller settings for the game, see `input.md`.

## Steam Deck

The Deck (work item 0076) runs the same play build, installed over SSH from the couch machine: `tools/install_play_build.sh --target deck@steamdeck:mine-oh-belowed/bin [commit]` builds here exactly as a local install does, then copies the build directory and the launcher with `rsync` through `ssh`, switches the remote `current` link in one rename and removes older remote builds by the same rule; nothing is installed locally. The path after the colon takes the place of `bin/` (absolute, or relative to the remote home; a leading `~/` is read as the home), so the example puts the launcher at `~/mine-oh-belowed/bin/mine-oh-belowed` and the builds under `~/mine-oh-belowed/bin/play/`. `--help` prints the usage. The remote side needs `bash`, `rsync`, `find` and `pgrep`. On the Deck, SSH needs a password for the `deck` user (`passwd` in Desktop Mode's Konsole) and `sudo systemctl enable --now sshd`; an SSH key (`ssh-copy-id deck@steamdeck`) saves typing it on every install. Verified here only against stub `ssh` and `rsync` commands acting on a local directory (2026-09-28), not against a Deck.

The shortcut: `tools/add_steam_shortcut.py` points the shortcut at `bin/mine-oh-belowed` beside its own `tools/` directory, so copy it to `~/mine-oh-belowed/tools/` on the Deck (`scp tools/add_steam_shortcut.py deck@steamdeck:mine-oh-belowed/tools/`, after `ssh deck@steamdeck mkdir -p mine-oh-belowed/tools`) and run it there in Desktop Mode with Steam closed, with `--user-id` set to the Deck's Steam user id (the directory under `~/.steam/steam/userdata/`). Then set the controller layout as `input.md` (Steam Deck) says.

The binary is built on the couch machine and links its libraries dynamically: `libSDL3.so.0`, `libX11.so.6`, `libm` and `libc` with glibc symbol versions up to `GLIBC_2.43` (`atan2f`, `asinf`, `acosf`, `sqrtf` in `libm`, read with `objdump -T` on 2026-09-28). The Deck must provide them; `ldd ~/mine-oh-belowed/bin/play/current/mine-oh-belowed` on the Deck names a missing library or version. Whether SteamOS ships a glibc that new and `libSDL3.so.0` was not checked from here.

The game applies a Steam Deck preset on its first start there, see `ui.md` (Steam Deck preset).

## Nix

`flake.nix` provides `packages.default` (the game), `devShells.default` (odin, raylib, glfw, sdl3) and `checks`. nixpkgs unstable ships odin dev-2026-09, raylib 6.0 and sdl3 3.4.16, matching the host. The game's raylib binding lives in the repository (0085), so the flake patches it in `postPatch` rather than the Odin package: `shared/raylib/raylib.odin` and `rlgl/rlgl.odin` link `system:raylib` instead of the committed archive, and `platform.odin` links `system:glfw`, since nixpkgs raylib is built against an external GLFW (a build input), which has both backends. libX11 stays a build input for the binding's import block. Both odin calls pass `-collection:shared=shared`. Nix is not installed on the couch machine, so the flake is validated by CI, not locally.

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and pull request on `ubuntu-latest`: enters the development shell and prints the Odin version, then runs `nix build`, which compiles the game with `-vet -strict-style`, runs `odin test src` and the Windows target check (`./build.sh check-windows`) inside the build. A second job, `windows`, builds the Windows executable, and a third, `android`, the APK, see below.

## Windows (GameNative on Android)

The user plays on an Android phone through GameNative, which runs Windows x86-64 programs under Wine and Box64 (work item 0102). The CI job `windows` on `windows-latest` builds and packages the game; it runs no tests (they assume Unix paths and sockets). Its steps, in `shell: bash` (Git Bash): checkout; the MSVC environment (`ilammy/msvc-dev-cmd@v1`, x64), which Odin links with; Odin from the release asset `odin-windows-amd64-dev-2026-09.zip` (https://github.com/odin-lang/Odin/releases/tag/dev-2026-09, SHA-256 checked), whose `dist/odin.exe` becomes `ODIN`; `SDL3-devel-3.4.16-VC.zip` (https://github.com/libsdl-org/SDL/releases/tag/release-3.4.16, SHA-256 checked), whose `lib/x64/SDL3.lib` is copied into the toolchain's `vendor/sdl3/` (the binding imports `SDL3.lib` next to itself, which Odin's release does not ship); `MINE_OH_BELOWED_COMMIT=<short commit> ./build.sh release` (the commit passed in, so a line ending difference in the checkout never marks the build dirty); then the package `dist/mine-oh-belowed/` with `mine-oh-belowed.exe`, `SDL3.dll`, `data/` and a `README.txt`, uploaded with `actions/upload-artifact@v7` as `mine-oh-belowed-windows-x64-<short commit>`. raylib comes from the committed `shared/raylib/windows/raylib.lib` (raylib's own MSVC release build, see `shared/raylib/README.md`); nothing of SDL is committed. The link uses the dynamic C runtime, which raylib's release library was built for (`/DEFAULTLIB:MSVCRT` inside it; the binding drops Odin's `libcmt`), so nothing may pull the static one: `core:c/libc` and `core:sys/posix` do (`libucrt.lib`, by their import alone, whether a procedure is used or not). `raylib_log.odin` declares its formatter against `ucrt.lib` instead of importing `core:c/libc`, and the files that need `core:sys/posix` carry `#+build !windows` on their first line (`logging_posix.odin`, `command_socket_posix.odin` and its test), each with a `#+build windows` counterpart holding the Windows side. A `when` block is not enough, since the import stays. `test_static_runtime_imports_stay_out_of_windows` (`platform_paths_test.odin`) fails when a file in `src/` imports either package without a tag that excludes Windows.

Fetching the artifact: open the workflow run on GitHub (Actions, the run of the commit) and download it under Artifacts, or `gh run download <run id> --name mine-oh-belowed-windows-x64-<short commit>` (`gh run list --workflow ci.yml` lists the runs). Either way it arrives as a zip holding the `mine-oh-belowed/` folder. Copy the folder to the phone, and in GameNative add a custom game pointed at `mine-oh-belowed/mine-oh-belowed.exe`. The executable finds `data/` beside itself; `SDL3.dll` must stay beside it. The release build opens no console window, so its stderr goes nowhere; the log file has every line.

Where files land under Wine (`platform_paths.odin`): `log.txt` sits beside `mine-oh-belowed.exe` (work item 0103: GameNative's Wine container lives in the app's private data, which the phone's file manager cannot reach, while the unzipped folder can be read), `%LOCALAPPDATA%\mine-oh-belowed\` holds `screenshots\`, `texture_edits.sjson` and `data_edits\` (the state home), `%APPDATA%\mine-oh-belowed\` holds `config.sjson`, `config.d\` and `saves\` (the config and data homes, so they roam on real Windows). In a Wine prefix these are `C:\users\<user>\AppData\Local` and `C:\users\<user>\AppData\Roaming`. `MINE_OH_BELOWED_SAVES` and `paths.saves` still win for saves; a leading `~/` in `paths.saves` is not expanded on Windows.

Smoke test here before the phone: `tools/wine_smoke_test.sh [path/to/mine-oh-belowed.exe]` runs the executable under Proton 11's Wine from Steam's library (`~/.steam/steam/steamapps/common/Proton 11.0/files/bin/wine`) in the prefix `tmp/wineprefix`, without a display: `--version` first, then a start that loads the data and ends at the window, and it prints the `log.txt` written beside the executable it ran. The default executable is the newest under `tmp/artifact`, where `gh run download <run id> --dir tmp/artifact` puts an artifact. This is how the ICU abort was found: `core:time/timezone`'s Windows path asks ICU (`icu.dll`, `ucal_getDefaultTimeZone`) for the local zone's name, which Wine does not implement and aborts on, so `local_zone_windows.odin` takes the offset from `GetTimeZoneInformation` instead (`local_zone.odin`).

What the Windows build lacks: the command socket (developer mode leaves it out silently, 0108; `tools/moc` stays Linux only), the redirect of stderr into the log and the raw back trace on SIGSEGV or SIGILL (an assertion or panic of the main thread still logs its back trace), and the couch launcher and play build installer (`tools/install_play_build.sh` is Linux only). Untested here: the build only runs on the phone; this machine checks the Windows target with `./build.sh check-windows`.

## Android toolchain

The native Android app (work item 0113, the game itself follows in 0114) is built with Odin's android subtarget and packaged with `odin bundle android`. The versions are the GitHub ubuntu-24.04 runner's, which ships them at `ANDROID_HOME=/usr/local/lib/android/sdk` with JDK 17: NDK 27.3.13750724, build-tools 34.0.0, platforms android-34.

- `tools/android_env.sh`, sourced by the build scripts and by a shell (`. tools/android_env.sh`), exports `ANDROID_NDK_VERSION`, `ANDROID_BUILD_TOOLS_VERSION` (34.0.0), `ANDROID_PLATFORM_VERSION` (34), `ANDROID_API_LEVEL=28` (the `-minimum-os-version`, Android 9; raylib's archive is built for the same level), `ODIN_ANDROID_SDK` (`$ODIN_ANDROID_SDK`, else `$ANDROID_HOME`, else `~/opt/android/sdk`) and `ODIN_ANDROID_NDK` (`$ODIN_ANDROID_SDK/ndk/<version>`), and puts the build-tools and platform-tools on the `PATH`. The same file serves the CI runner.
- `tools/android_toolchain.sh` installs the SDK under `${ODIN_ANDROID_SDK:-~/opt/android/sdk}`: the command line tools `commandlinetools-linux-15859902_latest.zip` (SHA-256 from https://developer.android.com/studio#command-line-tools-only, checked before unpacking, recorded in the script; the page no longer lists the 13114758 first planned) into `cmdline-tools/latest/`, the licenses, then `platform-tools`, `build-tools;34.0.0`, `platforms;android-34` and `ndk;27.3.13750724` through `sdkmanager`. Re-running skips what is installed. `sdkmanager`, `apksigner` and `keytool` need Java, which Bazzite lacks, so by default the script runs inside the distrobox `mine-oh-belowed-android` (image `registry.fedoraproject.org/fedora-toolbox:44`, created on first use with `java-25-openjdk-headless cmake gcc gcc-c++ make git unzip`; Fedora 44 has no JDK 21 package). `--host` runs the steps on a machine that has Java, curl and unzip. The home directory is shared, so the SDK lands under `~/opt` either way. The installed SDK takes 2.4 GB, mostly the NDK.
- `tools/build_raylib.sh --android` (run `tools/android_toolchain.sh` first, then builds in the same container; `--android --host` builds on this machine) clones the raylib tag as for the desktop, rewrites `precision mediump float;` to `precision highp float;` in the two OpenGL ES3 default shaders of `src/rlgl.h` (`rlLoadShaderDefault`, work item 0126; the script fails unless it finds exactly those two lines), bounds the key queue append in the key branch of `AndroidInputCallback` (`src/platforms/rcore_android.c`, work item 0133: `if (CORE.Input.Keyboard.keyPressedQueueCount < MAX_KEY_PRESSED_QUEUE)` around the store and the increment, the form `rcore_desktop_glfw.c` uses; the script fails unless it rewrites exactly one unbounded append), configures in `tmp/raylib-build-android/` with `-G "Unix Makefiles" -DCMAKE_TOOLCHAIN_FILE=$ODIN_ANDROID_NDK/build/cmake/android.toolchain.cmake -DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-28 -DPLATFORM=Android -DOPENGL_VERSION="ES 3.0" -DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF -DBUILD_EXAMPLES=OFF`, copies the archive through the NDK's `llvm-strip --strip-debug` (the NDK compiles with `-g` even in Release: 12.3 MB before, 2.6 MB after) to `shared/raylib/android/libraylib.a` and rewrites the Android build record in `shared/raylib/README.md`. ES 3.0 rather than raylib's default ES 2.0: the game's shaders (`data/shaders/`, `#version 330`) hash with `uint` arithmetic, which GLSL ES 1.00 lacks and GLSL ES 3.00 has. The precision patch: mediump is 16 bit on Mali, so without it the held block, models and particles (everything raylib's batch and default shader draw) jitter by a fraction of a block as the camera moves; the game's own shaders already get highp from `shader_source_for_gles`. The key queue patch: raylib 6.0 appends every key down to the 16 entry `keyPressedQueue` without checking its count, and the IME committing a long word delivers every character's key down in one poll, so the system keyboard (0133) would write past the queue; with the patch the keys past the sixteenth in a frame are dropped. The cmake warning "You are overriding the suggested GRAPHICS=GRAPHICS_API_OPENGL_ES2 with GRAPHICS_API_OPENGL_ES3!" is expected. The archive holds `rcore_android.c` (`android_main`, `GetAndroidApp`) and its own copy of `android_native_app_glue.c` (`ANativeActivity_onCreate`), no GLFW. The binding links it with `system:log`, `system:android`, `system:EGL`, `system:GLESv3` and `system:OpenSLES` (`shared/raylib/README.md`).
- Entry point (checked in Odin dev-2026-09, nightly a2fb372): `odin build -target:linux_arm64 -subtarget:android` refuses the executable build mode ("Unsupported -build-mode for -subtarget:android", only shared, object, assembly and llvm-ir). In shared mode the runtime exports a C `main` that returns 0 at once (`base/runtime/entry_unix.odin`), and although the link passes `-Wl,-init,'_odin_entry_point'` the library has no INIT entry (`llvm-readelf -d`), so the runtime startup never runs on its own. raylib's `android_main` calls `main(1, {"raylib", NULL})` on the native activity's thread. So the program builds with `-build-mode:shared -no-entry-point -extra-linker-flags:-Wl,--wrap=main`: the linker sends raylib's call to `main` to `__wrap_main`, which the program exports as `@(export, link_name = "__wrap_main") proc "c" (argc: i32, argv: [^]cstring) -> i32` and which sets `runtime.args__ = argv[:argc]`, then `context = runtime.default_context()`, calls `runtime._startup_runtime()` (the first time only, see below), then the program, and returns 0. The runtime starts once per process and is never cleaned up (work item 0116): after Back or Home the activity ends but Android keeps the process, the next launch runs `android_main` again on a new thread in the same process, and a second `_startup_runtime` runs every `@(init)` procedure again, where `core:image`'s `register` asserts on the PNG loader the first run registered (a `SIGTRAP` on every other launch). Android ends the process without notice, so `_cleanup_runtime` would have nothing to do that matters: the `@(fini)` procedures among the dependencies free the temporary allocator and `os.args` and restore a terminal the app does not have. The link name `main` itself is reserved in Odin. Odin compiles the NDK's `android_native_app_glue.c` into its own archive and adds `-u ANativeActivity_onCreate`, so the symbol is exported without a flag of ours; either copy of the glue satisfies it. `argv` from raylib is `{"raylib", NULL}` on `android_main`'s stack, not the process's, and it feeds `os.args` only. The environment does not come from it: the build links bionic (no `-no-crt`), so `os.get_env` is bionic's `getenv` (`core/os/env_linux.odin`, the branch after `when ODIN_NO_CRT`) and reads the environment Android gives the app, which has none of the XDG variables; the game must not expect one there.
- The final link passes `-Wl,--wrap=fopen` and `-Wl,--no-undefined` beside `--wrap=main` (added in work item 0114 after the phone test of the hello world). raylib's `rcore_android.c` reads files through `__wrap_fopen`, which opens a read from the APK's assets first and calls `__real_fopen` otherwise; the wrap must be applied at the link that makes the final library (its own comment says so, a static archive cannot carry it), and without it `__real_fopen` stays undefined. A shared library links with undefined symbols without complaint, so the hello APK linked and then failed on the phone at `dlopen` with "cannot locate symbol __real_fopen referenced by libmain.so". `--no-undefined` turns any such symbol into a link error here instead. With both, `llvm-nm -D --undefined-only libmain.so` lists `fopen` as an ordinary import from libc and no `__real_fopen`.
- `odin bundle android <dir>` runs `aapt package` on `<dir>/AndroidManifest.xml` (with `<dir>/res` and `<dir>/assets` when present), `zipalign` and `apksigner` from the smallest `build-tools/<n>` at or above the API level (34.0.0) against `platforms/android-<n>/android.jar`, and writes `test.apk` in the working directory. A quirk: it hands aapt `<dir>/lib` as a directory argument, and aapt adds that directory's contents at the APK root, so the library must sit at `<dir>/lib/lib/arm64-v8a/libmain.so` to land at `lib/arm64-v8a/libmain.so`. An `android:label` given as a literal string does not show in `aapt dump badging`; a `@string` resource from `<dir>/res/values/strings.xml` does.
- `tools/android/debug.keystore` (alias `androiddebugkey`, store and key password `android`, RSA 2048, 10000 days, `CN=Android Debug, O=Android, C=US`, the conventions of Android's own debug key, made with `keytool -genkeypair` in the container) is committed on purpose: Android installs an update over an installed app only when the new APK carries the same signature, so the couch and CI must sign alike, and a debug key guards nothing.
- Hello world, not committed (`tmp/android-hello/`, commands in work item 0113): the build above, `llvm-nm -D` on `libmain.so` shows `__wrap_main`, `android_main` and `ANativeActivity_onCreate` and `llvm-objdump -d` shows `android_main` calling `__wrap_main`; the bundle, then `aapt dump badging <apk>` names the package, SDK levels, `uses-gl-es: '0x30000'` and `native-code: 'arm64-v8a'`, and `apksigner verify --print-certs <apk>` passes (v3 scheme). Run all Odin and SDK steps inside the container on the couch: `apksigner` needs its Java, and the NDK runs there as well as on the host.

## Android app

The game as a native Android app (work item 0114), built with the toolchain above. `build.sh` has two modes for it:

- `./build.sh check-android`: `odin check src -target:linux_arm64 -subtarget:android -vet -strict-style` with `tools/android_env.sh` sourced. It runs on the host (`odin check` needs the NDK, not Java) and takes neither `-minimum-os-version` (`odin check` refuses the flag) nor the shared build mode (the check accepts the default).
- `./build.sh android`: the signed APK `build/android/mine-oh-belowed.apk` (not `bin/`, which is the installed play build's). `apksigner` needs Java, which the couch has only in the distrobox `mine-oh-belowed-android`, so without `java` on the `PATH` the script re-runs itself there (`distrobox enter mine-oh-belowed-android -- ./build.sh android`, as `tools/build_raylib.sh` does); the home directory is shared, so the output lands in the same tree. The build: `odin build src -target:linux_arm64 -subtarget:android -minimum-os-version:28 -build-mode:shared -no-entry-point -o:speed -vet -strict-style` with the `BUILD_INFO` define into `build/android/bundle/lib/lib/arm64-v8a/libmain.so` (the nested `lib/lib` is the bundle quirk above); `data/` copied to `build/android/bundle/assets/data/` and its list (`find data -type f | sort`) to `assets/data_files.txt`; `tools/android/res/` to the bundle's `res/`; `tools/android/AndroidManifest.xml` rendered with `@VERSION_CODE@` (the commit count, `git rev-list --count HEAD`, so each newer build installs over the last) and `@VERSION_NAME@` (the build info, commit and build time); `odin bundle android bundle` with the committed keystore, run in `build/android/`; `test.apk` renamed. The script prints the APK's path, size, version code and build info.
- The link flags: `-Wl,--no-undefined`, `-Wl,--wrap=main`, `-Wl,--wrap=fopen` (above), and `-Wl,--wrap=<name>` for six glibc functions Odin's core library links on Linux that Android 9's libc (bionic) lacks: `__errno_location` (bionic calls it `__errno`; `core:c/libc`), `pthread_setcancelstate` and `pthread_setcanceltype` (bionic has no thread cancellation; `core:thread` enables it on every thread), `backtrace`, `backtrace_symbols` and `backtrace_symbols_fd` (bionic has them from API level 33; `core:debug/trace` and the crash handler in `logging_posix.odin`). `src/android_libc/`, a leaf package the Android build imports, exports each as `__wrap_<name>`: `__errno_location` calls `__errno`, the cancellation calls succeed and do nothing, the back trace calls return no frames. The crash signal handlers are not installed on Android at all: bionic's `sigaction` struct puts `sa_flags` first while `core:sys/posix` follows glibc with the handler first, so the call installed SIG_DFL with stray flags (logcat, 2026-09-30); Android's own crash reporter writes the native trace to logcat (`adb logcat -s DEBUG`). Every directory the game makes goes through `make_directory_path` (`platform_paths.odin`, work item 0117), a `mkdir -p` that tries the directory, makes a missing parent the same way and tries again, so it never touches a directory above the first missing one: `os.make_directory_all` opens `/` to walk an absolute path and the SELinux policy refuses an app that read (`Permission_Denied` for the saves, the settings, the log and the command socket on version code 211). A test fails on any `os.make_directory_all` in a non test source file. An export under the plain name does not work: the same name is declared as a foreign procedure elsewhere in the program (`core:c/libc`, `logging_posix.odin`) and the compiler emits only one of the two, not always the same one. `core:thread` and `core:sys/posix` also link `system:pthread`, which the NDK does not have (bionic keeps the pthread functions in libc), so an empty archive `build/android/linker-shims/libpthread.a` stands in. The one undefined symbol left is `memfd_create`, a weak reference from the NDK's compiler runtime, which the loader allows.
- The entry point is `src/main_android.odin` (`#+build linux:android`), the exported `__wrap_main` described above, which starts the runtime once per process, never cleans it up, and calls the game's `main` on every launch. A second `main` in one process runs without the global initialisers, so `main` assigns or resets every mutable global before it reads it (`global_string_table`, the log and console state in `logging.odin` and `logging_posix.odin`, the last touch position and the pending Shift of the typed text in `input_raylib.odin`, which `start_input_backend` clears), and `apply_ui_theme` (called from `run_game` in `loop.odin`) assigns the `UI_*` colours of `ui_widgets.odin` before any drawing; the previous run's allocations stay, one run per relaunch. Quit is different: it returns from `main` while the activity is alive, and raylib resets its own state for the next launch only when the activity is being destroyed (`ClosePlatform` in `rcore_android.c` checks `destroyRequested`), so a later launch in the same process would start on stale raylib state. So after `main` returns, `__wrap_main` ends the process with `os.exit(0)` when the app's `destroyRequested` is 0; a system destroyed activity returns normally and keeps the process. `src/platform_android.odin` declares what the game needs beyond the binding: `GetAndroidApp` from raylib's archive with the leading fields of `android_app` (up to `destroyRequested`) and `ANativeActivity` (checked against the NDK 27.3.13750724 headers), `__android_log_write` and `glGetString`.
- Haptics (work item 0122): the raylib backend plays the frame's `Haptic_Request` on the phone's vibrator (`src/haptics_android.odin`, `#+build linux:android`; `haptics_desktop.odin` holds the no-op elsewhere). At start `start_vibrator` calls `activity.getSystemService("vibrator")`, keeps the service and the `android.os.VibrationEffect` class as global references with the method ids of `vibrate(VibrationEffect)`, `cancel` and the static `createOneShot(long, int)` (`hasVibrator` and `hasAmplitudeControl` are called once at start), and logs `haptics: vibrator found, amplitude control yes` (or what failed). A frame with a strength above 0 plays `createOneShot(HAPTIC_RUMBLE_MILLISECONDS, amplitude)`, amplitude 1 to 255 from `vibration_amplitude` (`input_actions.odin`), or `DEFAULT_AMPLITUDE` (-1) without amplitude control; the first frame at 0 after one calls `cancel()`. The JNI slice: a `JNIEnv` and a `JavaVM` point to a pointer to a table of function pointers, and `jni_function` reads a slot by the indices in `src/jni_indices.odin`, counted from the members of `struct JNINativeInterface` and `struct JNIInvokeInterface` in the NDK's `jni.h` (the numbers are in the work item and `jni_indices_test.odin`). The calls use the `Call...MethodA` variants (arguments as a `jvalue` array), so no call from Odin goes through C varargs. Every call checks `ExceptionCheck` and a nil result; a thrown exception is cleared, and either failure is logged once and turns the vibrator off for the run. The game thread attaches to the VM before every use, since raylib's `GetCurrentMonitor` (`rcore_android.c`, read by `current_monitor_size`) detaches the thread when it returns; attaching an attached thread only returns its `JNIEnv`. `stop_vibrator` at the end of `run_game` cancels, frees the references and detaches, since the thread may end with the activity while the process lives (entry point above). The manifest asks for `android.permission.VIBRATE`, a normal permission Android grants at install.
- The keyboard (work item 0133): a text field shows the phone's IME through `ANativeActivity_showSoftInput` and hides it with `ANativeActivity_hideSoftInput` (`src/system_keyboard_android.odin`, flags 0 both: an explicit request, and a hide however it was shown), declared against `system:android` (`native_activity.h`, NDK 27.3.13750724). raylib's Android backend queues key codes only (`AndroidInputCallback`'s key branch in `rcore_android.c`), so `GetCharPressed` returns nothing on the phone. `read_raylib_typed_text` (`input_raylib.odin`) instead drains `GetKeyPressed` and turns the keys into text with `character_for_key`: letters, digits, space and the punctuation keys raylib's `mapKeycode` table maps (minus, equals, left and right bracket, backslash, semicolon, apostrophe, grave, comma, period, slash), with Shift giving the upper case letter or the US layout's shifted character (`!` on 1, `_` on minus, `|` on backslash, `~` on grave); every other key types nothing. The IME types an upper case letter as Shift pressed, the letter pressed and both released, so a Shift in the queue applies to the next character only, also when that character arrives in a later frame; a frame without any key after the Shift drops it. On every platform the queue adds its keys to the frame's keys down (`add_pressed_keys`), since a key that goes down and up within one poll (the IME's, a virtual keyboard's on the desktop) never reads as down otherwise: `AKEYCODE_DEL` maps to `KEY_BACKSPACE` and `AKEYCODE_ENTER` to `KEY_ENTER` in `mapKeycode`, so the field's Enter works; each queued Backspace becomes `TEXT_BACKSPACE` in its place in the typed text, so every Backspace in a frame deletes one character (`advance_keyboard` then ignores the Backspace key's edge). raylib's queue holds `MAX_KEY_PRESSED_QUEUE` (16) keys a frame; the Android archive bounds its append (Android toolchain, above), so keys past the sixteenth in a frame are dropped.
- Files on the phone: Android starts the game with no environment (see the entry point above), so `platform_directories` takes the activity's paths (`android_platform_directories`, `platform_paths.odin`): the external files folder `Android/data/io.github.tubbles.mineohbelowed/files/`, which a USB connection and file managers with access to it reach, else the internal one. Under it `state/mine-oh-belowed/log.txt` is the log (plus `screenshots/`, `texture_edits.sjson` and `data_edits/`, the data edits overlay of 0129, whose copies win over the app's data files), `share/mine-oh-belowed/saves/` the saves and `config/mine-oh-belowed/` the configuration (`config.sjson`, `config.d/`) and the touch layouts the editor saved (`touch_overlay.sjson`, 0121). Every log line also goes to logcat with the tag `mine-oh-belowed` (priority info).
- Data: `core:os` reads the real file system only, and the asset manager cannot list a directory, so at start `resolve_data_directory` copies every file of `assets/data_files.txt` from the APK (read through `rl.LoadFileData`, which raylib's fopen wrapper serves from the assets) to the internal folder (`/data/user/0/io.github.tubbles.mineohbelowed/files/data/`), then writes the build info to `data/.build_stamp`. A start whose stamp matches the build skips the copy; any other start removes the old copy first, so a file a newer build dropped does not linger. A read or write failure logs `error: cannot copy <file> from the app: ...` and the start ends as with a missing data directory.
- Shaders: `load_shader_pair` reads the files and loads them with `rl.LoadShaderFromMemory` on every platform; on Android `shader_source_for_gles` first turns the `#version 330` line into `#version 300 es` with `precision highp float;` and `precision highp int;` (32 bit integer hashes). The four shipped shaders, rewritten that way, pass `glslangValidator` (installed in the container with `sudo dnf install glslang`).
- Display and input: raylib opens the window at the screen's size (`InitWindow(0, 0, ...)`); the window mode and resolution settings do nothing, vsync and the frame rate cap apply. The window platform reads `android`. SDL is not in the Android build (`input_sdl3.odin` is `#+build !linux:android`, `input_sdl3_android.odin` stands in), so input is raylib's: a Bluetooth or USB gamepad works at once, the first touch is the pointer, and in a world the touch overlay (0115, on by default there) is a virtual gamepad (`doc/input.md`). Every GLFW call is under `when ODIN_PLATFORM_SUBTARGET != .Android`; `shared/raylib/platform.odin` declares none on Android, so a stray one fails the check.
- CI: the job `android` on `ubuntu-latest` checks out with `fetch-depth: 0` (the commit count), downloads Odin's `odin-linux-amd64-dev-2026-09.tar.gz` (https://github.com/odin-lang/Odin/releases/tag/dev-2026-09, SHA-256 checked), prints the runner's Android tools and Java, and runs `MINE_OH_BELOWED_COMMIT=<short commit> ./build.sh check-android` and `./build.sh android` with the runner's `ANDROID_HOME`, which `tools/android_env.sh` picks up. The APK is uploaded as `mine-oh-belowed-android-arm64-<short commit>`.
- Installing: download the artifact from the workflow run (Actions, the run of the commit, Artifacts) or with `gh run download <run id> --name mine-oh-belowed-android-arm64-<short commit>`; it arrives as a zip holding `mine-oh-belowed.apk`. Copy the APK to the phone, open it, allow installs from that source when Android asks, and install. A build from the couch or from CI installs over the other, since both sign with the committed key and the version code only grows. With USB debugging on, `adb install -r build/android/mine-oh-belowed.apk` and `adb logcat -s mine-oh-belowed raylib` work from the container (`platform-tools` is on the `PATH` after sourcing `tools/android_env.sh`).
- What the Android build lacks: SDL3 and with it the Steam Controller features (trackpads, gyro, grip sense; the magnetometer's haptics play on the phone's vibrator instead), the command socket's client (`tools/moc` runs on Linux; the game still opens its socket under the state folder in developer mode where the file system allows one), the couch launcher and play build installer, crash back traces, the local time zone (`timezone.region_load("local")` finds no database, so the title screen's dates are UTC), and a launcher icon. Movement on a touch screen waits for the overlay (work item 0115).
