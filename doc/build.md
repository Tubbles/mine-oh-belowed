# Build

How to build, check, test and ship the game: the host toolchain, `build.sh`, the command line, the play build on the couch and the Deck, Nix, CI and the Windows build. The Android app has its own file, [android.md](android.md).

- Every build and check goes through `build.sh`, which passes the `shared` collection; a bare `odin check src` does not compile.
- `build/` holds build output; `bin/` is the installed play build's.
- After every commit on `main` that changes `src/` or `data/`, `tools/install_play_build.sh` installs the couch's build ([CLAUDE.md](../CLAUDE.md)).

## Host toolchain

The couch machine runs Bazzite.

| Tool | Where | Notes |
|---|---|---|
| Odin dev-2026-11a (nightly 9a69916) | `~/opt/odin-linux-amd64-nightly+2026-11-03`, linked as `~/opt/odin` | The `odin-linux-amd64-dev-2026-11a.tar.gz` release asset. `build.sh` uses `${ODIN:-$HOME/opt/odin/odin}` |
| clang 23 | Homebrew | Odin drives the linker through it |
| SDL3 3.4.16 | `/usr/lib64/libSDL3.so.0` (Fedora 44) | `vendor:sdl3` links `system:SDL3` |
| raylib 6.2 | `shared/raylib/` | Built from source, committed (below). Pinned, the reason beside `raylib_tag` in `tools/build_raylib.sh` |
| Blender 5.2 LTS | Flatpak `org.blender.Blender` with host file access | Only to regenerate models ([Models](#models)) |

### The shared collection

- `shared` is the collection Odin reserves for packages outside its own; `build.sh` points it at the repository's `shared/` with `-collection:shared=<repository>/shared` on every command. The toolchain stays untouched.
- `shared/raylib/` holds the toolchain's binding (`raylib.odin`, `raymath.odin`, `rlgl/rlgl.odin`, `LICENSE`), copied with one patch: `raylib.odin` and `rlgl/rlgl.odin` carry a `when` branch importing the Android archive (0113), which must be put back when the copy is redone after a raylib upgrade; an Odin upgrade alone keeps the copy ([shared/raylib/README.md](../shared/raylib/README.md) has the redo steps). Beside it: our `platform.odin` (`glfwGetPlatform`, `glfwGetCurrentContext`, `glfwGetWindowSize`, `glfwGetProcAddress`, which the binding lacks, left out on Android, and rlgl's `rlBindFramebuffer`, which the binding lacks too, on every platform, 0348) and the libraries. The copy exists because the binding names its library by a path next to itself, which no linker flag can swap.
- `shared/raylib/README.md` records each build (raylib commit, cmake flags, compiler, date, size) and how to redo the copy after a raylib upgrade.
- `shared/fsw/` is odin-fsw, the file watcher, vendored with patches for the Windows backend; `shared/fsw/README.md` records the commit, the patches and how to update. It has no foreign library. Check it alone with `~/opt/odin/odin check shared/fsw -no-entry-point -vet -strict-style`, plain and with `-target:windows_amd64`.

### raylib archive

- `linux/libraylib.a` (about 3.4 MB, committed, so a fresh checkout needs no cmake) has GLFW with both the Wayland and the X11 backend. It links the system `libdl`, `libpthread` and `libX11`; GLFW opens `libwayland-client`, `libwayland-cursor`, `libwayland-egl`, `libxkbcommon` and `libdecor` with dlopen at run time, so `ldd` shows no Wayland library and a machine without them falls back to X11. Windowed decorations on Wayland come through libdecor, and GLFW has fallback decorations without it.
- `tools/build_raylib.sh` clones raylib tag `6.2` from https://github.com/raysan5/raylib (shallow) into `tmp/raylib-src/`, configures in `tmp/raylib-build/`, builds, copies the archive into `shared/raylib/linux/` and rewrites the README's build record. Flags:

```
-G "Unix Makefiles" -DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF -DBUILD_EXAMPLES=OFF
-DPLATFORM=Desktop -DGLFW_BUILD_WAYLAND=ON -DGLFW_BUILD_X11=ON -DCMAKE_POSITION_INDEPENDENT_CODE=ON
```

- The generator is named because the user environment sets `CMAKE_GENERATOR=Ninja`, which the container lacks.
- The host has no cmake and no development headers, so by default the script runs itself with `--host` inside the distrobox `mine-oh-belowed-raylib` (image `registry.fedoraproject.org/fedora-toolbox:44`, created on first use with cmake, gcc, make, git and the Wayland, wayland-protocols, xkbcommon, libdecor, Mesa GL and X11 development packages; the home directory is shared). `tools/build_raylib.sh --host` runs the steps on a machine that has the tools.
- `windows/raylib.lib` is raylib's own MSVC release library and `android/libraylib.a` the Android build ([android.md](android.md)); both records are in `shared/raylib/README.md`.

### Linker shims

Gotcha: Bazzite ships runtime libraries without the development symlinks (`libX11.so.6` exists, `libX11.so` does not), so linking fails with `cannot find -lX11`.

- `build.sh` makes `tmp/linker-shims/` with `libX11.so -> /usr/lib64/libX11.so.6` and `libSDL3.so -> /usr/lib64/libSDL3.so.0` and passes `-extra-linker-flags:"-L<repository>/tmp/linker-shims"` to both builds, `test` and `bench`. No package is layered onto the image.
- `test` needs them too: Odin links a foreign library only when a reachable procedure uses it, and tests reach raylib (and with it X11).

## build.sh

```
./build.sh                # debug build (-debug) to build/mine-oh-belowed
./build.sh debug          # the same
./build.sh release        # optimised build (-o:speed) to build/mine-oh-belowed
./build.sh check          # odin check src -vet -strict-style
./build.sh check-windows  # the same check for -target:windows_amd64, on any host
./build.sh check-android  # the same check for Android arm64 (android.md)
./build.sh test [tier] [files or tests] [flags]  # the tests of a tier, all by default (Test tiers)
./build.sh nightly        # the report tests and test_factory_benchmark, optimised, 03:00 to 06:00 only
./build.sh bench          # test_factory_benchmark only, optimised, 03:00 to 06:00 only
./build.sh frame-profile [view ...]  # the frame table under gamescope, 03:00 to 06:00 only (Frame profile)
./build.sh android        # the signed APK (android.md)
./build.sh model-check [machine]  # the debug build, then --model-check (all by default)
```

- Every command passes the collection; both builds pass `-vet -strict-style` and the `BUILD_INFO` define (below).
- `test` builds the test binary `build/mine-oh-belowed-tests` with `odin build src -all-packages -build-mode:test` (what `odin test` builds), passes the flags given on (a define, `-o:speed`) and runs the tier's tests ([Test tiers](#test-tiers)); `unit` and `quick` add `-o:none` unless a `-o:` flag is given. `-all-packages`: plain `odin test src` runs only the game package's tests, not those of the packages under `src/` it imports (`src/platform/` and the others, [code_map.md](code_map.md), Packages). The checks need nothing extra: `odin check src` checks every package the game imports, tests included, for the target it checks.
- `check-windows` catches code that does not compile for Windows without a Windows machine; on every push the `windows` job's native build guards the same target ([CI](#ci)).
- `bench` runs `test_factory_benchmark` with `-o:speed`: size 1 on the field world (0179), its table logged, a failure when it averages 8 ms per tick or more, half the 60 Hz budget. Plain `test` (and CI) runs it unoptimised and only logs. `bench`, `nightly` and `frame-profile` ([Frame profile](#frame-profile)) are heavy benchmarks: they refuse to start (exit 2) outside 03:00 to 06:00 Europe/Stockholm, and hold `~/benchmark.lock` (its pid, start, expected minutes, directory, project, command and session) while they run, waiting for another live lock and removing a stale one, so no two benchmarks of any project share the machine. A stale lock is first renamed to a name of the guard's own and its pid read again there, so of two guards that found it only one removes it, and a lock that turns out live goes back.
- On a Windows host (Git Bash) `build.sh` makes no shims, writes `build/mine-oh-belowed.exe` and adds `-subsystem:windows` to `release`.

## Test tiers

The suite in tiers (0316), so an item iterates on tests that take seconds to a minute and runs the whole suite rarely. `tools/test_tiers.py` lists, selects and judges. Its tests are `python3 tools/test_tiers_test.py`.

- The tiers: `all` (every test, what CI runs, the default of bare `./build.sh test`), `unit` (every test not marked slow, the one to iterate on), `slow` (the tests marked slow), `quick` (the tests of the files or the tests named: a test file gives its tests, `src/<name>.odin` the tests of `src/<name>_test.odin`, both without their report tests, which a notice names, `test_<name>` or `game.test_<name>` that one test of any tier, a path that is not an `.odin` file is skipped with a notice. Paths that select no test, the files of a diff that touches no tested source, pass with the line `quick: no tests selected` and build nothing, while no selector or an unknown test name exits 2) and `nightly` (`./build.sh nightly`: the report tests and `test_factory_benchmark`, with `-o:speed` and `-define:ODIN_TEST_THREADS=1`, so no two of them run side by side and skew each other's timings, a benchmark under the rules of `bench` above).
- The mark: `@(test) // slow` on the attribute line marks a test that takes 1 s or more in a run of `all`. Anything else after `@(test)` is refused. The first marking (0316) was 237 tests holding 95% of the summed test time, which left `unit` at about 22 s of running on 8 threads.
- The runner selects by name only, so the lister reads `src/**/*.odin` (skipping a file whose `#+build` lines exclude the Linux desktop) and passes the tier's names as the binary's `-tests:` arguments, 200 names each. `all` passes none. `ODIN_TEST_NAMES` is refused: a test is named through `quick`.
- The run's checks: the binary is built with `ODIN_TEST_LOG_STATE_CHANGES`, and its output goes through the filter, which times each test from its state change lines. An unmarked test taking 10 s or more fails the run, one of 3 s or more is named in a notice, a name the build lacks fails it, and a finished run of `all` fails when it ran a test the lister does not list or missed one it does (a `#+build` form or an attribute the lister does not know).
- `build/test_times.tsv` holds the last run's tests, their seconds and tiers, slowest first: a new test there at 1 s or more gets the mark.
- A report test (a measurement that only logs, like `test_report_the_relief_cost`) sits indented inside a file level `when NAME {` block, with `NAME :: #config(NAME, false)` declared in its package. It runs in `nightly`, which passes every such define, or alone with `./build.sh test quick <test> -o:speed -define:NAME=true`. Any other enclosing `when` is refused, so no test drops out silently. A define that only changes what a running test does (`TEXTURE_PREVIEW`, `FIRE_FLICKER_DUMP`) is no gate.
- Every tier pays the compile of the test binary, about 23 s on Odin dev-2026-11a against 75 s on dev-2026-09 (0316). `./build.sh check` reports a compile error in about 4 s. `unit` and `quick` build with `-o:none` (0318): the compile is about a third of the default's and the run about 1.5 times slower. `all` and `slow` keep the default, their run outweighing the compile. `build/test_times.tsv` after a `unit` or `quick` run holds unoptimised times, so the slow mark is still read off a run of `all`.
- The tests' field sessions stage through the process's chunk cache (`stage_cached_field_set`, `src/simulation_field_chunk_cache_test.odin`, 0318): a chunk is generated once per process and copied into every later session and load (again only while another test is still generating it, or past the cache's capacity). A test whose subject is the generation, or with a hand-built planet, calls `generate_field_chunk`.

## Frame profile

The frame table (0342, [architecture.md](architecture.md), The frame profile): what a frame costs on the couch's GPU in fixed views, from one command in the night window, without the TV. `./build.sh frame-profile [view ...]` takes the benchmark guard (40 minutes) and the release build, then runs `tools/frame_profile.py`, which runs only under that guard: outside `--check` it exits 2 unless `~/benchmark.lock` names its parent shell. `nightly` does not run it, since the views need gamescope and about 25 minutes of the GPU.

- The sandbox: the game runs under a nested `gamescope --backend headless -W 1920 -H 1080` (no `DISPLAY`, the real `XDG_RUNTIME_DIR` for gamescope's socket, the run's `XDG_CONFIG_HOME`, so none of the user's gamescope scripts), its output in `<output>/gamescope.log`. The game gets its own runtime directory, `$XDG_RUNTIME_DIR/mine-oh-belowed-profile-<pid>` (0700, removed at the end; a path under `tmp/` would pass the socket path's 108 byte limit), so its socket cannot meet a play session's, GLFW finds no `wayland-0` and the game reaches no PulseAudio. It runs on gamescope's Xwayland (`WAYLAND_DISPLAY` unset, `XDG_SESSION_TYPE=x11`), with `XDG_CONFIG_HOME`, `XDG_CONFIG_DIRS`, `XDG_STATE_HOME` and `XDG_DATA_HOME` under `<output>/run/` and `MINE_OH_BELOWED_SAVES` unset: a fresh world, default settings, the user's saves untouched.
- The game: `--dev --input=none --name=frame_profile` (with `--water-model=<model>` for a view's model), vsync off, no frame rate cap, volume 0, no autosave. It runs free, so the GPU's clock is its own choice, logged and never forced. The start is refused (exit 1) when the log's `gl:` line names `llvmpipe` or `softpipe` or its last `display:` line is not `session x11`.
- The world: `pause`, `tick` the arrival's ticks (`arrival_ticks + arrival_settle_ticks` of `data/game.sjson`), `resume`, `seat stand`, `camera first`, `weather clear`.
- The views: `tools/frame_profile_views.sjson`, each at every distance (`view_distance`, 512 and 1024 m) and in every viewport count (one and two), at noon in clear weather. A run frames the view (`teleport`, `look` or `look at`; the second viewport's player through `as`), waits with `profile settle`, frames again (the player dropped onto the ground), takes the screenshot `<view>_<n>vp_<d>m`, settles again and samples 600 frames (`profile sample`, a view's `frames` for its own) while a thread reads the AMD card's `pp_dpm_sclk` (the line marked `*`) and `gpu_busy_percent` from sysfs every 0.1 s. The order adds one player only: the views in one viewport, `viewport add`, the views in two, the factory built on the pod's frame (its machines, then its `cables` as `cable` lines between them, 0384, so its rows before 0384 do not compare with those after), the factory in two, `viewport remove`, the factory in one, the large factory in one (`factory_large`, 0347, below), then the views that name a `water_model` (0379), each model's in a fresh game started under it, one viewport then two. The pod's frame leans 15 degrees, so the factory's pad floats at the views file's corner, clear of the ground under it, and its players fly (`fly on`) at a stand the script works out from the frame and the placed machines' cells: the nearest point back along the views file's look at the pad's top centre that keeps every corner of the pad and the machines inside the screen above the hotbar at the 70 degree field of view, outside the pad and beyond the tool's reach, so the held foundation shows no ghost. A line answered `error` fails its run and the next goes on; a render other than 1920 by 1080 fails the run.
- The large factory (0347): the views file's `factory_large` builds `copies` of the factory beside it under `pause` once the factory stands, `copies[0]` against the frame's right (along it the leaning pad sinks under the ground) and `copies[1]` along its forward, the factory the first, each pad `FACTORY_COPY_GAP_CELLS` (2) cells from the next. A copy holds the factory's pad and only its machines the views file names (the ones the field session draws), with their items, and no cable. A copy's refused line is counted and skipped, and the notes column says `placed <m> of <M> machines, <f> of <F> foundations`: 621 machines and 36036 foundations for the shipped 11 by 7. A count outside 1 to 32 on either axis stops the script with exit 2 and the line. The player flies at the middle of the copies one row over the pads, less `back_metres` along the frame's forward plus `up_metres` along its up, looking at that middle. The game answers a line a frame, so the copies' 36480 lines take minutes before the first run.
- The waits: `profile settle 3600` and `profile sample` wait for their frames at the frame time just measured (5 socket round trips, since the game reads the socket once a frame), twice over and at least 900 s, the other lines 900 s. A line still unanswered at the end of its wait, or a game that ended, ends that run (`unsettled` for a settle, `failed` with the reason otherwise), and the game is stopped as at the end and started afresh (a new world under the next run's water model, prepared again) for the runs after it, so one slow view never costs the night its other runs. A start for a run of another water model is made the same way and is not counted in the head's restarts. Only a start that fails or a cleanup that leaves a process stops the whole run, with the partial table written. The exit is 1 for a failed run, a stop or a failed cleanup, not for an unsettled run.
- The end, also on SIGTERM, SIGHUP or an error: gamescope's process group gets SIGTERM, then SIGKILL; then the game itself, found by the run's runtime directory in its environment, gets SIGKILL, and the runtime directory is removed only once no such process is left (otherwise a line names the pid and the script exits 1, as it does when gamescope outlives its SIGKILL). gamescope is started with `PR_SET_PDEATHSIG`, so a script that is killed outright takes it down.
- The outputs, in `tmp/frame_profile/<UTC time>/` (`--output`): `table.md`, each run's `query profile` answer as `<view>_<n>vp_<d>m.txt`, the game's `log.txt`, `screenshots/` and `gamescope.log`. The table's head names the date, the build stamp, the `gl:` line, the budget and the restarts (`log.txt` holds each start); the main table gives per run the frames a second, the GPU's mean and p99, the CPU at 60 Hz, the work's p99, the tick's mean and worst, the frame at 60 Hz and its headroom, the clock (mean and maximum MHz), the busy percent, the verdict (`pass` or `fail` at 512 m, `report` at 1024 m, `unsettled` or `unsettled: <reason>`, `failed: <reason>`) and the notes; then the CPU's and the GPU's section means and the counters' means, a row per run.
- `python3 tools/frame_profile.py --check [view ...]` runs every view once at 512 m in its viewport counts, capped at 30 frames a second with 30 frames sampled, to check the framing and the setup; its table is headed `check, not a measurement`. It is no benchmark and needs no window, but loads the GPU lightly for a few minutes, so it refuses (exit 2) while a benchmark holds the lock. Other flags: `--frames`, `--views`, `--binary`. Its tests, no game: `python3 tools/frame_profile_test.py`.

## Source checks

Python 3 scripts without dependencies, run by hand from anywhere; none is part of `build.sh` or CI.

- `python3 tools/check_docs.py` checks the Markdown docs against the repository: relative links, backticked paths, file names and identifiers. Exit 1 lists each finding.
- `python3 tools/check_dead_code.py` lists the definitions of `src/**/*.odin` (the game package and the packages under it) that nothing references, and those outside the test files that only `*_test.odin` files reference. It scans the declarations at file level, including those inside file level `when` and `foreign` blocks, and counts whole word uses in the code of every `.odin` file under `src/` (comments and strings stripped, the definition's own body and every definition line of the same name left out) plus `build.sh`, `tools/` and `data/shaders/`. `@(test)`, `@(export)`, `@(init)` and `@(fini)` definitions are exempt; its allow lists hold what no attribute covers (`main`) and the test seams, each with its reason. Exit 1 when it finds anything.
- `python3 tools/code_graph.py` prints the file dependency graph of `src/` grouped into clusters by file name prefix, each package under `src/` a cluster of its own, whose names resolve only in the package itself and in the packages it imports: the cluster edges with reference counts, the clusters that reference each other, the strongly connected components with the files outside the largest, and the files of the largest with the fewest edges into it. `--files` adds each file's edges, `--json` dumps the graph, `--tests` includes the test files; these exit 0. `--check doc/code_map.md` compares the cluster edges that the map's allowed dependency table does not allow with the map's record of them (the "Reaches into" line of each cluster): it exits 1 when an edge is new or above its recorded count, 2 when the map cannot be read, 0 otherwise, and marks the edges that fell below their record. A refactor that lowers a count lowers the record by hand ([code_map.md](code_map.md)).

## Models

The OBJ machine models (0204, [presentation.md](presentation.md), Machine models) are built by Python scripts that run inside Blender.

- `tools/blender <script> [argument ...]` runs a script headless (`--background --factory-startup --python-exit-code 1`, the arguments after `--`): the host's `blender` when it is on the PATH, else `flatpak run org.blender.Blender`. The Flatpak sees the home directory but not `/tmp`, so a script it runs lives under the repository.
- `tools/blender tools/make_models.py [model ...]` writes `data/models/<model>.obj` and `.mtl` for the named machines, all of them without names; an unknown name exits 1 listing the known ones. A model in `COLLISIONS` (0230) also gets `data/models/<model>.collision.sjson` from its script's `collision(b)` ("wrote data/models/<model>.collision.sjson (N volumes)", written to `<path>.tmp` and renamed over the path); every other model it builds loses a stale collision file ("removed ...").
- The committed OBJ and MTL files are the product: the build, the tests and CI never run Blender, only a regeneration does. The same script in the same Blender version writes the same bytes (the scene is cleared per machine, the booleans use the exact solver).
- The export: `bpy.ops.wm.obj_export` with forward `NEGATIVE_Z` and up `Y` (Blender's front +X and Z up become the game's +x and y up), scale 1, modifiers applied, triangulated, normals on, no UVs, colours or groups beyond the object names, materials on, paths stripped.
- Layout: `tools/models/palette.py` (the materials of `DESIGN.md`'s palette, byte colours and the glow flag), `tools/models/kit.py` (the frame, `box`, `cylinder`, `cone`, `cut`, `join`, `join_part`, `material`, `export`, `wedge`, `ring`, `pipe`, `hatch`, `rib_row`, `strip`, `opening`, `model_random`, `expect_footprint`), `tools/models/records.py` (the machine records, below), `tools/models/machines/` (one script per machine, `MACHINES` in its `__init__.py`, each `build(machine)` taking its record), `tools/models/collision.py` (0230: the collision volumes, plain Python without `bpy`). Each machine ends as one object `body` and, with a moving part, one `part`.
- Collision volumes (0230, [content.md](content.md), Models): a script may add `collision(b)` beside `build`, `b` a `collision.Collision`, listing `b.box(minimum, maximum, shell=0.0, axis="Z")`, `b.cylinder(centre, start, end, radius, axis="Z", shell=0.0, sector=None)` and `b.cone(centre, start, end, radius_start, radius_end, axis="Z", shell=0.0, sector=None)` in the kit's Blender frame and cells (`centre` as `kit.cylinder` takes it; a sector two angles in degrees about the axis from its first cyclic perpendicular, about Z from +X towards +Y); each call refuses what it can check alone and more than 64 volumes, naming the model and the volume. `COLLISIONS` in `tools/models/machines/__init__.py` maps a model to its `collision`; the pod's is the first. The file is in the game's frame (Blender (x, y, z) to (x, z, -y), a sector's angles turned with it, a Blender Y volume's swapped since its axis turns over), written deterministically (six decimals, trailing zeros stripped), so a regeneration writes the same bytes. `python3 tools/models/collision_test.py` checks the conversion, the text read back through `tools/sjson.py`, the lab's helpers (`contains`, `bounds`, `wire_lines`) and the refusals.

### The workbench

The model workbench (0207) checks a model in the game's own mesher and motion code and renders it with the game's renderer, so an agent writes the script and reads the result without directing a run of the game.

- The records: `tools/sjson.py` reads SJSON as the game does (an implicit root object, bare or quoted keys, `=` or `:`, optional commas, both comment forms, JSON values; a duplicate key is an error naming the line and column); `tools/make_placeholder_textures.py` reads `data/` through it too. `tools/models/records.py` reads `data/machines.sjson` into frozen dataclasses (footprint, motion with its pivot and an iris's hinge, ports, open cells, a pod's fixtures with their rotated sizes, light) and maps them into the kit's Blender frame: `pivot`, `hinge` (0231), `port(machine, name)` and `port_face` (the face's centre and normal), `open_cell_box`, `fixture_box` (0198), `footprint_box`. A port is named `<direction>_<fluid>` (`<direction>` without a fluid), a repeat taking `_2`, `_3` in file order. `tools/make_models.py` hands each script the first record naming its model (`machine_for_model`), and `kit.join_part(objects, machine, pivot, hinge)` refuses a part on a motion that moves none, a spin or swing without its pivot, an iris without its pivot and its hinge (0231), and a pivot or a hinge that is not the record's. `python3 tools/models/records_test.py` checks both modules against golden values of the shipped records.
- `--model-check=<machine|all>` (`model_check.odin`, `loop_model_check.odin`) runs no window. `all` takes every machine with a model; the OBJ models and the arm are checked, a voxel model is skipped and counted (named explicitly it is one `load` problem). The checks: `load`, the loader's refusal (0204's fit); `cap`, the sanity caps that catch a runaway mesh (a body 9600 and a part 600 triangles, a pod's body 76800 (0221, `model_body_triangles_cap`), three times the budgets the reference models were made under, 0275) and the limit of 8 materials, counted as distinct colour and glow pairs, and only within them the rest; `sweep`, the part posed by `motion_part_transforms` at 16 phases (index / 16), and at fraction 1 too for a slide or an iris (0231, whose phase is an open fraction that rests at 1), every blade of an iris, crossing the body (edges through triangle interiors, so contact and coplanar faces pass); `footprint`, the posed part's bounds through `model_footprint_problem`; `open_cells`, a body or part triangle at rest inside an open cell box shrunk by the footprint tolerance, and as well inside a pod's fixture box (0198, the detail naming `fixture box N` instead of `open cells box N`), so no pod geometry stands where a fixture's model stands; `collision` (0230), a collision volume inside an open cells box or a fixture box shrunk by the tolerance, sampled on a lattice of 1/8 cell (`model_collision_problems`, the detail `volume N enters open cells box M near (x, y, z)`; the volumes' bounds against the footprint are the loader's, so a file out of bounds stops the registry's load before the check); `sweep` also, for a pod, each fixture's part over its motion, every blade of an iris, open fraction 0 to 1 in 17 steps, placed at its fixture box, against the pod's body (0221, `pod_fixture_part_problems`, the detail naming `fixture N (<machine>)` and for an iris ` blade K`), the body filtered to the part's swept bounds first, and against the pod's open cells boxes as `open_cells` (0231, `fixture N (<machine>) blade K at open fraction F: M part triangles inside open cells box B near (x, y, z)`); `arm`, the upper arm, forearm, gripper and both fingers at 16 cycle fractions on a frame of `foundation_pitch_millimetres` crossing the base. - The data directory is the first of: `$MINE_OH_BELOWED_DATA` (wins even when missing, so a typo fails loudly), `./data`, `<executable directory>/data` (the unzipped Windows build), `<executable directory>/../share/mine-oh-belowed/data` (the Nix package). Android copies its own ([android.md](android.md)).
- The build stamp is the version, the short commit (`+dirty` with uncommitted changes) and the UTC build time. It shows under the title, at the bottom of the pause menu, in the log's header line and on `--version`, so a bug report names the build.
- `build.sh` passes commit and time as one `BUILD_INFO` define, a string with a space, since a define holding only digits arrives as a number. `MINE_OH_BELOWED_COMMIT` overrides the commit (the play build installer builds from a `git archive` without `.git`; CI passes it so a line ending difference never marks the build dirty). The Nix build uses the flake's revision and last modified date.

## Play build

`tools/install_play_build.sh [commit]` builds a commit (default HEAD) in release mode from a `git archive` into `bin/play/builds/<install time>-<commit>/` with its own copy of `data/`, switches `bin/play/current` to it in one rename, and writes the launcher `bin/mine-oh-belowed`, which resolves the link at launch.

- The install never waits for the game: a running game keeps its build directory and the next launch takes the newest. The two newest builds stay; older ones go unless a game still runs from them.
- The installed game never reads the working tree, so edits to `src/` and `data/` cannot break a couch session.
- The launcher unsets `SDL_GAMECONTROLLER_IGNORE_DEVICES` and sets `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD=0` ([input.md](input.md), Steam Input beside the game).

### Display

- GLFW tries Wayland first, so a Wayland desktop gets a native window, and under gamescope (the couch) the game can be a Wayland client of gamescope. With the high DPI flag a laptop at 2880 by 1920 and 170 percent renders 2880 by 1920 while the window is 1694 by 1129 in the desktop's units.
- `MINE_OH_BELOWED_X11=1 bin/mine-oh-belowed` is the way back to X11: the launcher unsets `WAYLAND_DISPLAY` and sets `XDG_SESSION_TYPE=x11`. Unsetting alone is not enough, since GLFW's Wayland connection falls back to the `wayland-0` socket.
- Under XWayland a scaled desktop hands the game the scaled screen and upscales it. `MINE_OH_BELOWED_GAMESCOPE` holds gamescope's own arguments and runs the game inside gamescope at the panel's full size: `MINE_OH_BELOWED_GAMESCOPE="-f -W 2880 -H 1920" bin/mine-oh-belowed`. Without gamescope on the path it prints one line to stderr and runs the game directly.
- The game logs `display: monitor W x H, window W x H, render W x H, scale X x Y, session <x11|xwayland|wayland>` after the window opens and after every display change, and again on a later frame whose render size differs from the last line's (0342). The second line is needed because raylib changes the render size only when GLFW reports the framebuffer's new size, in the event poll of the next frame, so a window that grows (borderless at start) logged the size from before. The session is the platform GLFW took (`glfwGetPlatform`); `xwayland` is X11 with `WAYLAND_DISPLAY` set, so the `MINE_OH_BELOWED_X11` route reports `x11`. On the couch at scale 1 render equals window.

## Steam shortcut

- `tools/add_steam_shortcut.py` adds or updates the "Mine oh Belowed" non-Steam shortcut in `~/.steam/steam/userdata/<user>/config/shortcuts.vdf`, pointing at `bin/mine-oh-belowed` beside its own `tools/` directory. `--user-id` picks the Steam user, `--dry-run` shows what would be written.
- It parses the binary VDF and refuses to write unless the existing file round trips through its parser byte for byte; other shortcuts stay untouched.
- Steam must be closed while it runs (`pgrep -x steam`), or Steam overwrites the file on exit.
- Steam Input for the shortcut is disabled by hand ([input.md](input.md)).

## The water tech demo

The play build's mode that judges the water models (0291; the items after it add the models, the look, the tools and the light): a world with no save, no quests and no fall, the player standing at the spring or in the pod with the demo kit, the HUD and the field controls as they are.

- The mode: the title's Tech demos button opens the list of the tech demos (0302), whose Water opens the Tech demo screen ([ui.md](ui.md), Other screens): the water model (teleport pressure or bodies, the stored world setting `water_model`), the planet radius (the default planet's presets) and the start point (the pod, or the spring whose water falls furthest to the sea, `planet_spring_start`), then Start. `start_tech_demo_session` builds a new world of `DEFAULT_WORLD_SEED` on the default planet at the chosen radius with saving off (the saves directory is "" and not found, so nothing is written), clears the arrival so nothing falls, silences the quests (`silence_quests`: none active, no Mission Control line, nothing completed, so no reward lands), empties the inventory and gives the kit of `tech_demo_items` in `data/game.sjson` (each kind named on the toolbar in order, 0278: the iron pickaxe, a stack of dirt, torches; validated like the starter kit), stands the player at the spring (`field_spring_spawn`: one sample towards the home from the spring's source sample, the generated surface when the spring has no air) or on the pod's cabin floor, and sets `Field_Content.tech_demo`, under which any digging tool digs every material that has an item (bedrock stays) with no credit and a place raises ground without spending anything ([architecture.md](architecture.md), Sessions). F4's world statistics overlay shows from the start with its water line ([developer_tools.md](developer_tools.md), Diagnostics pages); F4 or the Developer screen turn it off. Pause in the world offers Quit to title. The demo is one machine's: it is not hosted on the LAN and cannot be joined, since a joiner's field content would lack the demo flag.
- `--tech-demo` alone opens the title with the Tech demos list and the Tech demo screen pushed (`push_tech_demo_menu`). `core:flags` takes a value for a string flag, so `parse_command_line` rewrites the bare flag to `--tech-demo=menu`, which typed by hand means the same. `--tech-demo=<model>,<radius>,<start>` starts the demo world before the window opens, so a problem shows without a display: the model `teleport` or `bodies`, the radius a preset of the default planet in metres (checked against `data/planets.sjson` once the data is loaded, exit 2 otherwise), the start `home` or `spring`; an empty word keeps its default (`teleport`, the planet's default radius, `spring`), so `--tech-demo=,16000` is the 16 km world at the spring. `--seed` picks the seed; `--dev`, `--set`, `--input`, `--unlock-all`, `--touch-overlay` and `--watch-data` combine; the flags that start, load, host, join or preview a world, `--chapter`, `--give` and the workbench are refused with it.
- The way in is the play build ([Play build](#play-build)) and its "Mine oh Belowed" shortcut ([Steam shortcut](#steam-shortcut)). The launcher passes its arguments on, so LaunchOptions of `--tech-demo` open the list with the water screen, and `--tech-demo=<model>,<radius>,<start>` opens the demo world.

## Steam Deck

The Deck runs the same play build, installed over SSH from the couch machine (0076).

- `tools/install_play_build.sh --target deck@steamdeck:mine-oh-belowed/bin [commit]` builds here exactly as a local install, copies the build directory and the launcher with `rsync` over `ssh`, switches the remote `current` link in one rename and removes older remote builds by the same rule; nothing installs locally. `--help` prints the usage.
- The path after the colon takes the place of `bin/` (absolute, or relative to the remote home; a leading `~/` means the home), so the example puts the launcher at `~/mine-oh-belowed/bin/mine-oh-belowed`.
- The remote side needs `bash`, `rsync`, `find` and `pgrep`. On the Deck: a password for `deck` (`passwd` in Desktop Mode's Konsole), `sudo systemctl enable --now sshd`, and optionally `ssh-copy-id deck@steamdeck`.
- The remote install is tested only against stub `ssh` and `rsync` acting on a local directory, not against a Deck.
- The shortcut: `ssh deck@steamdeck mkdir -p mine-oh-belowed/tools`, `scp tools/add_steam_shortcut.py deck@steamdeck:mine-oh-belowed/tools/`, then run it there in Desktop Mode with Steam closed and `--user-id` set to the Deck's Steam user id (the directory under `~/.steam/steam/userdata/`). The controller layout: [input.md](input.md), Steam Deck.
- The binary links `libSDL3.so.0`, `libX11.so.6`, `libm` and `libc` dynamically, with glibc symbol versions up to `GLIBC_2.43` (`atan2f`, `asinf`, `acosf`, `sqrtf`; `objdump -T`). `ldd ~/mine-oh-belowed/bin/play/current/mine-oh-belowed` on the Deck names a missing library or version. Whether SteamOS ships a glibc that new and `libSDL3.so.0` is unchecked.
- The game applies a Steam Deck preset on its first start there ([ui.md](ui.md), Steam Deck preset).

## Nix

- `flake.nix` provides `packages.default` (the game), `devShells.default` (odin, raylib, glfw, sdl3, libX11) and `checks`.
- The flake patches the binding in `postPatch`: `shared/raylib/raylib.odin` and `rlgl/rlgl.odin` link `system:raylib` instead of the committed archive, and `platform.odin` links `system:glfw`, since nixpkgs raylib is built against an external GLFW with both backends. libX11 stays a build input for the binding's import block. A renamed foreign import line breaks `substituteInPlace` loudly.
- nixpkgs' raylib (6.2 since 2026-10-15) links against the committed binding, so a newer one there is the signal for the next raylib upgrade.
- The build runs `odin build` with `-o:speed -vet -strict-style`, then `odin test src -all-packages`, both with `-collection:shared=shared`, and installs the data under `share/mine-oh-belowed/`. It runs no Windows check: the `windows` job builds that target natively on every push.
- Nix is not installed on the couch machine; CI validates the flake.

## CI

`.github/workflows/ci.yml` runs on every push and pull request:

| Job | Runner | Does |
|---|---|---|
| `nix` | `ubuntu-latest` | `nix develop --command odin version`, then `nix build` (build, the whole suite (the `all` tier)) |
| `windows` | `windows-latest` | The Windows package (below), no tests: they assume Unix paths and sockets |
| `android` | `ubuntu-latest` | `check-android` and the APK ([android.md](android.md)) |

The toolchains float, and a pin needs a reason beside it (user, 2026-11-07, 0315):

- Odin: the `nix` job takes nixpkgs-unstable's (dev-2026-10 on 2026-11-07), which may lag the latest release, so the code compiles and runs on both. A range over a map's value by its key (`for item in table[key]`) crashes that release when the key is missing (0311's test on CI, dev-2026-11 is fine): look the key up with its `ok` first. The `windows` and `android` jobs take the latest release through `tools/ci_download_odin.sh <platform>`, the `odin-<platform>-` asset checked against the SHA-256 digest GitHub records for it (the releases publish no checksum file). No match or two fail the step and list the assets.
- SDL3 (`windows`): the highest `release-3.x.y` of libsdl-org/SDL by version that is neither draft nor prerelease, not the newest by date, since SDL 2 releases share the repository and an older 3.x line can publish after a newer one. Its `SDL3-devel-<version>-VC.zip` is checked against GitHub's digest.
- The pins left, each with its reason where it is set: raylib 6.2 (`tools/build_raylib.sh`), the Android target SDK 34 (`tools/android_env.sh`) and the Android command line tools zip (`tools/android_toolchain.sh`).
- nixpkgs follows `nixos-unstable` without a lock, and the GitHub actions float within their major tags (`actions/checkout@v7`).

## Windows (GameNative on Android)

The user plays on an Android phone through GameNative, which runs the Windows x86-64 build under Wine and Box64 (0102).

- The `windows` job, in Git Bash: checkout; the MSVC environment (`ilammy/msvc-dev-cmd@v1`, x64), which Odin links with; the latest Odin release and the latest SDL3 3.x `SDL3-devel-<version>-VC.zip`, both checked against GitHub's SHA-256 digest ([CI](#ci)); `SDL3.lib` copied into the toolchain's `vendor/sdl3/`, where the binding imports it next to itself, over the one Odin's release bundles (the job's SDL3 is the latest SDL release, independent of Odin's, so the import library matches the `SDL3.dll` packaged beside the game); `MINE_OH_BELOWED_COMMIT=<short commit> ./build.sh release`.
- Odin links with radlink, its default Windows linker since dev-2026-10 (Odin #7739).
- The package `dist/mine-oh-belowed/` holds `mine-oh-belowed.exe`, `SDL3.dll`, `data/` and a `README.txt`, uploaded as `mine-oh-belowed-windows-x64-<short commit>`. raylib comes from the committed `shared/raylib/windows/raylib.lib`; nothing of SDL is committed.

### The C runtime

Gotcha: raylib's release library is built for the dynamic C runtime (`/DEFAULTLIB:MSVCRT` inside it; the binding drops Odin's `libcmt`), so nothing may pull the static one.

- `core:c/libc` and `core:sys/posix` pull `libucrt.lib` by their import alone, whether a procedure is used or not. A `when` block does not help, since the import stays.
- `raylib_log.odin` declares its formatter against `ucrt.lib` instead of importing `core:c/libc`.
- Files that need `core:sys/posix` carry `#+build !windows` on their first line, each with a `#+build windows` counterpart ([architecture.md](architecture.md), Platforms).
- `test_static_runtime_imports_stay_out_of_windows` (`platform_paths_test.odin`) fails when a file in `src/` or a package directory under it imports either package without a tag that excludes Windows.

### Fetching and installing

- Download the artifact from the workflow run (Actions, the run of the commit, Artifacts), or `gh run download <run id> --name mine-oh-belowed-windows-x64-<short commit>` (`gh run list --workflow ci.yml` lists runs). It arrives as a zip holding `mine-oh-belowed/`.
- Copy the folder to the phone and add a custom game in GameNative pointed at `mine-oh-belowed/mine-oh-belowed.exe`. `data/` and `SDL3.dll` stay beside it.
- The release build opens no console window, so its stderr goes nowhere; `log.txt` has every line.

| File | Under Wine |
|---|---|
| `log.txt` | Beside `mine-oh-belowed.exe`, since GameNative's Wine container lives in the app's private data the phone's file manager cannot reach |
| `screenshots\`, `texture_edits.sjson`, `data_edits\` | `%LOCALAPPDATA%\mine-oh-belowed\` (`C:\users\<user>\AppData\Local`) |
| `config.sjson`, `config.d\`, `saves\` | `%APPDATA%\mine-oh-belowed\` (`C:\users\<user>\AppData\Roaming`), so they roam on real Windows |

- `MINE_OH_BELOWED_SAVES` and `paths.saves` still win for saves; a leading `~/` in `paths.saves` is not expanded on Windows.

### Smoke test

- `tools/wine_smoke_test.sh [path/to/mine-oh-belowed.exe]` runs the executable under Proton 11's Wine from Steam's library (`~/.steam/steam/steamapps/common/Proton 11.0/files/bin/wine`) in the prefix `tmp/wineprefix`, without a display: `--version`, then a start that loads the data and ends at the window, then it prints the `log.txt` beside the executable.
- The default executable is the newest under `tmp/artifact`, where `gh run download <run id> --dir tmp/artifact` puts an artifact.
- Gotcha: `core:time/timezone`'s Windows path asks ICU (`icu.dll`, `ucal_getDefaultTimeZone`) for the local zone, which Wine does not implement and aborts on, so `local_zone_windows.odin` takes the offset from `GetTimeZoneInformation`.

### What the Windows build lacks

- The command socket: `COMMAND_SOCKET_SUPPORTED` is false, so developer mode opens none and logs nothing about it (0108); `tools/moc` is Linux only, and `--input=none`, whose only input is the socket, exits 2 (0341).
- The stderr redirect into the log and the raw back trace on SIGSEGV or SIGILL; an assertion or panic of the main thread still logs its back trace.
- The couch launcher and the play build installer (Linux only).
- Testing here: the build runs only on the phone; this machine checks the target with `./build.sh check-windows`.
