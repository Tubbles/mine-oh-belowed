# Build

## Host toolchain (couch machine, Bazzite)

- Odin release dev-2026-09 (nightly build a2fb372) extracted to `~/opt/odin-linux-amd64-nightly+2026-09-01`, with a stable symlink `~/opt/odin`. Source: the `odin-linux-amd64-dev-2026-09.tar.gz` asset of the GitHub release. Odin drives the linker through `clang`, which Homebrew provides (clang 23).
- raylib 6.0 comes from the repository's `shared` collection (work item 0085), not from `vendor:raylib`: `shared/raylib/` holds the Odin binding copied unchanged from the toolchain's `vendor/raylib/` (`raylib.odin`, `raymath.odin`, `rlgl/rlgl.odin`, `LICENSE`), our `platform.odin` (GLFW's `glfwGetPlatform`, `glfwGetCurrentContext` and `glfwGetWindowSize`, which the binding lacks) and `linux/libraylib.a`, a static raylib whose GLFW has both the Wayland and the X11 backend. The game imports `shared:raylib` and `shared:raylib/rlgl`: `shared` is the collection Odin reserves for packages outside its own (the toolchain's `shared/` directory, empty), and `build.sh` re-points it at the repository's `shared/` with `-collection:shared=<repository>/shared` on every command, so a bare `odin check src` no longer compiles: verify through `build.sh`. The copy exists because the binding names its library by a path next to itself, which no linker flag can swap; the toolchain stays untouched. `shared/raylib/README.md` has the build record (the raylib commit, the cmake flags, the compiler, the date, the archive's size) and how to redo the copy after an Odin upgrade.
- The archive links against the system `libdl`, `libpthread` and `libX11` as before. GLFW loads `libwayland-client`, `libwayland-cursor`, `libwayland-egl`, `libxkbcommon` and `libdecor` with dlopen at run time, so the executable's `ldd` shows no new library, and a machine without them falls back to X11. Windowed mode on Wayland draws its decorations through libdecor; Borderless and Fullscreen do not need it.
- `tools/build_raylib.sh` builds the archive: it clones the raylib tag `6.0` from https://github.com/raysan5/raylib (shallow) into `tmp/raylib-src/`, configures in `tmp/raylib-build/` with `-G "Unix Makefiles" -DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF -DBUILD_EXAMPLES=OFF -DPLATFORM=Desktop -DGLFW_BUILD_WAYLAND=ON -DGLFW_BUILD_X11=ON -DCMAKE_POSITION_INDEPENDENT_CODE=ON` (the generator is named because the user environment sets `CMAKE_GENERATOR=Ninja`, which the container lacks), builds, copies `libraylib.a` into `shared/raylib/linux/` and rewrites the README's build record. The host has no cmake and no development headers, so by default the script runs inside the distrobox `mine-oh-belowed-raylib` (image `registry.fedoraproject.org/fedora-toolbox:44`, created on first use with cmake, gcc, make, git and the Wayland, wayland-protocols, xkbcommon, libdecor, Mesa GL and X11 development packages; the home directory is shared, so the script calls itself inside it with `--host`). `tools/build_raylib.sh --host` runs the same steps on a machine that has the tools. The archive is committed (about 3.4 MB, rebuilt rarely), so a fresh checkout builds without cmake or a container.
- Bazzite is an immutable image with runtime libraries but without development symlinks: `libX11.so.6` exists, `libX11.so` does not, so linking fails with `cannot find -lX11`. The fix that avoids layering packages onto the image is a shim directory of symlinks to the runtime libraries, passed with `-extra-linker-flags:"-L<dir>"`. `build.sh` creates `tmp/linker-shims/` with `libX11.so -> /usr/lib64/libX11.so.6` and `libSDL3.so -> /usr/lib64/libSDL3.so.0`. Verified 2026-09-26 by compiling and linking a raylib hello world.
- SDL3: the host `libSDL3.so.0` is 3.4.16 (Fedora 44 package). `vendor:sdl3` links `system:SDL3`, so the same shim applies.

Commands (`build.sh` uses the toolchain at `${ODIN:-$HOME/opt/odin/odin}`):

```
./build.sh            # debug build (-debug) to build/mine-oh-belowed
./build.sh debug      # same as above
./build.sh release    # optimised build (-o:speed) to build/mine-oh-belowed
./build.sh check      # odin check src -vet -strict-style (with the collection)
./build.sh test       # odin test src (with the collection)
./build.sh bench      # the factory benchmark test, optimised (-o:speed)
```

`./build.sh bench` runs only `test_factory_benchmark` (work item 0050) with `-o:speed`: it builds the benchmark factory at sizes 1 and 4, logs both tables and fails when size 4 averages 8 milliseconds per tick or more, half the 60 Hz budget. The plain `./build.sh test` (and CI) runs the same test unoptimised and only logs the numbers, since an unoptimised build's timings are not the release's.

Every command passes `-collection:shared=<repository>/shared`. Both build modes pass `-vet -strict-style` and `-extra-linker-flags:"-L<repository>/tmp/linker-shims"`, creating the shim directory first.

Command line (parsed with `core:flags` in Unix style, `--help` or `-h` prints the usage page and exits): `config` (prints the configuration files found and the effective values, no window), `--set=<key>=<value>`, `--load=<world>`, `--name=<world>`, `--unlock-all`, `--version`, `--input=sdl3` or `--input=raylib` (default: SDL3 with raylib fallback), `--seed=<unsigned 64 bit decimal>` (default a fixed constant so runs are reproducible), `--debug-terrain` (the fixed 8 by 2 by 8 chunk test terrain instead of the generated world, nothing streams), `settings.font` and `settings.monospace_font` (0077) take family ids from `data/fonts/fonts.sjson`, an unknown id is refused like any other configuration error. `--watch-data=<off|presentation|all>` (0054, also the `settings.watch_data` key with `default` following developer mode) chooses what reloads while the game runs, and the developer flags of work item 0043: `--dev` (a Developer entry in the pause menu, see `ui.md`; the settings screen's Developer mode toggle does the same without launch options), `--chapter=<n>` (a new world with the quests before chapter n completed and their rewards delivered, plus chapter n's kit from `data/dev_kits.sjson`) and `--give=<item>:<count>` (repeatable, items into the inventory on the first tick, the rest into the drop capsule). `--chapter` and `--give` start a world like `--seed`; `--chapter` cannot be combined with `--load`. `--benchmark=<size>` (work item 0050, size 1 to 16) runs the headless factory benchmark instead of the game: no window and no controller, the shipped data, two simulated minutes of warm up and ten measured, then the table on stdout (milliseconds per tick per simulation system, the average and worst tick, the entity counts, the idle machines); it exits 1 when the factory cannot be built or a machine idles, and cannot be combined with `--load`, `--seed`, `--name`, `--chapter` or `--debug-terrain`. Quote its numbers from the release build: `./build.sh release && ./build/mine-oh-belowed --benchmark=16`. Size 16 takes about a quarter of a minute of wall time. Larger sizes are not offered (user, 2026-09-28): the cost per tick is close to linear in the size, so read them off size 16, and a size 64 build took minutes, since every placement rebuilds the belt, fluid and electric networks. A bad command line exits with status 2 (unknown items and chapters included), a failed start with status 1.

At run time the game looks for its data directory in this order: `$MINE_OH_BELOWED_DATA` if set, `./data`, then `<executable directory>/../share/mine-oh-belowed/data` (the layout the Nix package installs). `build/mine-oh-belowed --version` prints the build stamp without opening a window: the version, the short commit (`+dirty` with uncommitted changes) and the UTC build time. The same stamp shows under the title screen's name, at the bottom of the pause menu and in the log's header line, so a bug report from the couch can name the build. `build.sh` passes commit and time as one `BUILD_INFO` define (one string with a space, since a define holding only digits arrives as a number), the play build installer passes the archived commit in `MINE_OH_BELOWED_COMMIT`, and the Nix build uses the flake's revision and last modified date.

## Steam library shortcut

`tools/install_play_build.sh` builds a commit (HEAD, or the commit given as its argument) in release mode from a `git archive` into its own directory `bin/play/builds/<install time>-<commit>/` with its own copy of `data/`, switches the `bin/play/current` link to it in one rename, and writes the launcher `bin/mine-oh-belowed`, which resolves the link at launch. The install never waits for the game (double buffering): a running game keeps its build directory and the next launch takes the newest; the two newest builds stay and older ones are removed unless a game still runs from them. The installed game never reads the working tree, so agents editing `src/` and `data/` cannot break a couch session. The couch always runs the latest build: run the script after every commit that lands on `main` (see `CLAUDE.md`). On a Wayland desktop the game opens a native Wayland window (0085): GLFW tries Wayland first, and with the high DPI flag the framebuffer has the panel's pixels under a fractional scale, so a laptop at 2880 by 1920 and 170 percent renders 2880 by 1920 while the window is 1694 by 1129 in the desktop's units. Under gamescope (the couch) the game may now be a Wayland client of gamescope. `MINE_OH_BELOWED_X11=1 bin/mine-oh-belowed` is the way back to X11 if Wayland or gamescope misbehaves: the launcher unsets `WAYLAND_DISPLAY` and sets `XDG_SESSION_TYPE=x11` for the game (unsetting alone is not enough, GLFW's Wayland connection falls back to the `wayland-0` socket). Under XWayland a scaled desktop hands the game the scaled screen and upscales it (0084); the launcher then runs the game inside gamescope when `MINE_OH_BELOWED_GAMESCOPE` holds gamescope's own arguments, which presents it at the panel's full size without changing a desktop setting: `MINE_OH_BELOWED_GAMESCOPE="-f -W 2880 -H 1920" bin/mine-oh-belowed`. With the native Wayland window the laptop no longer needs it; the variable stays as an option. Without gamescope on the path it prints one line to stderr and runs the game directly. The game logs `display: monitor W x H, window W x H, render W x H, scale X x Y, session <x11|xwayland|wayland>` after the window opens and after every display change; the session is the platform GLFW took (`glfwGetPlatform`), `xwayland` for X11 with `WAYLAND_DISPLAY` set, so the `MINE_OH_BELOWED_X11` route reports `x11`. On the couch at scale 1 the line's render equals its window. `tools/make_placeholder_models.py` (0055) writes the placeholder `.vox` machine models into `data/models` deterministically; rerun it after changing it and commit the files. `tools/moc` (Python, standard library only) sends one command line to the running game's command socket and prints the response; the game must run with `--dev` or the developer mode setting, protocol and commands in `commands.md`. `tools/add_steam_shortcut.py` adds or updates the "Mine oh Belowed" non-Steam shortcut in `~/.steam/steam/userdata/<user>/config/shortcuts.vdf`, pointing at that launcher. It parses the binary VDF, refuses to write unless the existing file round trips through its parser byte for byte, and keeps the other shortcuts untouched. Steam must be closed while it runs (check with `pgrep -x steam`), otherwise Steam overwrites the file on exit. `--dry-run` shows what would be written. Steam Input for the shortcut is disabled by hand in Steam's controller settings for the game, see `input.md`.

## Nix

`flake.nix` provides `packages.default` (the game), `devShells.default` (odin, raylib, glfw, sdl3) and `checks`. nixpkgs unstable ships odin dev-2026-09, raylib 6.0 and sdl3 3.4.16, matching the host. The game's raylib binding lives in the repository (0085), so the flake patches it in `postPatch` rather than the Odin package: `shared/raylib/raylib.odin` and `rlgl/rlgl.odin` link `system:raylib` instead of the committed archive, and `platform.odin` links `system:glfw`, since nixpkgs raylib is built against an external GLFW (a build input), which has both backends. libX11 stays a build input for the binding's import block. Both odin calls pass `-collection:shared=shared`. Nix is not installed on the couch machine, so the flake is validated by CI, not locally.

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and pull request on `ubuntu-latest`: enters the development shell and prints the Odin version, then runs `nix build`, which compiles the game with `-vet -strict-style` and runs `odin test src` inside the build.
